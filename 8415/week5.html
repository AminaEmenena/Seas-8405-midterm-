1. What is Zero Trust?
CORE PRINCIPLE: "Never trust, always verify" — no implicit trust based on network location.

Traditional perimeter security followed a castle-and-moat model: everything inside the network was considered trusted. Zero Trust flips this assumption entirely. It treats every access request as potentially hostile, regardless of where it originates.

Zero Trust assumes breach has already occurred.
Every access request must be authenticated, authorized, and encrypted — whether it comes from inside or outside the corporate network.

The term was coined by John Kindervag, a Forrester Research analyst, in 2009. His insight was simple but profound: the traditional perimeter model creates a hard shell with a soft interior. Once an attacker gets past the perimeter, they can move laterally with minimal resistance.

Remember This
"Never Trust, Always Verify" — John Kindervag, Forrester, 2009
Professor Fossaceca's Emphasis: Zero Trust is not a product you buy — it is an architecture philosophy. Vendors who sell "Zero Trust solutions" are marketing; the real work is redesigning how access decisions are made across the organization.

3. NIST SP 800-207 Core Tenets
KEY READING: NIST SP 800-207 is THE authoritative reference on Zero Trust Architecture. Know these tenets.

The Seven Core Tenets

  1. All data sources and computing services are considered resources — not just servers, but IoT devices, SaaS applications, personal devices accessing enterprise data
  2. All communication is secured regardless of network location — internal network traffic gets the same security treatment as external traffic
  3. Access to individual enterprise resources is granted on a per-session basis — no persistent trust; each session is independently evaluated
  4. Access is determined by dynamic policy — considers identity, device health, behavioral attributes, and environmental conditions
  5. Enterprise monitors and measures integrity and security posture of all assets — continuous monitoring, not point-in-time assessments
  6. All resource authentication and authorization are dynamic and strictly enforced — before access is granted, every time
  7. Enterprise collects as much information as possible about current state of assets — feeds into the trust algorithm for better decisions
Memory Aid
7 Tenets: Resources, Secure Comms, Per-Session, Dynamic Policy, Monitor All, Enforce Strictly, Collect Intel
Professor Fossaceca's Tip: NIST SP 800-207 is not prescriptive about implementation — it describes principles. The exam will test whether you understand the PRINCIPLES, not specific vendor implementations.
4. Zero Trust Architecture Components (NIST)
CRITICAL FOR EXAM: Know the three core components and the two planes. This is the structural backbone of ZTA.

Core Components

ComponentRoleAnalogy
Policy Engine (PE)Makes access decisions based on policy and input from data sourcesThe judge — decides yes/no
Policy Administrator (PA)Establishes/shuts down communication paths based on PE decisionsThe bailiff — executes the judge's orders
Policy Enforcement Point (PEP)Enables, monitors, and terminates connections between subjects and resourcesThe security guard at the door

Two Planes

Control Plane

Carries policy and access control decisions. Where PE and PA operate. Think of it as the brain.

Data Plane

Carries the actual data traffic. Where PEP operates. Think of it as the body that does the work.

Best Practice: The PE never directly interacts with the data plane. It makes decisions, the PA implements them, and the PEP enforces them. This separation of concerns is fundamental to ZTA security.
5. Trust Algorithm
DEFINITION: The Trust Algorithm is used by the Policy Engine to determine whether to grant, deny, or require additional authentication for an access request.

Trust Algorithm Inputs

InputWhat It Considers
User IdentityWho is requesting access? Are credentials valid? MFA completed?
Device HealthIs the device patched? Running approved OS? Has endpoint protection?
Behavioral PatternsIs this normal behavior for this user? Unusual time/location?
Threat IntelligenceAre there active threats targeting this resource or user type?
Time of RequestIs this during normal working hours? Is the timing suspicious?

Key Characteristics

  • Dynamic and continuous — access can be revoked mid-session if conditions change
  • Context-aware — same user on a managed device vs personal device may get different access levels
  • Output: Grant access, Deny access, or Require additional authentication (step-up)
Access Request → Trust Algorithm → Grant / Deny / Step-Up
Exam Note: The trust algorithm is NOT a one-time check at login. It continuously evaluates throughout the session. This is what distinguishes Zero Trust from traditional VPN-based access.
6. Deployment Approaches
NIST SP 800-207 identifies multiple deployment approaches. Know the differences and when each is appropriate.
ApproachFocusHow It Works
Enhanced Identity GovernanceIdentity as the primary security boundaryStrong identity verification, conditional access policies, identity-centric controls
Micro-segmentationNetwork segmentationDivides network into small isolated segments, each with independent security controls
Software-Defined Perimeters (SDP)Resource hidingCreates one-to-one connections; resources invisible to unauthorized users

Network-Based vs Identity-Based

Network-Based Approach

Focuses on network segmentation and traffic control. Uses micro-segmentation and network-level policies. Better for environments with strong network infrastructure.

Identity-Based Approach

Focuses on user and device identity as the primary control. Uses strong authentication, conditional access. Better for cloud-first and remote-work environments.

Best Practice: Most mature Zero Trust implementations use a combination of approaches. Start with identity governance (quick wins), then layer in micro-segmentation and SDP as the architecture matures.

8. Micro-segmentation
KEY CONCEPT: Micro-segmentation limits lateral movement — even if one segment is compromised, the attacker cannot easily reach other segments.

Micro-segmentation divides the network into small, isolated zones. Each segment has its own security controls and policies. This is fundamentally about controlling east-west traffic (internal traffic between segments), not just north-south traffic (in/out of the network).

Implementation Levels

  • Network Level — VLANs, SDN, network firewalls between segments
  • Host Level — host-based firewalls, agent-based microsegmentation
  • Application Level — application-aware policies, API gateways
Micro-segmentation Lateral Movement Prevention
WITHOUT MICRO-SEGMENTATION: Attacker → Server A → Server B → Database → Exfiltrate (free lateral movement) WITH MICRO-SEGMENTATION: ┌─────────┐ ┌─────────┐ ┌─────────┐ │Segment A│ X │Segment B│ X │Segment C│ │Server A │ │Server B │ │Database │ │ [PEP] │ │ [PEP] │ │ [PEP] │ └─────────┘ └─────────┘ └─────────┘ Attacker → Server A → BLOCKED (no lateral movement)
Best Practice: Start micro-segmentation around your most critical assets (databases, payment systems) and expand outward. Don't try to segment everything at once.
9. Cryptographic Foundations of Zero Trust
Zero Trust relies heavily on cryptographic mechanisms for authentication and encryption.
MechanismPurposeHow It Works
Mutual TLS (mTLS)Both client and server authenticate each otherBoth parties present certificates; neither trusts the other implicitly
End-to-End EncryptionProtect all communicationsData encrypted from source to destination, not just at the perimeter
Multi-Factor AuthenticationStrong identity verificationSomething you know + something you have + something you are
Short-Lived CertificatesContinuous verificationCertificates expire quickly, forcing re-authentication
Data-at-Rest EncryptionProtect stored dataEven if storage is compromised, data remains encrypted
mTLS is essential to Zero Trust
In regular TLS, only the server proves its identity. In mTLS, BOTH the client and server authenticate each other with certificates. This eliminates the implicit trust that traditional TLS gives to any connecting client.
Exam Focus: Understand WHY mTLS is preferred over regular TLS in Zero Trust. The bidirectional authentication aligns with "never trust, always verify" — the server doesn't trust the client just because it can connect.
10. Implementation Challenges
Zero Trust is not easy to implement. Understanding the challenges is as important as understanding the theory.
ChallengeDetails
Legacy SystemsOlder systems may not support modern authentication, encryption, or policy enforcement
Asset InventoryYou cannot protect what you don't know about — requires comprehensive discovery
Cultural ShiftMoving from "trust but verify" to "never trust, always verify" requires organizational buy-in
Policy ComplexityManaging granular access policies at scale is operationally complex
Performance OverheadContinuous authentication and encryption add latency and processing overhead
Infrastructure InvestmentMay require significant investment in identity systems, monitoring, and segmentation tools
Professor Fossaceca's Perspective: The biggest barrier to Zero Trust adoption is not technology — it's organizational inertia. Executives understand the concept, but the operational complexity of implementation across legacy environments is where most organizations stall.
Best Practice: Implement Zero Trust incrementally. Start with identity (MFA, conditional access), then tackle device trust, then micro-segmentation. Trying to do everything at once leads to failure.
11. Jericho Forum & De-perimeterization
HISTORICAL ORIGIN: The earliest formal work on what became Zero Trust came from the Jericho Forum — a security consortium of CISOs wrestling with the limitations of perimeter security.

The Jericho Forum was founded by Paul Simmonds in 2007 (the same year as the first iPhone). It was a consortium of chief information security officers who recognized that the traditional perimeter model was failing and would continue to fail as technology evolved.

Core Concept: De-perimeterization

The Jericho Forum promoted de-perimeterization: the idea that organizations should protect enterprise data flowing in and out, rather than trying to keep it behind a network boundary. The core idea was simple but radical: "secure assets where they are" — stop confining assets to a network they don't belong on.

Key Insight: De-perimeterization has happened, is happening, and is inevitable. Central protection is decreasing in effectiveness as data and users move beyond traditional boundaries.

The Jericho Forum developed a generic roadmap to assist organizations in planning their transition away from perimeter-centric security toward data-centric protection.

Remember This
Jericho Forum (2007) = De-perimeterization = "Secure assets where they are"
12. Jericho Forum Commandments
FOUNDATIONAL PRINCIPLES: The Jericho Forum Commandments laid the groundwork for what would become Zero Trust thinking.

Fundamentals

  • (1) The scope and level of protection should be specific and appropriate to the asset at risk
  • (2) Security mechanisms must be pervasive, simple, scalable, and easy to manage
  • (3) Assume context at your peril

Surviving in a Hostile World

  • (1) Devices and applications must use open, secure protocols — enforce the network to only allow encrypted protocols and eliminate insecure ones
  • (2) All devices must be capable of maintaining their security policy on an untrusted network

Need for Trust

  • (1) All people, processes, and technology must have declared and transparent levels of trust
  • (2) Mutual trust assurance levels must be determinable

Identity, Management, and Federation

  • (1) Authentication, authorization, and accountability must interoperate outside your locus of control

Access to Data

  • (1) Access controlled by security attributes of the data itself
  • (2) Data privacy requires segregation of duties/privileges
  • (3) By default, data must be appropriately secured when stored, in transit, and in use
Professor Note: The Jericho Forum Commandments read like an early blueprint for Zero Trust. Notice how "assume context at your peril" foreshadows "never trust, always verify."
13. Kindervag and Forrester (2009)
ORIGIN OF THE TERM: John Kindervag coined "Zero Trust" in 2009 at Forrester Research — NOT 2010 as commonly stated.

Kindervag's core belief was that "trust is a vulnerability". Security must be designed with the principle of "Never trust, always verify." Any implicit trust granted to users, devices, or network segments creates an exploitable weakness.

Kindervag's Zero Trust Model

  • Workload-first: Focus security on protecting workloads, not network segments
  • Data-driven: Use data about users, devices, and context to make access decisions
  • Identity-aware: Identity is the new perimeter — every access request must be tied to a verified identity

Kindervag argued that Zero Trust improves both security AND employee experience. However, the professor raises the question: "But does it?" — challenging students to think critically about whether the additional verification steps truly improve or hinder the user experience.

Common Mistake: Many sources (and even some exam prep materials) cite 2010 as the year Kindervag coined Zero Trust. The correct year is 2009.
Remember This
Kindervag (2009): "Trust is a vulnerability" — Never trust, always verify
14. Perimeter vs Zero Trust Architecture Comparison
KEY COMPARISON: Understanding the architectural differences between perimeter security and Zero Trust is essential for the exam.
AspectPerimeter SecurityZero Trust
Security Perimeter Static: defined around environment boundary Dynamic: defined by transaction attributes
Access Approach Trust Model: users authorized by identity, role, clearance Transactional Model: authorization based on attributes for each transaction
Access Longevity Persistent: decisions in place as long as role unchanged Temporal: decisions only for duration of transaction, then re-evaluated
Key Takeaway: Perimeter security is static, trust-based, and persistent. Zero Trust is dynamic, attribute-based, and temporal. This shift from static to dynamic is the fundamental architectural change.

17. Implicit Trust Zone
KEY CONCEPT: Understanding implicit trust zones is critical for ZTA exam questions.

An implicit trust zone is the area beyond the Policy Enforcement Point (PEP) where all entities are trusted to at least the level of the last PDP/PEP gateway. In other words, once you pass through a PEP, you are within a zone where a certain level of trust is assumed.

Zero Trust Principle: Move the PDP/PEPs closer to the resource. The smaller the implicit trust zone, the more granular the security.
Important: The entire enterprise private network is NOT considered an implicit trust zone in Zero Trust. That would be the old perimeter model. Instead, implicit trust zones are kept as small as possible.

All connections must be authenticated and all traffic encrypted, regardless of network location. There is no "safe inside" — every segment requires its own verification.

Remember This
Implicit Trust Zone = area beyond PEP | ZT shrinks these zones as small as possible
18. ZT Data & Policy Sources
DATA INPUTS: The Zero Trust policy engine relies on multiple data sources to make access decisions.

Key Data and Policy Sources

  • CDM (Continuous Diagnostics and Mitigation) system — monitors network and device health
  • Industry compliance system — ensures regulatory requirements are met
  • Threat intelligence feeds — external threat data to inform decisions
  • Network and system activity logs — behavioral and activity data
  • Data access policies — rules governing who can access what data
  • Enterprise PKI — certificate management and cryptographic identity
  • ID management system — user identity and authentication data
  • SIEM (Security Information and Event Management) system — aggregated security event analysis
Professor Note: The policy engine does not operate in isolation. It synthesizes inputs from ALL of these sources to make a single access decision. Know these data sources for the exam.
19. Three NIST ZTA Deployment Models
NIST MODELS: NIST SP 800-207 defines three distinct deployment models for Zero Trust Architecture.

Figure 3: Device Agent/Gateway Model

An agent installed on the device communicates with a gateway that protects the resource. The agent acts as the subject-side PEP component.

Figure 4: Enclave Gateway Model

A gateway protects a resource enclave — a group of related resources. This model is useful when resources are naturally grouped together.

Figure 5: Resource Portal Model

A gateway portal serves as a single entry point to data resources. All access goes through this centralized portal.

Common Architecture: All three models maintain the separation of the Control Plane (Policy Engine + Policy Administrator) from the Data Plane (Subject → PEP → Resource).
NIST ZTA Deployment Model Structure
CONTROL PLANE ┌─────────────────────────┐ │ Policy Policy │ │ Engine Administrator │ └─────────────────────────┘ │ ─ ─ ─ ─ ─ ─│─ ─ ─ ─ ─ ─ ─ │ DATA PLANE Subject ──── PEP ──── Resource(s)
20. Zero Trust Network vs Software-Defined Perimeter
KEY COMPARISON: Know the differences between ZTN and SDP — they are complementary but distinct.
AspectZero Trust NetworkSoftware-Defined Perimeter
Core Focus "Never trust, always verify" — continuous authentication for all Dynamically create secure, isolated connections; hide resources
Architecture Security philosophy using auth, authz, micro-segmentation, monitoring Defined framework using SDP controllers and gateways
Auth & Authz Continuous, per-request based on identity, device, context Strong cryptographic methods ensure only verified users/devices connect
Visibility Deep insight into traffic and user behavior Tracks who accesses what; resources hidden from public internet
Deployment Flexible, coexists with existing infrastructure Requires SDP controllers/gateways, often for remote access
Key Distinction: Zero Trust is a security philosophy that can be implemented many ways. SDP is a specific framework/architecture that implements many Zero Trust principles. SDP can be a tool within a broader Zero Trust strategy.
