W1 — Ciphers, Fundamentals & Hashing
  • CRYPTOGRAPHY DEFINED: Science of secure communication in presence of adversaries. Three goals: Confidentiality (only authorized access), Integrity (data not altered), Authentication (verify identity). Kerckhoffs' Principle: security depends on KEY secrecy, not algo secrecy — all modern algos are public (AES, RSA). Opposite of "security through obscurity." Why proprietary ciphers are risky: lack rigorous peer review needed to find vulnerabilities.
  • ATOMIC PRIMITIVES: Higher-level protocols built on atomic primitives. Two types: (1) Engineered constructs — designed by humans (AES, SHA-256), (2) Mathematical problems — found in nature (discrete log, factoring). Protocols tell parties what to do but NOT the adversary. The adversary NEVER vanishes in formal analysis. Prof Fossaceca emphasis: "the Game of cryptography."
  • CLASSICAL — SUBSTITUTION: Caesar cipher = monoalphabetic, shift each letter by fixed amount, trivially broken by frequency analysis. Monoalphabetic = 1-to-1 letter mapping, vulnerable to frequency analysis. Vigenere = polyalphabetic, uses repeating keyword to change substitution per position, defeats simple frequency analysis but broken by Kasiski examination. Key distinction: polyalphabetic > monoalphabetic.
  • CLASSICAL — TRANSPOSITION: Rail Fence = write plaintext in zigzag across rows, read off by row. Columnar transposition = rearrange columns based on keyword. Bifid = UNIQUE because it combines substitution WITH transposition using Polybius square. Key distinction: substitution CHANGES letters, transposition REARRANGES positions.
  • SHANNON'S PERFECT SECRECY & OTP: Claude Shannon (1949) defined perfect secrecy: ciphertext reveals ZERO information about plaintext. P(M|C) = P(M). One-Time Pad = ONLY cipher achieving perfect secrecy. OTP requirements: key must be (1) truly random, (2) as long as message, (3) used only ONCE, (4) kept secret. OTP is impractical — key distribution/management impossible at scale. Computational security = practical alternative: cost/time to break exceeds value of information.
  • SHANNON'S 5 CRITERIA (1949): (1) Degree of secrecy = amount of labor to break, (2) Algorithm should be free from complexity, (3) Implementation should be simple, (4) Ciphertext size <= plaintext size (C <= P), (5) Error propagation should be limited. Prof emphasized: "STILL VALID TODAY" — likely testable!
  • COMPLEXITY THEORY: Probability of breaking a cipher <= t/2^200 where t = number of computing cycles. Adversary modeled as probabilistic polynomial-time (PPT) algorithm. Security proven by reduction: if breaking cipher is easy --> solving known hard problem is also easy (contradiction). This is the formal foundation of modern cryptographic security proofs.
  • SYMMETRIC vs ASYMMETRIC: Symmetric = same key enc/dec (fast, bulk data, AES). Asymmetric = pub/priv key pair (slower, solves key distribution, RSA/ECC). Hybrid systems = use asym to exchange sym key, then sym for data (TLS model). Symmetric is 100-1000x faster than asymmetric.
  • HASHING: One-way functions: easy to compute, infeasible to reverse. Properties: deterministic, fixed-length output, avalanche effect (small input change --> drastically different output), collision resistance. MD5 = 128-bit, BROKEN (collisions found). SHA-1 = 160-bit, deprecated. SHA-256/SHA-3 = current standards. Also: RIPEMD, Tiger, HAVAL. NOT encryption — hashing is IRREVERSIBLE.
  • SALTING & PASSWORD SECURITY: Salt = unique random string added BEFORE hashing. Ensures identical passwords produce different hashes. Defeats rainbow table attacks (precomputed hash lookups). Each user gets unique salt stored alongside hash.
  • KEY STRETCHING: Transforms weak/short password into stronger key. PBKDF2 = applies HMAC repeatedly (thousands of iterations). bcrypt = based on Blowfish, includes automatic salt, adaptive cost factor. Deliberately slow — that's the FEATURE. Makes brute-force expensive even with weak passwords.
  • HMAC: Hash-based Message Authentication Code. Combines hashing with secret key. Provides Integrity AND Authentication (NOT confidentiality). HMAC = Hash(key || message). Used in TLS, API auth, data integrity verification.
  • DATA STATES: At Rest = stored on persistent media (HDD, DB) --> encrypt with AES. In Transit = moving across networks --> protect with TLS/SSL. In Use = processed by CPU --> hardest to protect (emerging: secure enclaves, homomorphic encryption).
  • BLOCK vs STREAM CIPHERS: Block = encrypt fixed-size blocks (AES = 128-bit blocks). Stream = encrypt one bit/byte at a time (RC4, ChaCha20). Modern block ciphers use substitution-permutation networks.
  • PRNG PROPERTIES: Pseudo-Random Number Generators. Requirements: uncorrelated sequences (output not predictable from prior values), long period (no repeats), uniformity (all values equally likely). CSPRNG (Cryptographically Secure PRNG) required for crypto — weak PRNGs --> predictable keys.
  • SYMMETRIC CIPHER COMPARISON: RC4: stream, 40-2048 bit key, BROKEN (WEP). DES: 56-bit key, 64-bit block, BROKEN 1999. 3DES: 112/168-bit key, 64-bit block, deprecated, 3x slower. AES: 128/192/256-bit key, 128-bit block, CURRENT STANDARD, selected 2001.
  • MATH FOUNDATIONS: Modular arithmetic: a mod n = remainder. XOR (XOR): key operation in ciphers. GCD: important for RSA key gen. Primes >3 are form 6k+/-1. Binary key space: n-bit key = 2^n possible keys. Permutations (order matters) vs Combinations (order doesn't).
  • ENIGMA: No plaintext letter ciphered as itself — key vulnerability allowing Allies to dismiss translations. Alan Turing cracked it at Bletchley Park.
  • KASISKI EXAMINATION: Systematic attack breaking polyalphabetic ciphers (Vigenere). Finds repeated ciphertext sequences to determine keyword length.
  • PRE-IMAGE RESISTANCE: Infeasible to find ANY input mapping to specific hash. Different from collision resistance. TRAP: Avalanche effect = small change --> big output change, NOT about collisions.
  • NONCE: Unique random number used ONCE. Prevents replay attacks. HMAC fails non-repudiation because both parties share key. One-way function analogy: smashing a plate.
  • KEY LENGTH MATH: N to N+k bits = key space x 2^k. 8-->16 bits = 256x more keys. Brute force average = 2^(N-1) not 2^N. NVIDIA CUDA enables parallel brute-force cracking.
  • PUB KEY TWO USES: (1) Digital Signatures, (2) Symmetric Key Exchange. NOT "confidentiality" as primary. Message Digest = fixed-size hash output. Washington's spies = invisible ink (steganography).
W2 — Asymmetric Crypto & Key Exchange
  • KEY DISTRIBUTION PROBLEM: Symmetric crypto's fundamental challenge: N users need N(N-1)/2 keys for pairwise communication — doesn't scale. 10 users = 45 keys, 100 users = 4,950 keys. Motivated invention of public key cryptography.
  • DIFFIE-HELLMAN (1976): First published public key exchange (Diffie & Hellman). Based on discrete logarithm problem. How it works: Alice & Bob agree on public p (prime) and g (generator). Each picks secret (a, b). Exchange g^a mod p and g^b mod p. Both compute shared secret g^(ab) mod p. DOES NOT authenticate — vulnerable to MITM. Example: p=23, g=5, a=6, b=15 --> shared secret.
  • RSA (1977): Rivest, Shamir, Adleman. Based on difficulty of factoring product of two large primes. Key gen: pick p,q (large primes) --> n=p*q --> phi(n)=(p-1)(q-1) --> choose e coprime to phi(n) --> d=e^(-1) mod phi(n). Public key=(n,e). Private key=(n,d). Encrypt: c=m^e mod n. Decrypt: m=c^d mod n. Trap-door function: easy forward, hard reverse without key.
  • DIGITAL SIGNATURES: Provide authentication + integrity + non-repudiation. Sign with PRIVATE key, verify with PUBLIC key (opposite of encryption). Process: hash message --> encrypt hash with private key = signature. Non-repudiation: signer cannot deny (unique private key). Anyone with public key can verify.
  • PKI: Public Key Infrastructure. CA (Certificate Authority) = trusted third party issuing certificates. Certificate binds identity to public key. Chain of trust: Root CA --> Intermediate CA --> End entity. Certificate revocation: CRL (Certificate Revocation List) and OCSP (Online Certificate Status Protocol).
  • TRAP-DOOR FUNCTIONS: One-way functions with secret "trap door" enabling reversal. RSA trap door: knowing factorization of n (p,q) allows computing d. Foundation of all public key crypto.
  • HYBRID ENCRYPTION: Combines asymmetric (key exchange) with symmetric (data). Asymmetric is 100-1000x slower. TLS: use RSA/DH to exchange AES session key, then AES for bulk data. Envelope encryption: encrypt data with sym key, encrypt sym key with pub key.
  • KEY MANAGEMENT: Generation: use CSPRNG. Storage: protect private keys (HSMs, key vaults). Rotation: periodically change keys. Escrow: third party holds copy (controversial — law enforcement vs privacy).
  • MITM ATTACKS: Attacker intercepts key exchange, establishes separate keys with each party. Defeats plain DH (no auth). Prevention: digital signatures, certificates, authenticated key exchange. "Double Key Creation" = encrypt session key once for server, once for law enforcement.
  • DH CALCULATION (EXAM): g=2,p=19,a=6,b=3: Y=2^6 mod 19=7, C=2^3 mod 19=8, S=8^6 mod 19=18 or 7^3 mod 19=18. MATCH. Use repeated squaring for large exponents. One-way func is "easy/simple/feasible" to compute (NOT "efficient").
  • ECC: Elliptic Curve Cryptography. Lighter, more agile alternative to RSA. Smaller keys: ECC-256 approx RSA-3072. Ideal for IoT, mobile, battery-powered devices. Based on ECDLP (Elliptic Curve Discrete Log Problem). ECDSA (signatures), ECDH (key exchange). CAB Forum now requires RSA minimum 3072 bits — driving ECC adoption.
  • "RSA IS DEAD" DISCUSSION: 90% of internet SSL connections still use RSA. Key length must keep growing (3072+ now). CSPRNG seeding vulnerability: weak RNG --> predictable keys. Key scaling problem: RSA grows exponentially, ECC stays small. Quantum threat via Shor's algorithm.
  • POST-QUANTUM CRYPTOGRAPHY: Shor's algorithm = quantum algorithm breaking RSA, DH, ECC (factors/solves discrete log in polynomial time). NIST PQC standardization: 5 candidate categories: (1) Code-based (McEliece), (2) Lattice-based (CRYSTALS-Kyber, CRYSTALS-Dilithium — NIST winners), (3) Hash-based (SPHINCS+), (4) Multivariate polynomial, (5) Super-singular isogeny (SIKE — BROKEN 2022). "Harvest now, decrypt later" = adversaries collect encrypted data today to decrypt with future quantum. NIST migration timeline: by 2035.
W3 — Secure Design & Usability
  • WHY JOHNNY CAN'T ENCRYPT (Whitten & Tygar 1999): Landmark PGP 5.0 usability study. Even technically competent users made critical errors. "Quill pen" icon problem: failed to communicate private key was used for signing. Users confused encryption with signing. 1/3 of participants sent secrets WITHOUT encrypting. Key insight: security software must be usable or people won't use it correctly.
  • WHY CRYPTOSYSTEMS FAIL (Anderson 1993): Studied real-world banking crypto failures. Key finding: most failures NOT from broken algorithms but implementation/configuration errors. Over 90% of computer security failures = config/implementation errors. Crypto community lacks "learning mechanism" found in aeronautical engineering (govt secrecy). Banking "phantom withdrawals" — banks blamed customers. Anderson: security bugs should be tracked/published like aviation incidents.
  • "U" IN CRYPTO STANDS FOR USABLE: Mobile cryptocurrency wallet usability study. "Uninformed people" gave 1-star reviews for issues dev had no control over (network fees). Primary cause of double-spends: poor interface design — Send button fails to give immediate clear feedback. Blockchain irreversibility amplifies UX errors — single mistake = permanent financial loss. Users apply "traditional payment" mental model expecting reversibility.
  • BARN DOOR PROPERTY: Once a secret is exposed, can't be un-exposed. Makes PREVENTION of high-cost errors a design priority. Especially critical in crypto wallets: blockchain irreversibility = errors permanent. Design implication: build guardrails BEFORE mistakes happen.
  • ABSTRACTION PROPERTY: Security management involves abstract rules/policies alien to general users. Users don't think about security until something goes wrong. Good design makes security invisible and automatic.
  • COGNITIVE WALKTHROUGH: Usability evaluation technique particularly fitting for security. Evaluator mentally simulates novice user's understanding. Concerned with learnability. Can be done WITHOUT actual users (expert evaluation). Ask: will user know what to do? Notice correct action? Understand feedback?
  • IEEE TOP 10 SECURE DESIGN FLAWS: (1) Earn or Give, But Never Assume, Trust — don't offload security from server to client. (2) Use Cryptography Correctly — don't roll your own, use established libraries. (3) Authorize After You Authenticate — knowing identity != allowing all actions. (4) Strictly Separate Data and Control Instructions — prevent injection. (5) Define approach ensuring all data explicitly validated. (6) Use strong auth. (7) Compartmentalize and isolate. (8) Least privilege. (9) Don't implement security yourself. (10) Make security usable.
  • OWASP CRYPTOGRAPHIC FAILURES (Top 10 #2): Three categories: (1) Loss of confidentiality (data exposure), (2) Non-repudiation failure, (3) Failed integrity checks. Common mistakes: weak algos (MD5, SHA-1, DES), hardcoded keys, improper key mgmt. "Access control vulnerabilities" is NOT one of the three (separate OWASP category).
  • CLIPPER CHIP & KEY ESCROW (1993): US govt proposed hardware enc device with built-in backdoor. Used classified Skipjack algo. Key escrow = govt holds copies of enc keys. Matt Blaze found protocol vulnerability. Public backlash killed it. Lesson: can't have strong encryption AND guaranteed govt access — fundamental trade-off. Prof Fossaceca emphasized as recurring theme.
  • LAW ENFORCEMENT ACCESS: "Going dark" problem: can't access encrypted comms even with warrant. Apple vs FBI (2015-16): FBI demanded backdoor for San Bernardino phone. Apple refused (dangerous precedent). FBI used third-party tool (Cellebrite). "Double Key Creation" = encrypt session key for server AND for law enforcement pub key. No technical solution providing access ONLY to "good guys."
  • RONIN NETWORK HACK (2022): $620M stolen from Axie Infinity blockchain bridge. Root cause: compromised private keys (5 of 9 validators). Usability failure: reduced validators 9-of-9 to 5-of-9 for "convenience." Temporary Sky Mavis permission never revoked. Barn Door Property in action — funds irrecoverable. Security config shortcuts have permanent consequences.
  • OWASP RENAME: "Sensitive Data Exposure" --> "Cryptographic Failures" (2021). Shifted from symptom to root cause. Flaw=design mistake, Bug=implementation issue. "Agility"=capability to change algos as needed.
  • HW-TESTED DETAILS: RBF (Replace-by-Fee)=overwrite stuck Bitcoin tx w/ higher fee. Hard-coded passwords=significant failure mode. 96% negative reviews (not 94%). PGP users encrypted w/ OWN pub key (not recipient's). Unmotivated User Property=users don't seek security. Lack of Feedback Property=software can't error-check because only user knows intent. Salting !=Seeding (salt=unique hashes, seed=PRNG start). Anderson's paradigm shift=fuse security w/ software engineering.
W4 — Zero Knowledge Proofs
  • ZKP DEFINITION: Proof where Prover convinces Verifier a statement is true WITHOUT revealing any information beyond truth of statement. Example: prove you know a password without revealing it. Invented by Goldwasser, Micali, Rackoff (1985). Three properties: (1) Completeness — honest prover convinces honest verifier of true statement, (2) Soundness — cheating prover can't convince verifier of false statement (except negligible probability), (3) Zero-knowledge — verifier learns NOTHING beyond whether statement is true. Threat model assumes potential cheating from Prover.
  • ALI BABA CAVE (Quisquater): Peggy (Prover) proves she knows secret word to open door in circular cave. Victor (Verifier) waits outside, Peggy enters path A or B. Victor calls which path to exit. If Peggy knows secret, always exits correctly. Cheating probability = 1/2^n after n rounds — negligible.
  • INTERACTIVE vs NON-INTERACTIVE: Interactive = back-and-forth between Prover and Verifier. Non-interactive = single proof message anyone can verify. Fiat-Shamir heuristic: transforms interactive ZKP into non-interactive by replacing Verifier's random challenges with hash function output. Peggy uses one-way hash to ensure Victor cannot learn polynomial amount of info.
  • zk-SNARKs: Zero-Knowledge Succinct Non-interactive ARgument of Knowledge. (zk) = proving without revealing. (S) = Succinct — computationally feasible, proof small enough to verify in milliseconds. (NARK) = Non-interactive Argument of Knowledge — no back-and-forth. Require trusted setup phase — creates initial parameters. Trusted setup = vulnerability: if compromised, fake proofs possible. Properties: Completeness, Soundness, Zero-knowledge, Succinct, Non-interactive, Argument (soundness vs PPT prover), of Knowledge (proof can't be constructed without witness). Proof size: ~100s of bytes. Verification: ~10ms. Used in Zcash. VULNERABLE to quantum attacks (uses elliptic curves).
  • zk-STARKs: Zero-Knowledge Scalable Transparent ARgument of Knowledge. Key advantage: NO trusted setup (transparent) — uses public randomness. Quantum resistant (uses hash functions, not ECC — Grover's doesn't meaningfully break collision-resistant hashing). Larger proofs (~100s of kilobytes) but more scalable. Starkware = company commercializing. "Verifiable trust." Proof size: ~100s KB. Verification: 50-100ms.
  • SNARKs vs STARKs DETAILED: Trusted setup: SNARKs YES, STARKs NO. Crypto basis: SNARKs = elliptic curves/pairings, STARKs = hash functions. Scalability: SNARKs less scalable, STARKs highly scalable. Proof size: SNARKs ~100s bytes (small), STARKs ~100s KB (larger). Verify speed: SNARKs faster (~10ms), STARKs slower (50-100ms). Quantum: SNARKs NOT safe, STARKs safe. Maturity: SNARKs more mature/widely adopted, STARKs newer. Communication complexity: SNARKs grow linearly, STARKs polylogarithmic. Prover complexity: STARKs ~10x faster as computation increases.
  • PINOCCHIO: First general-purpose verifiable computation system. Client creates public evaluation key. Worker evaluates computation + produces proof of correctness. Proof = only 288 bytes regardless of computation size. Verification: 5-7 orders of magnitude faster than previous work (~10ms). First to demonstrate verification cheaper than native execution. Reduces worker proof effort 19-60x. Generalizes to ZKP at negligible cost. End-to-end toolchain: compiles C subset into verifiable programs.
  • SELF-SOVEREIGN IDENTITY: Personal data (DOB, SSN) = our identity. Facebook data mining + Equifax breach = orgs can't be trusted. Self-sovereign identity: individuals own/manage their data. zk-SNARKs enable proving identity without sharing sensitive info. Crypto proof can't be linked to data used to create it. With ZKP, Equifax-type leaks could become thing of the past.
  • ZCASH — zk-SNARKs IN PRACTICE: First widespread zk-SNARK application. Shielded transactions: fully encrypted on blockchain but verifiable. Requires trusted setup via multi-party ceremony. Original: 6 participants, 5 revealed identities. 6th = pseudonym "John Dobbertin" = Edward Snowden. Zerocash protocol. Cons: computationally intensive, complicated setup, incorrect implementation --> coin forgery. New ceremony: 88 participants. Zcash market cap ~$794M (Sept 2025).
  • TRUSTING TRUST (Ken Thompson 1984): Turing Award lecture. Can't fully trust code you didn't write (even compiler). Self-replicating Trojan: modify compiler to insert backdoor, then modify compiler to insert the modification — persists even with clean source. Thompson: "more balanced media portrayal" needed. Trust is fundamental and hard to establish in computing.
  • QUANTUM RESISTANT vs PROOF: Important distinction from lecture. Resistant = like water RESISTANT watch (resists to certain depth). Proof = WATERPROOF (impervious). Until true quantum capabilities known, can only claim RESISTANCE. zk-STARKs = quantum resistant. zk-SNARKs = vulnerable. May not see changes to Bitcoin/Ethereum encryption until mainstream quantum closer.
  • COMMITMENT SCHEMES: Coin-tossing vs ZKP distinction. Commitment scheme = Alice commits to value without revealing, later opens. Different from ZKP (which proves knowledge without revealing).
  • HW-TESTED TRAPS: Acme Bank handle time reduced by C&D (reduce questions + streamline verification), NOT "all of the above." Hash in ZKP = "prevent cheating" (soundness), NOT "surrogate for verifier." "Succinct"=small proof size. FRI=method proving function close to low-degree polynomial. "Cut and choose"=basic ZKP technique (Schneier). PCPs=key to verifiable computation. Ripple NOT a zk-STARK adopter. Thompson read about Trojans in Air Force Multics critique.
W5 — Zero Trust Architecture
  • WHAT IS ZERO TRUST: "Never trust, always verify." Security model: no one blindly trusted inside network. Supports "least privilege access." Conceived in response to: mobile/remote workers, BYOD trend, shadow IT, cloud services. At its core: effective Identity and Access Management Platform. ZT brings back control in face of dissolving network perimeter.
  • WHY ZERO TRUST: Move to cloud --> APIs, distributed microservices, IoT ecosystems. Each "thing" = sophisticated actor. Data protected in every deployment model. Consumer-facing services (banking, healthcare, connected car, telco) already use ZT models. Convergence of: identity, trust, authorization, access. Global ZT market projected $52 billion by 2026 (CNBC). Driving growth: frequency of target-based cyber attacks + increasing regulations.
  • JERICHO FORUM (2007): Earliest formal work on Zero Trust concepts. Security consortium of CISOs. Founded by Paul Simmonds (same time as first iPhone). Promoted "de-perimeterization": protect data flowing in/out rather than behind boundary. "Secure assets where they are." De-perimeterization has happened, is happening, is inevitable; central protection decreasing. Generic roadmap for planning.
  • JERICHO COMMANDMENTS: Fundamentals: (1) Protection scope specific/appropriate to asset at risk, (2) Security mechanisms must be pervasive, simple, scalable, easy to manage, (3) Assume context at your peril. Surviving Hostile World: (1) Use open, secure protocols — eliminate insecure ones, (2) All devices maintain security on untrusted network. Need for Trust: (1) Declared/transparent trust levels, (2) Mutual trust assurance determinable. Identity/Federation: Auth/authz/accountability interoperate outside your control. Access to Data: (1) Controlled by data's security attributes, (2) Privacy requires segregation of duties, (3) Data secured when stored, in transit, AND in use.
  • KINDERVAG & FORRESTER (2009): John Kindervag coined "Zero Trust" at Forrester in 2009 (NOT 2010). Core belief: "trust is a vulnerability." Security designed with "Never trust, always verify." Workload-first, data-driven, identity-aware model. Improves security AND employee experience (Prof: "But does it?").
  • NIST SP 800-207 (2020): Abstract definition of ZTA. General deployment models and use cases. Also: "Planning for ZTA: Starting Guide for Administrators" (Aug 2021). Why NIST: vendor neutral, standardized definitions, used as specifications/requirements.
  • ZT vs ZTA vs ZTE DEFINITIONS: Zero Trust (ZT) = collection of concepts designed to minimize uncertainty in enforcing accurate, least privilege per-request access decisions in systems viewed as compromised. Zero Trust Architecture (ZTA) = enterprise cybersecurity plan utilizing ZT concepts, encompassing component relationships, workflow planning, access policies. Zero Trust Enterprise = network infrastructure + operational policies as product of ZTA plan.
  • PERIMETER vs ZERO TRUST: Perimeter: Static perimeter defined around boundary | Trust Model: users authorized by identity/role/clearance | Persistent Access: decisions stay as long as role unchanged. Zero Trust: Dynamic perimeter defined by transaction attributes | Transactional Model: authorization by attributes for each transaction | Temporal Access: decisions only for duration, then re-evaluated.
  • 7 NIST ZT TENETS: (1) All data sources and computing services = resources (incl personally owned devices), (2) All communication secured regardless of network location (protect confidentiality/integrity, provide source auth), (3) Access to individual resources granted per-session (least privilege), (4) Access determined by dynamic policy (client identity, app/service, requesting asset, behavioral/environmental attributes), (5) Enterprise monitors/measures integrity and security posture of ALL assets (no asset inherently trusted, evaluate posture per request, continuous monitoring, patch as needed), (6) All auth/authz dynamic and strictly enforced (constant cycle: obtain access, scan, assess threats, adapt, re-evaluate — ICAM + MFA), (7) Collect as much info as possible about asset state, infrastructure, communications to improve posture.
  • ZT VIEW OF NETWORK: Entire enterprise private network NOT considered implicit trust zone. Authenticate all connections, encrypt all traffic. Devices may not be enterprise-owned/configurable. No resource inherently trusted. Not all resources on enterprise infrastructure. Remote subjects can't trust local network. Consistent security policy across enterprise/non-enterprise.
  • LOGICAL COMPONENTS (NIST): Policy Engine (PE) = makes and logs decisions (approved/denied). Policy Administrator (PA) = generates session-specific auth tokens/credentials. Policy Enforcement Point (PEP) = enables, monitors, terminates connections. Beyond PEP = trust zone hosting resource. Control Plane = PE + PA (policy decisions). Data Plane = subject --> PEP --> resource (actual data traffic). Logical components don't necessarily need to be unique systems.
  • ZT DATA/POLICY SOURCES: CDM (Continuous Diagnostics & Mitigation), Industry compliance system, Threat intelligence feeds, Network/system activity logs, Data access policies, Enterprise PKI, ID management system, SIEM.
  • ZT NETWORK COMPONENTS (Microsoft/Soseman): Identity provider (track users), Device directory (list of devices + type/integrity info), Policy evaluation service (user/device conform to policy?), Access proxy (grant/deny based on signals), Anomaly detection + ML. Conditional access controls = "if-this-then-that" automated approach. Controls: allow/deny, require MFA, force password reset, control session access (read not download), block legacy auth.
  • DEVICE HEALTH CONDITIONS: Machine risk level (malware, Pass-the-Hash). System integrity/posture (hardware-rooted boot-time + runtime checks). Integrity checks: drivers, kernel, firmware, peripheral firmware, antimalware driver code. Verify boot state. Compliance policy checks (OS security settings).
  • IDENTITY CONDITIONS: User risk level. Sign-in from: known botnet IP? Anonymous IP? Unauthorized browser (Tor)? Unfamiliar location? Impossible travel? Suspicious sign-in (failed attempts across accounts, attacker IP patterns)? Leaked credentials (dark web)?
  • IMPLICIT TRUST ZONE: Area beyond PEP where all entities trusted to at least level of last PDP/PEP gateway. ZT principle: move PDP/PEPs CLOSER to the resource. The idea: explicitly auth/authz ALL subjects, assets, workflows.
  • THREE NIST ZTA DEPLOYMENT MODELS: (1) Device Agent/Gateway Model — agent on device communicates with gateway protecting resource. (2) Enclave Gateway Model — gateway protects resource enclave (group of resources). (3) Resource Portal Model — gateway portal = single entry point to data resources. All maintain Control Plane (PE+PA) separate from Data Plane.
  • ZTN vs SDP: ZTN: Core = "never trust, always verify" (continuous auth). Architecture = philosophy using auth/authz/micro-seg/monitoring. Auth = continuous per-request based on identity/device/context. Visibility = deep insight into traffic/behavior. Deploy = flexible, coexists with existing infra. SDP: Core = dynamically create secure isolated connections, hide resources. Architecture = defined framework with controllers/gateways. Auth = strong crypto ensures only verified connect. Visibility = tracks access, resources hidden from public internet. Deploy = requires SDP controllers/gateways, often for remote/cloud.
  • EO 14028 + OMB M-22-09: Executive Order 14028: comprehensive cybersecurity initiatives for US govt. 7 provisions: (1) ZTA, (2) Improved cybersecurity standards, (3) Incident response/remediation, (4) Software supply chain security, (5) Cybersecurity Review Board, (6) Information sharing, (7) Federal contracting requirements. OMB M-22-09 (Jan 26, 2022): requires agencies meet specific cybersecurity standards by end of FY2024. Strategic goals align with CISA 5 pillars: Identity (phishing-resistant MFA), Devices (complete inventory), Networks (encrypt all DNS/HTTP), Applications (internet-connected, empirical testing), Data (thorough categorization).
  • CISA ZT MATURITY MODEL v2.0 (Apr 2023): 5 pillars + 3 cross-cutting capabilities (Visibility/Analytics, Automation/Orchestration, Governance). Four maturity levels: Traditional --> Initial --> Advanced --> Optimal. Each pillar has specific capabilities at each level. One of many roadmaps for ZT transition.
  • ZT BENEFITS: Allow conditional access while restricting high-value resources to managed devices. Prevent lateral movement with stolen credentials. Enable productivity (work anywhere). Identity = control plane. "If-this-then-that" automation. Can enable new business outcomes.

  • ZT ACRONYMS: ZT = Zero Trust. ZTA = Zero Trust Architecture. ZTN = Zero Trust Network. SDP = Software Defined Perimeter. PE = Policy Engine. PA = Policy Administrator. KEY FORMULAS & NUMERICAL FACTS
  • RSA: n=pxq, phi(n)=(p-1)(q-1), exd congruent to 1 mod phi(n), Encrypt: c=m^e mod n, Decrypt: m=c^d mod n. Public=(n,e), Private=(n,d).
  • DH: Shared secret = g^(ab) mod p. Alice sends g^a mod p, Bob sends g^b mod p. Both compute g^(ab) mod p. Based on discrete log problem.
  • KEY SPACE: n-bit key = 2^n possibilities. DES: 2^56 = 7.2x10^16. AES-128: 2^128 = 3.4x10^38. AES-256: 2^256 = 1.16x10^77.
  • SYMMETRIC KEY PAIRS: N users need N(N-1)/2 keys. 10 users = 45 keys. 100 = 4,950. 1000 = 499,500. Doesn't scale --> motivated public key crypto.
  • ZKP CHEATING PROB: After n rounds = 1/2^n. 10 rounds = 1/1024. 20 rounds = 1/1,048,576. 30 rounds = ~1 in a billion.
  • KEY EQUIVALENCE: AES-128 approx RSA-3072 approx ECC-256. AES-256 approx RSA-15360 approx ECC-512. Source: NIST SP 800-57.
  • SECURITY BOUND: Prob of breaking <= t/2^200 where t = computing cycles available to adversary.
  • AES ROUNDS: 128-bit key = 10 rounds. 192-bit = 12 rounds. 256-bit = 14 rounds. Each round: SubBytes --> ShiftRows --> MixColumns --> AddRoundKey.
  • PINOCCHIO: 288-byte proofs. Verification 5-7 orders of magnitude faster. Worker effort reduced 19-60x.
  • SNARK PROOFS: ~100s bytes, ~10ms verify. STARK PROOFS: ~100s KB, 50-100ms verify. STARKs ~10x faster prover.
  • GROVER'S IMPACT: Halves key length. AES-128-->64-bit (broken). AES-192-->96-bit (weak). AES-256-->128-bit (secure). Need AES-256 for post-quantum.
  • ZT MARKET: $52 billion projected by 2026. Anderson: >90% security failures = config errors. 1/3 PGP users sent secrets unencrypted. Ronin: $620M stolen.
EXCEL FORMULAS — BUILD FROM BLANK SHEET
  • CORE EXCEL FUNCTIONS: =MOD(a,n) — modular arithmetic (remainder). =POWER(base,exp) — exponentiation. =GCD(a,b) — greatest common divisor. =CODE("A") — ASCII value (A=65). =CHAR(65) — ASCII to letter. =LEN(text) — string length. =MID(text,start,len) — extract substring.
  • RSA SETUP (start with blank sheet): A1: "p" B1: enter prime (e.g., 61) | A2: "q" B2: enter prime (e.g., 53) | A3: "n=pxq" B3: =B1*B2 | A4: "phi(n)" B4: =(B1-1)*(B2-1) | A5: "e" B5: enter value coprime to phi (e.g., 17) | A6: "GCD check" B6: =GCD(B5,B4) must=1 | A7: "d" B7: find d where dxe mod phi(n)=1 (try values or use extended Euclidean) | A8: "verify d" B8: =MOD(B7*B5,B4) must=1
  • RSA ENCRYPT: Message in C1. Ciphertext: =MOD(POWER(C1,B5),B3) — c = m^e mod n. RSA DECRYPT: =MOD(POWER(ciphertext,B7),B3) — m = c^d mod n. NOTE: Excel POWER overflows for large numbers. For exam-size problems (small primes), it works fine.
  • DIGITAL SIGNATURE: Sign: =MOD(POWER(message,B7),B3) (use private key d). Verify: =MOD(POWER(signature,B5),B3) (use public key e). Result should = original message.
  • DIFFIE-HELLMAN SETUP: A1: "p" B1: prime (23) | A2: "g" B2: generator (5) | A3: "a (Alice secret)" B3: enter (6) | A4: "b (Bob secret)" B4: enter (15) | A5: "A=g^a mod p" B5: =MOD(POWER(B2,B3),B1) | A6: "B=g^b mod p" B6: =MOD(POWER(B2,B4),B1) | A7: "Alice shared secret" B7: =MOD(POWER(B6,B3),B1) | A8: "Bob shared secret" B8: =MOD(POWER(B5,B4),B1) | A9: "Match?" B9: =B7=B8 must=TRUE
  • CAESAR CIPHER: Plaintext letter in A1. Key (shift) in B1. Encrypt: =CHAR(MOD(CODE(UPPER(A1))-65+B1,26)+65). Decrypt: =CHAR(MOD(CODE(UPPER(A1))-65-B1+26,26)+65). For full word: use MID to extract each letter, apply formula, CONCATENATE results.
  • VIGENÈRE: Plaintext letter in A1, keyword letter in B1. Encrypt: =CHAR(MOD(CODE(UPPER(A1))+CODE(UPPER(B1))-130,26)+65). Key letter cycles: use =MID(keyword,MOD(column-1,LEN(keyword))+1,1) to get the right key letter for each position.
  • KEY SPACE: =POWER(2,n) where n=key bits. DES: =POWER(2,56)=7.2x10^16. AES-128: =POWER(2,128)=3.4x10^38. Symmetric keys for N users: =N*(N-1)/2. 100 users = 4,950 keys.
  • ZKP CHEATING PROB: =1/POWER(2,n) where n=rounds. 10 rounds: =1/POWER(2,10)=0.00098. 20 rounds: ~1 in a million. 30 rounds: ~1 in a billion.
  • HASH OUTPUT SIZE: MD5=128 bits=16 bytes. SHA-1=160=20 bytes. SHA-256=256=32 bytes. SHA-512=512=64 bytes. Bits to bytes: =bits/8.
  • GROVER'S IMPACT: Post-quantum effective key length: =keybits/2. AES-128-->64 (broken). AES-256-->128 (safe). PBKDF2 iterations: enter count. bcrypt: =POWER(2,cost) where cost=12 --> 4096 rounds.
  • MODULAR INVERSE (brute force for small numbers): To find d where dxe congruent to 1 mod phi: In column A put 1,2,3... In column B: =MOD(A1*e,phi). Scan column B for value=1. That row's A value = d. Works for exam-sized numbers.
  • PRIME CHECK (simple): =AND(MOD(n,2)<>0,MOD(n,3)<>0,MOD(n,5)<>0,MOD(n,7)<>0) works for primes <121. For larger: all primes >3 are form 6k+/-1, check =OR(MOD(n-1,6)=0,MOD(n+1,6)=0).
  • XOR IN EXCEL: No native XOR for numbers. Use =IF(A1=B1,0,1) for single bits. For bytes: convert to binary with =DEC2BIN(), XOR each bit, convert back with =BIN2DEC(). OTP/stream cipher: XOR plaintext with key byte-by-byte.
ASSIGNED READINGS & KEY PAPERS SUMMARY
  • Diffie & Hellman "New Directions" (1976): Introduced public key crypto concept. Proposed key exchange without pre-shared secret. Discrete log as one-way function. Revolutionized cryptography — enabled secure communication without trusted courier. Did NOT solve authentication (MITM still possible).
  • RSA Paper (Rivest, Shamir, Adleman 1977): First practical public key encryption system. Based on factoring difficulty. Provides both encryption AND digital signatures. Trap-door one-way function. n=pq where p,q are large primes. Security scales with key size but so does computation cost.
  • Shannon "Communication Theory of Secrecy Systems" (1949): Founded information-theoretic security. Defined perfect secrecy: P(M|C)=P(M). Proved OTP = only perfectly secure cipher. Introduced confusion + diffusion as cipher design principles. 5 criteria for good ciphers still valid today.
  • Whitten & Tygar "Why Johnny Can't Encrypt" (1999): PGP 5.0 usability study. Users confused signing with encryption. Quill pen icon miscommunicated private key usage. 1/3 sent secrets in the clear. Conclusion: security UI must be designed for non-experts or it fails in practice.
  • Anderson "Why Cryptosystems Fail" (1993): Banking system failures study. >90% failures = implementation/config, NOT broken math. "Phantom withdrawals" — banks blamed customers. Crypto community lacks learning mechanism (unlike aviation). Solution: publish failures like NTSB reports.
  • "The U in Crypto" (2021): Mobile crypto wallet usability. Double-spends from poor Send button feedback. Uninformed users gave 1-star reviews for things dev couldn't control. Barn Door Property: once secret exposed, can't undo. Blockchain irreversibility amplifies every UX mistake permanently.
  • Thompson "Reflections on Trusting Trust" (1984): Turing Award lecture. Demonstrated self-replicating compiler Trojan. Even clean source code compiled by compromised compiler produces backdoored binary. Backdoor persists across compilations. You can NEVER fully trust code you didn't write. Moral: trust is foundation of computing security.
  • Quisquater "Ali Baba Cave" (1990): Intuitive ZKP explanation. Peggy proves she knows cave secret without revealing it. Victor calls exit path, repeated trials make cheating probability negligible (1/2^n). Made ZKP accessible to non-mathematicians.
  • Goldwasser, Micali, Rackoff (1985): Formalized ZKP with three properties: completeness, soundness, zero-knowledge. Defined interactive proof systems. Knowledge complexity = information leaked. Foundation of all modern ZKP systems.
  • NIST SP 800-207 (2020): Defines ZTA. 7 tenets of zero trust. PE/PA/PEP logical components. Three deployment models (agent/gateway, enclave, resource portal). Control plane vs data plane separation. Implicit trust zone concept. Used as specification by federal agencies per EO 14028.
  • ZK-STARKs Medium Posts (Parts 1-3): Scalable Transparent ARgument of Knowledge. No trusted setup (public randomness). Quantum resistant (hash-based, not ECC). Polylogarithmic communication complexity. ~10x faster prover than SNARKs. Starkware commercializing. "Verifiable trust" concept.
  • IEEE Top 10 Secure Design Flaws: (1) Never assume trust, (2) Use crypto correctly, (3) Authorize after authenticate, (4) Separate data/control, (5) Validate all data, (6) Strong auth, (7) Compartmentalize, (8) Least privilege, (9) Don't DIY security, (10) Make security usable.
  • OWASP Crypto Failures: #2 on Top 10. Three failure categories: loss of confidentiality, non-repudiation failure, failed integrity. NOT access control (separate category). Common mistakes: weak algos, hardcoded keys, no key rotation, improper padding.
  • Buchanan Textbook Chapters: Ch1 p.3-20,33-48: Fundamentals, sym/asym intro. Ch2 p.49-85: Ciphers, sub/trans, block cipher modes, DES/AES. Ch3 p.87-97,117-120,133-135: Hashing. Ch4 p.143-155: Asymmetric. Ch5 p.167-177: Key exchange. Ch6 p.183-212: Zero Trust. Ch8 p.251-254: Usability. Ch11 p.337-367: ZKP.

WHAT PROVIDES WHAT? (EXAM TRAPS)
  • HMAC: Integrity YES | Authentication YES | Confidentiality NO | Non-repudiation NO (both parties share key).
  • DIGITAL SIGNATURES: Integrity YES | Authentication YES | Non-repudiation YES | Confidentiality NO.
  • ENCRYPTION (symmetric): Confidentiality YES | Integrity NO | Authentication NO. Add HMAC or GCM mode for integrity.
  • HASHING: Integrity YES | Confidentiality NO | Authentication NO (no key). One-way & irreversible.
  • OTP: Perfect secrecy YES | Practical NO. Key must be: truly random, >= message length, used ONCE, kept secret.
  • OWASP CRYPTO FAILURE CATEGORIES: (1) Loss of confidentiality, (2) Non-repudiation failure, (3) Failed integrity. Access control = SEPARATE category (NOT crypto failure).
  • FEISTEL (DES): Split block in half, same structure enc/dec. SPN (AES): Full block sub+perm, different ops for enc vs dec.
  • CONFUSION (Shannon): Complex key<-->ciphertext relationship (S-boxes). DIFFUSION: Each plaintext bit affects many ciphertext bits (ShiftRows/MixColumns).
  • SYMMETRIC: Same key, fast (100-1000x), bulk data, N users = N(N-1)/2 keys. ASYMMETRIC: Pub/priv pair, slow, solves key distribution, N users = 2N keys.
  • SNARKs: Trusted setup, ECC-based, ~100s bytes, ~10ms verify, quantum VULNERABLE. STARKs: No trusted setup, hash-based, ~100s KB, 50-100ms, quantum RESISTANT.
  • PERIMETER MODEL: Static boundary, role-based trust, persistent access. ZERO TRUST: Dynamic per-transaction, attribute-based, temporal access, re-evaluated.
  • ZTN vs SDP: ZTN = philosophy (continuous auth, micro-seg). SDP = framework (controllers/gateways, hides resources from public internet).
