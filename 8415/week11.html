🔒 1. TLS/SSL Protocol (Buchanan Ch 7)
KEY IDEA: TLS (Transport Layer Security) is the most widely deployed cryptographic protocol, securing web traffic, email, VPN, and more. It evolved from SSL (Secure Sockets Layer).

TLS Handshake Process

Client Hello --> Server Hello + Certificate --> Key Exchange --> Session Keys Established --> Encrypted Communication

Handshake Steps (TLS 1.2)

  • Client Hello: Supported cipher suites, random nonce, TLS version
  • Server Hello: Chosen cipher suite, server's random nonce, server certificate (X.509)
  • Certificate Verification: Client verifies server cert against trusted CAs
  • Key Exchange: Pre-master secret encrypted with server's public key (RSA) or via Diffie-Hellman
  • Session Keys: Both sides derive symmetric session keys from pre-master secret + nonces
  • Finished: Both sides confirm with MAC of entire handshake transcript

TLS 1.3 Improvements

Major changes in TLS 1.3 (RFC 8446):
  • Reduced handshake: 1-RTT (one round trip) instead of 2-RTT. Supports 0-RTT for resumed sessions
  • Removed weak ciphers: No more RC4, 3DES, SHA-1, static RSA, DH key exchange
  • Mandatory PFS: Perfect Forward Secrecy required -- only ephemeral Diffie-Hellman (DHE or ECDHE)
  • Simplified cipher suites: Only 5 cipher suites remain (all AEAD: AES-GCM, ChaCha20-Poly1305)
  • Encrypted handshake: Server certificate is now encrypted (hidden from passive observers)
Cipher Suite Negotiation: A cipher suite specifies four algorithms -- key exchange (e.g., ECDHE), authentication (e.g., RSA), bulk encryption (e.g., AES-256-GCM), and MAC (e.g., SHA-384). In TLS 1.3, the key exchange and authentication are separated from the cipher suite string.
0-RTT Warning: TLS 1.3's 0-RTT mode is vulnerable to replay attacks. An attacker can capture and resend the early data. Only use for idempotent requests (e.g., GET, not POST with financial transactions).
🖥 2. SSH -- Secure Shell
SSH (Secure Shell): Protocol for secure remote access, replacing insecure Telnet and rsh. Provides encrypted terminal sessions, file transfer (SCP/SFTP), and port forwarding.

SSH Authentication Methods

Method How It Works Security Level
Password User sends password over encrypted channel Basic -- vulnerable to brute force
Public Key Client proves possession of private key matching authorized public key on server Strong -- recommended default
Certificate-based SSH CA signs user/host keys, server trusts the CA Enterprise -- scalable trust

Port Forwarding (SSH Tunneling)

Three Types of SSH Port Forwarding

  • Local forwarding (-L): Forward a local port to a remote destination through the SSH server. Use case: access a database behind a firewall
  • Remote forwarding (-R): Forward a port on the SSH server to a local destination. Use case: expose a local dev server to the internet
  • Dynamic forwarding (-D): Creates a SOCKS proxy. Use case: route all browser traffic through the SSH tunnel
SSH Host Key Verification: On first connection, SSH presents the server's host key fingerprint. Users must verify it ("Trust on First Use" / TOFU model). If the key changes later, SSH warns about a potential man-in-the-middle attack.
🛡 3. IPsec -- Internet Protocol Security
KEY IDEA: IPsec operates at the network layer (Layer 3), providing security for ALL traffic between two endpoints -- unlike TLS which protects individual application connections.

Transport Mode vs Tunnel Mode

Feature Transport Mode Tunnel Mode
What's protected Only the payload (data) Entire original IP packet
IP header Original IP header preserved New IP header added; original encrypted
Use case Host-to-host communication Gateway-to-gateway (site-to-site VPN)
Overhead Lower (no extra header) Higher (extra IP header)

AH vs ESP

Protocol AH (Authentication Header) ESP (Encapsulating Security Payload)
Confidentiality No encryption Yes -- encrypts payload
Integrity Yes -- covers IP header + payload Yes -- covers payload only (not outer IP header)
Authentication Yes Yes
NAT compatible No (AH covers IP header, NAT changes it) Yes (with NAT-T encapsulation)
IKE (Internet Key Exchange): Two-phase protocol for establishing IPsec Security Associations (SAs).
  • Phase 1: Authenticate peers, establish a secure channel (IKE SA). Uses Diffie-Hellman for key exchange
  • Phase 2: Negotiate IPsec SAs (which algorithms, keys, and policies to use for actual data protection)
Remember This
AH = Authentication only (no encryption). ESP = Encryption + Authentication. ESP is used far more in practice because AH breaks with NAT.
🏢 4. PKI in Practice -- Certificates, CAs, and Trust
PKI (Public Key Infrastructure): The framework of policies, procedures, hardware, software, and people needed to create, manage, distribute, use, store, and revoke digital certificates.

X.509 Certificate Format

Key Fields in an X.509 Certificate

  • Version: Currently v3
  • Serial Number: Unique identifier from the CA
  • Signature Algorithm: Algorithm used by CA to sign the cert (e.g., SHA-256 with RSA)
  • Issuer: Distinguished Name of the CA that issued it
  • Validity Period: Not Before / Not After dates
  • Subject: Distinguished Name of the entity (e.g., CN=www.example.com)
  • Subject Public Key: The entity's public key and algorithm
  • Extensions: Key Usage, Subject Alternative Names, Basic Constraints, etc.
  • CA's Digital Signature: Binds all fields together

Certificate Chain of Trust

Root CA (self-signed, offline) | v Intermediate CA (signed by Root) | v End-Entity Certificate (signed by Intermediate) | v Your browser trusts Root --> trusts Intermediate --> trusts End-Entity

Certificate Revocation

Method CRL (Certificate Revocation List) OCSP (Online Certificate Status Protocol)
How it works CA publishes a list of revoked serial numbers, downloaded periodically Client queries a responder in real-time for a specific certificate's status
Freshness Can be stale (published on schedule) Real-time (current status)
Bandwidth Large download (entire list) Small query/response per cert
Privacy No privacy issue (download full list) OCSP responder sees which sites you visit (mitigated by OCSP stapling)

Hierarchical Trust (PKI) vs Web of Trust (PGP)

Feature PKI (Hierarchical) PGP (Web of Trust)
Trust anchor Root Certificate Authorities Individual users who vouch for each other
Structure Top-down hierarchy Peer-to-peer, decentralized
Scalability Scales well for organizations Difficult to scale beyond small communities
Single point of failure Compromised CA breaks all certs it issued No single point of failure
CA Compromise is Catastrophic: If a root CA private key is compromised, every certificate in the chain is untrustworthy. Real-world example: DigiNotar (2011) -- CA was compromised, fraudulent Google certificates issued, entire CA was shut down.
📧 5. Email Encryption -- S/MIME and PGP
Feature S/MIME PGP / GPG
Trust model Hierarchical PKI (CAs issue certs) Web of Trust (users sign each other's keys)
Key distribution X.509 certificates from CAs Public key servers, direct exchange
Encryption Hybrid: RSA/ECDH for key exchange + AES for message Hybrid: RSA/ECDH for key exchange + AES for message
Built into Outlook, Apple Mail, enterprise clients Thunderbird (via Enigmail), command-line tools
Best for Enterprise/corporate environments Individual privacy, journalism, activism
Both S/MIME and PGP use hybrid encryption: The message body is encrypted with a symmetric key (fast), and that symmetric key is encrypted with the recipient's public key (so only they can decrypt). This combines the speed of symmetric crypto with the key distribution advantage of asymmetric crypto.
Efail Vulnerability (2018): Researchers showed that HTML rendering in email clients could be exploited to exfiltrate plaintext from S/MIME and PGP encrypted emails. This was an implementation bug in email clients, not a flaw in the cryptographic algorithms.
✏️ 6. Digital Signature Algorithm (DSA) (Buchanan Ch 8)
KEY IDEA: DSA is the NIST standard (FIPS 186) for digital signatures. Unlike RSA signatures, DSA can ONLY sign -- it cannot encrypt. It is based on the difficulty of computing discrete logarithms.

DSA Key Generation

Parameters and Keys

  • p: Large prime (1024-3072 bits)
  • q: Prime factor of (p-1), typically 160-256 bits
  • alpha (g): Generator of order q in Z*_p, computed as g = h^((p-1)/q) mod p
  • Private key d: Random integer, 0 < d < q
  • Public key beta: beta = alpha^d mod p

DSA Signing Process

To sign message m:

  • Choose random ephemeral key k, where 0 < k < q
  • Compute r = (alpha^k mod p) mod q
  • Compute s = k^(-1) * (H(m) + d*r) mod q, where H(m) is SHA hash of message
  • Signature is the pair (r, s)

DSA Verification Process

To verify signature (r, s) on message m:

  • Compute w = s^(-1) mod q
  • Compute u1 = H(m) * w mod q
  • Compute u2 = r * w mod q
  • Compute v = (alpha^u1 * beta^u2 mod p) mod q
  • Signature is valid if v = r
CRITICAL -- NEVER REUSE THE EPHEMERAL KEY k: If the same k is used to sign two different messages, an attacker can recover the private key d. This is exactly what happened to Sony's PS3 ECDSA implementation in 2010 -- they used a fixed k value, and hackers extracted the private signing key.
Remember This
DSA ephemeral key reuse = private key compromise. Sony PS3 hack (2010) is the classic example.
📈 7. ECDSA -- Elliptic Curve Digital Signature Algorithm
ECDSA: The elliptic curve version of DSA. Same logic but operates on points of an elliptic curve instead of modular arithmetic in Z*_p. Provides equivalent security with much shorter keys.
Security Level (bits) DSA Key Size ECDSA Key Size RSA Key Size
80 1024 160 1024
112 2048 224 2048
128 3072 256 3072
256 15360 512 15360
Where ECDSA is Used:
  • Bitcoin / Ethereum: Transaction signing uses secp256k1 curve
  • TLS 1.3: Server authentication and key exchange
  • Code signing: macOS, iOS app signatures
  • SSH: Ed25519 keys (related EdDSA, not exactly ECDSA but same family)
Same ephemeral key warning applies: The PS3 hack exploited ECDSA specifically. The ephemeral key k must be truly random and NEVER reused. Modern implementations use RFC 6979 (deterministic k from message + private key) to eliminate this risk.
🔑 8. Key Management Challenges
KEY IDEA: The cryptographic algorithms are the easy part. Key management -- generating, distributing, storing, rotating, revoking, and recovering keys -- is where most real-world systems fail.

Key Lifecycle

Generation --> Distribution --> Storage --> Use --> Rotation --> Revocation --> Destruction
Challenge Description Solution
Key Distribution How to get keys to the right parties securely Diffie-Hellman, PKI, key wrapping, out-of-band exchange
Key Storage Protecting keys at rest from theft or compromise HSMs (Hardware Security Modules), TPMs, key vaults
Key Rotation Regularly replacing keys to limit exposure from compromise Automated rotation policies, versioned keys
Key Escrow Storing keys with a trusted third party for recovery Split-key escrow, M-of-N schemes (Shamir's Secret Sharing)
Key Recovery Retrieving keys when the primary holder is unavailable Recovery agents, secure backup procedures
Key Escrow Controversy: The 1990s "Clipper Chip" debate -- US government wanted key escrow for all encryption (government holds a copy of every key). Privacy advocates and industry resisted. Key escrow creates a high-value target and introduces trust issues.
💥 9. Common Deployment Failures
KEY IDEA: Ross Anderson's "Why Cryptosystems Fail" (1993) -- most cryptographic failures are NOT due to broken algorithms. They are due to implementation bugs, poor key management, and operational mistakes.

Categories of Failure

Category Examples
Implementation bugs Heartbleed (OpenSSL buffer over-read), goto fail (Apple TLS), padding oracle attacks
Protocol design flaws POODLE (SSLv3 padding), BEAST (CBC mode in TLS 1.0), CRIME (compression side-channel)
Key management failures Hardcoded keys, keys in source code, weak random number generators
Operational mistakes Expired certificates, misconfigured servers, using deprecated algorithms
Usability failures Users bypassing crypto because it is too hard, ignoring certificate warnings

Side-Channel Attacks

Attacks that exploit physical characteristics, not mathematical weaknesses

  • Timing attacks: Measure how long operations take. Different inputs cause different execution times, leaking information about the key
  • Power analysis: Monitor power consumption during cryptographic operations. Simple Power Analysis (SPA) and Differential Power Analysis (DPA) can extract keys from smart cards and embedded devices
  • Electromagnetic emissions: Capture EM radiation from processors during crypto operations (TEMPEST)
  • Cache attacks: Exploit shared CPU caches (Flush+Reload, Prime+Probe) to determine which memory lines a crypto operation accessed
Constant-time programming: Cryptographic code must execute in the same amount of time regardless of input to prevent timing attacks. This means no early exits, no data-dependent branches, no variable-time memory access.
👥 10. Usability -- "Why Johnny Can't Encrypt"
KEY IDEA: Whitten & Tygar's "Why Johnny Can't Encrypt" (1999) -- even motivated users failed to use PGP correctly. If crypto is not usable, people will bypass it entirely, making the system LESS secure.

Key Findings from "Why Johnny Can't Encrypt"

  • Users confused their public key with their private key
  • Users accidentally sent unencrypted messages thinking they were encrypted
  • Key management concepts (keyring, trust, revocation) were incomprehensible to non-experts
  • Users could not distinguish between signing and encrypting
  • The mental model of public-key cryptography did not match users' expectations
Modern Usability Improvements:
  • Signal Protocol: End-to-end encryption with no key management for the user
  • Let's Encrypt: Free, automated TLS certificates -- removed cost and complexity barriers
  • HTTPS Everywhere: Browser defaults to encrypted connections
  • iMessage / WhatsApp: Encryption transparent to the user
Remember This
Security at the expense of usability comes at the expense of security. -- AviD's Rule of Usability

1 What is the most significant improvement in TLS 1.3 compared to TLS 1.2?

Support for longer encryption keys
Addition of certificate pinning
Mandatory Perfect Forward Secrecy and reduced handshake to 1-RTT
Support for HTTP/2 multiplexing
TLS 1.3 mandates Perfect Forward Secrecy (only ephemeral DH/ECDH allowed), reduces the handshake from 2-RTT to 1-RTT, removes weak cipher suites (RC4, 3DES, SHA-1, static RSA), and encrypts the server certificate during handshake.

2 In IPsec, what is the key difference between Transport Mode and Tunnel Mode?

Transport Mode encrypts the entire packet; Tunnel Mode only encrypts the payload
Transport Mode protects only the payload with the original IP header intact; Tunnel Mode encapsulates the entire original packet with a new IP header
Transport Mode is for wireless; Tunnel Mode is for wired networks
Transport Mode uses AH; Tunnel Mode uses ESP exclusively
Transport Mode protects the payload while keeping the original IP header visible -- used for host-to-host. Tunnel Mode encapsulates the entire original IP packet inside a new one -- used for site-to-site VPN through gateways.

3 Why is AH (Authentication Header) rarely used in modern IPsec deployments?

AH provides no integrity checking
AH is computationally too expensive
AH only works in Tunnel Mode
AH is incompatible with NAT because it authenticates the IP header, which NAT modifies
AH authenticates the entire packet including the IP header. Since NAT changes the IP header (modifying source/destination addresses and ports), AH authentication fails after NAT translation. ESP does not cover the outer IP header, making it NAT-compatible with NAT-T.

4 What catastrophic event demonstrated the risk of CA compromise in PKI?

DigiNotar (2011) -- CA compromised, fraudulent Google certificates issued, entire CA shut down
Heartbleed (2014) -- OpenSSL vulnerability exposed private keys
POODLE (2014) -- SSLv3 padding oracle attack
SHA-1 collision (2017) -- SHAttered attack by Google
DigiNotar, a Dutch CA, was compromised in 2011. Attackers issued fraudulent certificates for Google and other domains, enabling man-in-the-middle attacks against Iranian users. The CA was completely distrusted by all browsers and shut down.

5 In DSA, what happens if the ephemeral key k is reused for two different signatures?

The signatures become identical
The hash function is compromised
An attacker can recover the private key d from the two signatures
The verification process fails for both signatures
If the same k is used for two messages m1 and m2, the r values are identical. An attacker can solve the two signature equations simultaneously to extract k, then trivially compute the private key d. The Sony PS3 hack (2010) exploited exactly this flaw in ECDSA.

6 What advantage does ECDSA have over standard DSA?

ECDSA can encrypt and sign, while DSA can only sign
ECDSA provides equivalent security with much shorter key sizes (e.g., 256-bit ECC vs 3072-bit DSA for 128-bit security)
ECDSA does not require an ephemeral key
ECDSA is immune to quantum computing attacks
ECDSA operates on elliptic curves, providing the same security level with much shorter keys. A 256-bit ECDSA key provides the same security as a 3072-bit DSA key. This means faster operations, smaller signatures, and less bandwidth. Both DSA and ECDSA are vulnerable to quantum attacks.

7 What is the difference between CRL and OCSP for certificate revocation?

CRL is real-time; OCSP is periodic
CRL checks individual certificates; OCSP downloads full lists
CRL is used by PGP; OCSP is used by PKI
CRL is a periodically published list of all revoked certificates; OCSP provides real-time status checks for individual certificates
CRL (Certificate Revocation List) is a complete list of revoked certificates published by the CA on a schedule -- it can be stale and is a large download. OCSP (Online Certificate Status Protocol) queries a responder in real-time for a single certificate's status -- more current but raises privacy concerns (mitigated by OCSP stapling).

8 According to Ross Anderson's "Why Cryptosystems Fail," what is the most common cause of cryptographic system failures?

Implementation bugs and operational failures, not broken algorithms
Weak encryption algorithms being used
Insufficient key lengths
Quantum computing advances
Anderson demonstrated that the vast majority of cryptographic failures come from implementation mistakes (like Heartbleed, goto fail), poor key management (hardcoded keys), and operational errors (expired certs, misconfigurations) -- not from mathematically broken algorithms.

9 What is a timing side-channel attack?

An attack that exploits the time between key rotations
An attack that measures power consumption during encryption
An attack that measures how long cryptographic operations take to infer secret information like keys
An attack that exploits expired certificates
Timing attacks measure execution time differences in cryptographic operations. If code takes different amounts of time depending on the key value (e.g., early exit on comparison failure), attackers can deduce the key bit by bit. Countermeasure: constant-time programming.

10 What was the key finding of Whitten & Tygar's "Why Johnny Can't Encrypt" study?

PGP's encryption algorithm was fundamentally flawed
Even motivated users could not use PGP correctly -- confusing public/private keys, sending unencrypted messages by mistake
Users preferred symmetric encryption over asymmetric
Email encryption was unnecessary for most users
Whitten & Tygar found that PGP's user interface was so confusing that users mixed up public and private keys, accidentally sent unencrypted messages thinking they were encrypted, and could not manage key trust. The lesson: if crypto is not usable, people bypass it, making the system less secure overall.
