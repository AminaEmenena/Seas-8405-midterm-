🔒 1. Real World Systems -- Why We Need Crypto
KEY IDEA: Data faces real risks on untrusted networks -- packet sniffing, data tampering, and spoofed gateways. Cryptographic systems solve these problems through secure tunneling, encrypted channels, and shared encryption keys.

Network Threats

Data at Risk

  • Packet sniffing: Attackers capture data traversing the network
  • Data tampering: Packets modified in transit without detection
  • Spoofed gateways: Fake network devices impersonate legitimate ones

Security Requirements

Requirement Solution
Privacy Encryption -- prevent eavesdropping
Authentication Verify devices are who they claim to be
Integrity Ensure data has not been modified in transit

Five Security Services

The five fundamental security services provided by cryptographic systems:
  1. Authentication -- verify the identity of communicating parties
  2. Key Agreement/Exchange -- establish shared secrets securely
  3. Confidentiality -- keep data private through encryption
  4. Integrity -- detect any modification to data
  5. Nonrepudiation -- prevent denial of having sent a message
Solution approach: Secure tunneling (VPNs), encrypted channels, and shared encryption keys address these threats. Different protocols (PGP, SSL/TLS, IPsec) implement these services in different ways.
Remember This
Five security services: Authentication, Key Agreement, Confidentiality, Integrity, Nonrepudiation. Different protocols provide different subsets.
📧 2. Secure Email -- S/MIME and Crypto Basics
KEY IDEA: Email crypto is unique -- the sender unilaterally chooses crypto parameters (no negotiation like SSL/IPsec). Messages go to a mail server, not directly to the recipient. The receiver takes it or leaves it.

S/MIME in Outlook

S/MIME Requirements

  • Requires an X.509 digital certificate from a Certificate Authority (CA)
  • Enables both encryption and digital signing of emails
  • Older S/MIME used 512-bit keys -- consider PGP for stronger keys
  • Modern secure email uses AES and RSA

Generic Secure Email Process

Sending a Secure Email (Alice to Bob)
Alice's Side (Sending): 1. Generate a random SESSION KEY 2. Encrypt the message with session key (symmetric) 3. Encrypt session key with BOB'S PUBLIC KEY (asymmetric) 4. Sign the message with ALICE'S PRIVATE KEY 5. Send everything to Bob Bob's Side (Receiving): 1. Decrypt session key with BOB'S PRIVATE KEY 2. Decrypt message with session key 3. Verify signature with ALICE'S PUBLIC KEY 4. Check if certificate has been revoked
Signed Digest: The signed digest ensures two things:
  • Integrity: Message cannot be altered without detection
  • Authentication/Nonrepudiation: Alice cannot deny signing the message
User must explicitly invoke crypto services -- it is NOT automatic. Encryption does no good unless you turn it on!

Confidentiality vs Authentication

Users must know the difference: Encrypted email should also be signed. Encryption alone does NOT imply integrity -- someone could tamper with the encrypted data. Always sign AND encrypt.
🔐 3. PGP -- Pretty Good Privacy
KEY IDEA: PGP uses asymmetric crypto for authentication and symmetric crypto for confidentiality. Key insight: PGP combines fast symmetric encryption with secure asymmetric key exchange.

PGP Encryption Pipeline

PGP Email Encryption Steps
Plaintext Message | v 1. Hash with MD5 --> message digest | v 2. Sign digest with sender's RSA PRIVATE key --> digital signature | v 3. Append signature to message, then ZIP compress | v 4. Encrypt compressed data with IDEA session key (symmetric) | v 5. Encrypt IDEA session key with recipient's RSA PUBLIC key | v 6. Send: encrypted session key + encrypted message

Why This Pipeline?

  • MD5 hash: Creates a fixed-size digest of the message for signing
  • RSA private key signing: Provides authentication (proves sender identity) and nonrepudiation
  • ZIP compression: Reduces message size BEFORE encryption (encrypted data cannot be compressed)
  • IDEA session key: Fast symmetric encryption for the bulk message data
  • RSA public key: Encrypts only the small session key -- avoids slow RSA on large data
Remember This
PGP pipeline: Hash (MD5) -> Sign (RSA private) -> ZIP -> Encrypt (IDEA session key) -> Encrypt session key (RSA public). Compress BEFORE encryption!
🔄 4. Sign-then-Encrypt vs Encrypt-then-Sign
KEY IDEA: The order of signing and encrypting matters greatly for security properties and performance. PGP/SSL and IPsec use different approaches for good reasons.
Property Sign-then-Encrypt (PGP/SSL) Encrypt-then-Sign (IPsec)
Signature covers Plaintext Ciphertext
Privacy of signatories Encryption hides who signed the message Signature is visible (signer identity exposed)
Authentication speed Must decrypt BEFORE authenticating -- cannot quickly discard forged packets Verify signatures BEFORE decrypting -- efficient for automated verification
Weakness Receiver must decrypt before verifying -- resource cost on forged packets BlackHat can send forged packets (signature on ciphertext is visible)
Best for Human-to-human communication (email) Machine-to-machine, high-throughput traffic (VPN)
Deterring email viruses: Accept only signed emails -- verified signatures before viruses can take control. This is a practical security measure enabled by secure email.
Remember This
PGP/SSL = sign then encrypt (hides signer, must decrypt to verify). IPsec = encrypt then sign (verify before decrypting, efficient for automation).
🔒 5. SSL & TLS -- Securing the Web
KEY IDEA: SSL/TLS provides authentication, confidentiality, and message integrity for web traffic. SSL/TLS does NOT provide nonrepudiation -- this is a key difference from PGP.

History and Evolution

Timeline

  • 1994: Netscape creates SSL v2
  • 1994: Microsoft creates PCT as a competitor
  • 1995: SSL v3 released
  • 1996: IETF TLS Working Group formed
  • 1999: TLS 1.0 released
  • 2015: SSL officially deprecated
  • Today: TLS 1.3 is the current standard (RFC 8446)
Fun fact: Microsoft implemented TLS before Netscape. Today's "SSL certificates" actually use TLS. SSL is deprecated.

TLS Version Comparison

Version Status Key Issues
SSL 2.0/3.0 Deprecated Serious vulnerabilities (POODLE, etc.)
TLS 1.0 Outdated BEAST attack vulnerability
TLS 1.1 Obsolete Improved but still deprecated
TLS 1.2 Strong but complex AES-CBC padding oracle attacks possible
TLS 1.3 Current standard Rebuilt from scratch -- streamlined, faster, more secure

What TLS Does

  • TLS is the "S in HTTPS"
  • Application agnostic -- works with any application protocol
  • Workhorse of internet security -- also used in machine-to-machine IoT
  • Goals: confidential, authenticated, unmodified data. Prevent MITM via certificates
  • Efficient, interoperable, extensible, versatile
Notable TLS vulnerabilities: Heartbleed, BEAST, CRIME, POODLE all targeted TLS implementations. These are implementation bugs, not flaws in the protocol math itself.

SSL v2 Export-Grade Ciphers

Export-grade ciphersuites used 40-bit session keys -- deliberately weak due to US export regulations. This made "secure" connections trivially breakable by anyone with moderate computing power. A cautionary tale about governments weakening crypto.
🛡 6. TLS Protocol Suite -- Handshake & Record
KEY IDEA: TLS has two main protocols: the Record protocol (how to transmit data) and the Handshake protocol (key agreement). The handshake is often confused as "the" TLS protocol, but it is only one part.

TLS Placement in the Network Stack

SSL/TLS sits between the application and transport layers:
  • HTTP port 80 becomes HTTPS port 443
  • SMTP port 25 becomes SMTPS port 465

TLS Handshake Process

SSL/TLS Handshake
Client Server | | |-- Client Hello (list cipher suites) ---------> | | | |<- Server Hello (certificate, select suite) --- | | | |-- Client Key Exchange -----------------------> | | (pre-master secret encrypted with | | server's public key) | | | | Both derive 6 shared secret keys | | (3 each direction) | | | |<========= Encrypted Communication ==========> |

The 6 Secret Keys

SSL/TLS derives 6 separate secret keys (3 per direction):
  • Encryption key -- for bulk data encryption (e.g., DES, AES)
  • HMAC key -- for message authentication and integrity
  • IV (Initialization Vector) -- think of it as cipher initialization random plaintext

Each direction (client-to-server and server-to-client) gets its own set of 3 keys = 6 total.

SSL/TLS Session Flow

Hello + Negotiate --> Exchange Certificates --> Key Agreement --> Authentication --> Confidentiality & Integrity

Sending a Confidential Message (Alice to Bob)

Alice Sends:

  1. Compress the message
  2. Hash with HMAC key (message authentication)
  3. Encrypt with DES key (confidentiality)

Bob Receives:

  1. Decrypt with DES key
  2. Authenticate (verify HMAC)
  3. Decompress

Cipher Suite Example

A cipher suite specifies four components:
  • RSA -- for key exchange
  • DES -- for bulk encryption
  • SHA-1 -- for message digest
  • PKZip -- for compression
Remember This
6 secret keys: 3 per direction (encryption key + HMAC key + IV). Cipher suite = key exchange + encryption + digest + compression.
🏢 7. Digital Certificates & Trust
Digital certificates establish trust: Alice sends her digital certificate to Bob. Bob verifies it using the trusted root CA's public key. This establishes a chain of trust.

Certificate Verification Flow

Alice Bob Root CA | | | |-- Digital Certificate ----> | | | |-- Verify with ------> | | | CA's public key | | |<-- Trust confirmed -- | | | | |<===== Secure Channel =====> | |

Key Points

  • SSL allows client to authenticate server (Bob authenticates Alice's server)
  • Certificate exchange establishes the trust chain
  • Always check if the certificate has been revoked
  • S/MIME requires X.509 digital certificate from a CA
Certificate revocation: A valid-looking certificate may have been compromised. Always verify revocation status before trusting a certificate.

Encrypt-then-sign provides nonrepudiation but sign-then-encrypt does not
There is no practical difference -- they provide identical security properties
Sign-then-encrypt (PGP/SSL) means the signature is over plaintext and encryption hides the signatories, but the receiver must decrypt before authenticating -- you cannot quickly discard forged packets. Encrypt-then-sign (IPsec) lets you verify signatures before decrypting, which is efficient for automated, high-throughput verification.

SSL/TLS derives 6 separate secret keys: 3 for each direction of communication. Each direction gets an encryption key (for bulk data encryption), an HMAC key (for message authentication), and an IV (initialization vector -- think of it as cipher initialization random plaintext).

6 What are the four components of an SSL/TLS cipher suite?

AES, SHA-256, ECDHE, and HMAC
Key exchange algorithm (e.g., RSA), encryption algorithm (e.g., DES), digest algorithm (e.g., SHA-1), and compression algorithm (e.g., PKZip)
Public key, private key, session key, and initialization vector
Certificate Authority, server certificate, client certificate, and root certificate
A cipher suite specifies four components: the key exchange algorithm (e.g., RSA), the bulk encryption algorithm (e.g., DES), the message digest algorithm (e.g., SHA-1), and the compression algorithm (e.g., PKZip). During the handshake, the client lists supported suites and the server selects one.

7 In the SSL/TLS message flow, what is the difference between the HMAC key and the encryption key?

They are the same key used for different purposes
The HMAC key is used during the handshake, the encryption key is used afterward
The HMAC key provides message authentication and integrity verification, while the encryption key provides confidentiality by encrypting the data
The encryption key is longer than the HMAC key
In SSL/TLS, the HMAC key is used to hash the message for authentication and integrity verification (ensuring data has not been tampered with). The encryption key (e.g., DES key) is used to encrypt the data for confidentiality. Alice compresses, hashes with HMAC key, then encrypts with the encryption key. Bob reverses: decrypt, verify HMAC, decompress.
