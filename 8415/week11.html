🔒 1. TLS/SSL Protocol (Buchanan Ch 7)
KEY IDEA: TLS (Transport Layer Security) is the most widely deployed cryptographic protocol, securing web traffic, email, VPN, and more. It evolved from SSL (Secure Sockets Layer).

TLS Handshake Process

Client Hello --> Server Hello + Certificate --> Key Exchange --> Session Keys Established --> Encrypted Communication

Handshake Steps (TLS 1.2)

  • Client Hello: Supported cipher suites, random nonce, TLS version
  • Server Hello: Chosen cipher suite, server's random nonce, server certificate (X.509)
  • Certificate Verification: Client verifies server cert against trusted CAs
  • Key Exchange: Pre-master secret encrypted with server's public key (RSA) or via Diffie-Hellman
  • Session Keys: Both sides derive symmetric session keys from pre-master secret + nonces
  • Finished: Both sides confirm with MAC of entire handshake transcript

TLS 1.3 Improvements

Major changes in TLS 1.3 (RFC 8446):
  • Reduced handshake: 1-RTT (one round trip) instead of 2-RTT. Supports 0-RTT for resumed sessions
  • Removed weak ciphers: No more RC4, 3DES, SHA-1, static RSA, DH key exchange
  • Mandatory PFS: Perfect Forward Secrecy required -- only ephemeral Diffie-Hellman (DHE or ECDHE)
  • Simplified cipher suites: Only 5 cipher suites remain (all AEAD: AES-GCM, ChaCha20-Poly1305)
  • Encrypted handshake: Server certificate is now encrypted (hidden from passive observers)
Cipher Suite Negotiation: A cipher suite specifies four algorithms -- key exchange (e.g., ECDHE), authentication (e.g., RSA), bulk encryption (e.g., AES-256-GCM), and MAC (e.g., SHA-384). In TLS 1.3, the key exchange and authentication are separated from the cipher suite string.
0-RTT Warning: TLS 1.3's 0-RTT mode is vulnerable to replay attacks. An attacker can capture and resend the early data. Only use for idempotent requests (e.g., GET, not POST with financial transactions).
🖥 2. SSH -- Secure Shell
SSH (Secure Shell): Protocol for secure remote access, replacing insecure Telnet and rsh. Provides encrypted terminal sessions, file transfer (SCP/SFTP), and port forwarding.

SSH Authentication Methods

Method How It Works Security Level
Password User sends password over encrypted channel Basic -- vulnerable to brute force
Public Key Client proves possession of private key matching authorized public key on server Strong -- recommended default
Certificate-based SSH CA signs user/host keys, server trusts the CA Enterprise -- scalable trust

Port Forwarding (SSH Tunneling)

Three Types of SSH Port Forwarding

  • Local forwarding (-L): Forward a local port to a remote destination through the SSH server. Use case: access a database behind a firewall
  • Remote forwarding (-R): Forward a port on the SSH server to a local destination. Use case: expose a local dev server to the internet
  • Dynamic forwarding (-D): Creates a SOCKS proxy. Use case: route all browser traffic through the SSH tunnel
SSH Host Key Verification: On first connection, SSH presents the server's host key fingerprint. Users must verify it ("Trust on First Use" / TOFU model). If the key changes later, SSH warns about a potential man-in-the-middle attack.
🛡 3. IPsec -- Internet Protocol Security
KEY IDEA: IPsec operates at the network layer (Layer 3), providing security for ALL traffic between two endpoints -- unlike TLS which protects individual application connections.

Transport Mode vs Tunnel Mode

Feature Transport Mode Tunnel Mode
What's protected Only the payload (data) Entire original IP packet
IP header Original IP header preserved New IP header added; original encrypted
Use case Host-to-host communication Gateway-to-gateway (site-to-site VPN)
Overhead Lower (no extra header) Higher (extra IP header)

AH vs ESP

Protocol AH (Authentication Header) ESP (Encapsulating Security Payload)
Confidentiality No encryption Yes -- encrypts payload
Integrity Yes -- covers IP header + payload Yes -- covers payload only (not outer IP header)
Authentication Yes Yes
NAT compatible No (AH covers IP header, NAT changes it) Yes (with NAT-T encapsulation)
IKE (Internet Key Exchange): Two-phase protocol for establishing IPsec Security Associations (SAs).
  • Phase 1: Authenticate peers, establish a secure channel (IKE SA). Uses Diffie-Hellman for key exchange
  • Phase 2: Negotiate IPsec SAs (which algorithms, keys, and policies to use for actual data protection)
Remember This
AH = Authentication only (no encryption). ESP = Encryption + Authentication. ESP is used far more in practice because AH breaks with NAT.
🏢 4. Digital Certificates & PKI (Buchanan Ch 7)
PKI (Public Key Infrastructure): The framework of policies, procedures, hardware, software, and people needed to create, manage, distribute, use, store, and revoke digital certificates.

X.509 Certificates and Standards

Key Standards (from Buchanan)

  • X.509: Standard format for digital certificates. Contains subject, issuer, public key, validity, extensions, and CA signature
  • IKE (Internet Key Exchange): Protocol for establishing shared keys in IPsec
  • PKCS#7: Cryptographic Message Syntax -- format for signed and encrypted data
  • PKCS#10: Certificate Signing Request (CSR) format -- what you send to a CA to get a certificate

Certificate Types

Certificate Type Purpose
Server Authentication Proves identity of a server (e.g., HTTPS websites)
Client Authentication Proves identity of a client connecting to a server
Code Signing Verifies software publisher identity and code integrity
Email (S/MIME) Enables encrypted and signed email
Timestamping Proves data existed at a specific time

Key/Certificate Management Lifecycle (Buchanan)

Three Phases

  • Initialization: Key generation, certificate creation, distribution to parties, secure backup of keys
  • Issued (Active): Certificate retrieval (from directory/repository), validation (check chain and revocation status), recovery (if key lost), update (before expiry)
  • Cancellation: Expiration (natural end of validity period), revocation (premature invalidation due to compromise), archiving (store for historical verification)

Certificate Revocation (Buchanan)

Two Revocation States:
  • Revoked: Permanently invalidated -- cannot be reinstated
  • Hold: Temporarily suspended -- can be reinstated if the issue is resolved
Method CRL OCSP
How it works CA publishes a list of revoked serial numbers, downloaded periodically Client queries a responder in real-time for a specific certificate's status
Freshness Can be stale (published on schedule) Real-time (current status)
Problems (Buchanan) Lack of checking by clients, revoking errors, DoS attacks on CA distribution point Privacy concern (responder sees which sites you visit). Mitigated by OCSP stapling
CRL Problems (from textbook): Many clients simply don't check CRLs. CAs can make errors when revoking. CRL distribution points are targets for DoS attacks. OCSP is lighter-weight but not universally deployed.
📧 5. PGP Email Encryption (Buchanan Ch 7)
KEY IDEA: PGP uses a hybrid approach combining hashing, digital signatures, compression, symmetric encryption, and public-key encryption in a specific pipeline.

PGP Encryption Pipeline (Figure 6.26)

PGP Email Encryption Steps
Plaintext Message | v 1. Hash with MD5 --> message digest | v 2. Sign digest with sender's RSA PRIVATE key --> digital signature | v 3. Append signature to message, then ZIP compress | v 4. Encrypt compressed data with IDEA session key (symmetric) | v 5. Encrypt IDEA session key with recipient's RSA PUBLIC key | v 6. Send: encrypted session key + encrypted message

Why This Pipeline?

  • MD5 hash: Creates a fixed-size digest of the message for signing
  • RSA private key signing: Provides authentication (proves sender identity) and integrity (message not tampered)
  • ZIP compression: Reduces message size BEFORE encryption (encrypted data cannot be compressed)
  • IDEA session key: Fast symmetric encryption for the bulk message data
  • RSA public key: Encrypts only the small session key -- avoids slow RSA on large data
Hybrid Approach: PGP combines the speed of symmetric encryption (IDEA for bulk data) with the key distribution advantage of asymmetric encryption (RSA for the session key). The recipient decrypts the session key with their private key, then uses it to decrypt the message.
🔑 6. Kerberos Authentication (Buchanan Ch 7)
DEFINITION: Kerberos is a ticket-based authentication protocol that allows users to prove their identity without sending passwords over the network. Used extensively in Active Directory environments.

Key Components

Component Role
Identity Provider (IP) / Authentication Server (AS) Verifies user identity and issues initial ticket (Ticket Granting Ticket / TGT)
Ticket Granting Server (TGS) Issues service tickets based on valid TGT. User presents TGT to get access to specific services
Relying Party (RP) / Service The service the user wants to access. Verifies the service ticket

Kerberos Flow

User AS (Auth Server) TGS Service | | | | |-- Credentials --------> | | | |<-- TGT (encrypted) ---- | | | | | | | |-- TGT + Service Req ------------------> | | |<-- Service Ticket (encrypted) --------- | | | | | | |-- Service Ticket ----------------------------------------> | |<-- Access Granted ---------------------------------------- |
Key Advantage: Passwords are NEVER sent over the network after initial authentication. All subsequent authentication uses encrypted tickets. Tickets have limited lifetime, reducing exposure from compromise.
Remember This
Kerberos = ticket-based auth. AS issues TGT, TGS issues service tickets. No passwords on the wire after login.
💥 7. Cryptographic Attack Types (Buchanan Ch 8)
KEY IDEA: Buchanan Ch 8 covers "Crypto Cracking" -- the various ways cryptographic systems can be attacked. Understanding attacks is essential for building secure systems.

Attack Categories

Attack Type Description
Known Plaintext Attack Attacker has matching plaintext-ciphertext pairs and uses them to crack other ciphertexts encrypted with the same key
Replay Attack Capture a legitimate encrypted message and resend it later. The receiver processes it as valid even though it is a replay
Man-in-the-Middle (MITM) Intruder positions between two parties, impersonating each to the other. Intercepts and potentially modifies all communications
Active Attack Attacker inserts or modifies messages in transit (not just passive eavesdropping)
Cut and Paste Mix parts of different encrypted messages to create a new valid-looking ciphertext. Exploits block cipher modes without proper authentication
Defense: These attacks are prevented through nonces/timestamps (replay), mutual authentication and certificates (MITM), MACs/AEAD modes (active attack, cut-and-paste).
🔓 8. RSA Cracking Methods (Buchanan Ch 8)
KEY IDEA: While RSA with proper key sizes is computationally secure, there are multiple attack vectors when RSA is improperly implemented or used.

RSA Attack Methods (from textbook)

1. Different e Value Attack

  • Same message M encrypted with two different public exponents e1 and e2 (same N)
  • Attacker gets C1 = M^e1 mod N and C2 = M^e2 mod N
  • Solve for x, y where x*e1 + y*e2 = 1 (Extended Euclidean Algorithm)
  • Compute M = C1^x * C2^y mod N

2. Factoring N

  • If you can factor N into P and Q, RSA is broken
  • Compute PHI = (P-1) * (Q-1)
  • Find d such that (d * e) mod PHI = 1
  • This is why N must be large enough that factoring is computationally infeasible

3. M^e < N (Short Message Attack)

  • If the message M is very short, M^e may be less than N
  • Then C = M^e (no modular reduction happens)
  • Attacker can recover M using simple logarithms: M = 10^(log(C)/e)
  • Defense: Always pad messages (OAEP padding)

4. CRT (Chinese Remainder Theorem) Attack

  • Same message encrypted with same small e (e.g., e=3) but different N values (N1, N2, N3)
  • Attacker collects 3 ciphertexts: C1, C2, C3
  • Use CRT to solve for M^e (single value across all three moduli)
  • Take the e-th root to recover M

5. Chosen Cipher Attack

  • Eve captures C = M^e mod N
  • Eve picks random r, computes C' = C * r^e mod N
  • Eve sends C' to Bob for decryption (tricks Bob into decrypting)
  • Bob returns M' = (M*r) -- the decryption of C'
  • Eve computes M = M'/r -- recovers original message

6. Blinding Attack (Signature Forgery)

  • Goal: Get Bob to sign a message M without him knowing
  • Eve computes M' = r^e * M mod N (a "blinded" version of M)
  • Eve tricks Bob into signing M': S' = (M')^d mod N
  • Eve computes S = S'/r = M^d mod N = valid signature on M
  • Bob never knew he signed M

7. Bleichenbacher's Attack (PKCS#1 v1.5)

  • Exploits PKCS#1 v1.5 padding format: ciphertext starts with 0x00 0x02
  • Attacker sends modified ciphertexts to server
  • Server responds differently: "Bad crypto" (invalid padding) vs. processes normally (valid padding)
  • This difference is an oracle that leaks information
  • Attacker iterates through s values to find valid padding
  • Requires 30,000 to 130,000 attempts to fully recover the plaintext
  • Defense: Use OAEP padding (PKCS#1 v2.0+), not v1.5
Bleichenbacher is a real-world threat: This attack (also called the "million message attack" or ROBOT attack) has been used against real TLS implementations. PKCS#1 v1.5 padding is STILL used in some legacy systems. TLS 1.3 removes RSA key exchange entirely, eliminating this vector.
🔨 9. AES Cracking Methods (Buchanan Ch 8)
KEY IDEA: AES itself has no known practical attacks on the algorithm. But AES implementations and usage patterns create vulnerabilities.

AES Attack Vectors (from textbook)

1. ECB Copy-and-Paste Attack

  • ECB (Electronic Codebook) mode encrypts each block independently
  • Same input block = same output block (deterministic)
  • Attacker can rearrange, duplicate, or swap cipher blocks
  • Example: swap encrypted "amount" blocks between two transactions
  • Defense: Use CBC, CTR, or GCM mode instead of ECB

2. Brute Force with Common Passwords

  • If the AES key is derived from a password (e.g., key = SHA-256(password))
  • Attacker tries common passwords, computes SHA-256 of each, uses as AES key
  • If the password is weak, the AES key is predictable despite being 256 bits
  • Defense: Use proper key derivation (PBKDF2, Argon2) with salt and high iterations

3. Non-Random Number Generator

  • If the PRNG used to generate AES keys is deterministic or poorly seeded
  • An attacker who knows the PRNG state can predict future keys
  • Real-world example: Dual_EC_DRBG (NSA backdoor in NIST-approved PRNG)
  • Defense: Use cryptographically secure random number generators (CSPRNG)
Remember This
ECB mode is the most dangerous AES mode -- same plaintext block = same ciphertext block. Always use CBC, CTR, or GCM. AES is only as strong as its key generation and mode of operation.
👥 10. Key Management and Common Failures
KEY IDEA: The cryptographic algorithms are the easy part. Key management and implementation errors cause more real-world failures than broken algorithms.

Key Lifecycle

Generation --> Distribution --> Storage --> Use --> Rotation --> Revocation --> Destruction

Common Failure Categories

Category Examples
Implementation bugs Heartbleed (OpenSSL buffer over-read), goto fail (Apple TLS), Bleichenbacher padding oracle
Protocol design flaws POODLE (SSLv3), BEAST (CBC in TLS 1.0), ECB mode in AES
Key management failures Hardcoded keys, keys in source code, weak PRNG, password-derived keys without KDF
Operational mistakes Expired certificates, misconfigured servers, using PKCS#1 v1.5 instead of OAEP
Anderson's Principle: "Why Cryptosystems Fail" (1993) -- most cryptographic failures are NOT from broken algorithms but from implementation bugs, poor key management, and operational errors. Security at the expense of usability comes at the expense of security.

Bleichenbacher's attack exploits PKCS#1 v1.5 padding. The server responds "Bad crypto" for invalid padding but processes normally for valid padding (starting with 0x00 0x02). This difference allows the attacker to iteratively narrow down the plaintext, requiring 30,000 to 130,000 attempts.

2 Why is ECB mode dangerous for AES encryption?

ECB uses a weaker key schedule than other modes
Same plaintext block always produces the same ciphertext block, allowing copy-and-paste attacks
ECB does not support 256-bit keys
ECB requires an initialization vector that can be guessed
ECB (Electronic Codebook) encrypts each block independently and deterministically. Same input = same output. An attacker can rearrange, duplicate, or swap cipher blocks (copy-and-paste attack). Use CBC, CTR, or GCM mode instead.

3 In the RSA "short message" attack, what happens when M^e < N?

No modular reduction occurs, so C = M^e and the attacker can recover M using logarithms: M = 10^(log(C)/e)
The ciphertext wraps around and becomes negative
The encryption fails and returns an error
The message is automatically padded to fill N bits
When M^e < N, the modular reduction (mod N) has no effect -- C simply equals M^e. The attacker can recover M by computing the e-th root of C using logarithms. This is why messages must always be padded (e.g., with OAEP) before RSA encryption.

Root CA, Intermediate CA, End-Entity Certificate

Kerberos uses three components: the Authentication Server (AS/Identity Provider) verifies user identity and issues TGTs, the Ticket Granting Server (TGS) issues service tickets, and the Service (Relying Party) verifies service tickets and grants access. Passwords are never sent over the network after initial authentication.

The CRT attack requires the same message encrypted with the same small e value (e.g., e=3) but sent to different recipients with different N values. Collecting e ciphertexts allows the attacker to use CRT to solve for M^e, then take the e-th root to recover M.

Buchanan describes two revocation states: Revoked (permanently invalidated, cannot be reinstated) and Hold (temporarily suspended, can be reinstated if the issue is resolved). This distinction is important for certificate lifecycle management.

7 In the RSA blinding attack, what does Eve accomplish?

Gets Bob to unknowingly sign a message M by having him sign a blinded version M' = r^e * M mod N, then divides by r
Recovers Bob's private key by analyzing multiple signatures
Decrypts Bob's messages by exploiting the padding scheme
Creates a fake certificate signed by Bob's key
In the blinding attack, Eve computes M' = r^e * M mod N (blinded message), tricks Bob into signing it: S' = (M')^d mod N. Then Eve computes S = S'/r = M^d mod N, which is a valid signature on M. Bob never knew he signed M.

8 In PGP email encryption (Buchanan), what is the correct order of operations?

Encrypt with RSA, then hash, then sign, then ZIP
ZIP, encrypt with IDEA, hash with MD5, sign with RSA
Hash with SHA-256, encrypt with AES, sign with ECDSA
Hash with MD5, sign with RSA private key, ZIP compress, encrypt with IDEA session key, encrypt session key with recipient's RSA public key
PGP's pipeline: (1) Hash message with MD5, (2) Sign hash with sender's RSA private key, (3) ZIP compress, (4) Encrypt with IDEA symmetric session key, (5) Encrypt IDEA session key with recipient's RSA public key. Compression happens BEFORE encryption because encrypted data cannot be compressed.

9 What problem does the CRL distribution system have, according to Buchanan?

CRLs are too small to include all revoked certificates
CRLs can only be distributed via email
Clients often don't check CRLs, CAs can make revoking errors, and CRL distribution points are vulnerable to DoS attacks
CRLs reveal which websites users visit
Buchanan identifies three CRL problems: (1) Many clients simply don't check CRLs (lack of checking), (2) CAs can make errors when revoking certificates, and (3) CRL distribution points are targets for Denial of Service attacks. OCSP provides a lighter-weight alternative.

10 Why does deriving AES keys from passwords (key = SHA-256(password)) make AES vulnerable?

SHA-256 output is too short for AES-256
Attackers can brute-force common passwords, compute SHA-256 of each, and try as AES keys -- the key space is effectively the password space, not 2^256
SHA-256 collisions allow multiple passwords to produce the same key
SHA-256 is not a cryptographic hash function
If key = SHA-256(password), the effective key space is the password space (maybe thousands of common passwords), not 2^256. An attacker tries common passwords, hashes each with SHA-256, and uses the result as the AES key. Defense: use a proper KDF like PBKDF2 or Argon2 with salt and high iteration count.
