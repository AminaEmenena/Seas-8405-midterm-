👥 1. Multi-Party Computation (MPC) -- The Problem
DEFINITION: Multi-Party Computation (MPC) allows multiple parties to jointly compute a function over their inputs while keeping each input private. No party reveals their individual data to anyone else.

Two Motivating Problems

1. Billionaire's Problem (Yao 1982): Two billionaires want to know who is richer WITHOUT revealing their actual wealth. Reminiscent of Zero-Knowledge Proofs -- the answer (who is richer) is revealed, but the amounts stay secret.
2. Average Salary Problem: Three friends (Sam, Bob, Cassy) want to compute their average salary without revealing individual salaries. They need a protocol that gives the correct average while keeping each salary private.

MPC Uses in Practice

Real-world MPC applications:
  • Distributed key generation
  • Distributed digital signature creation
  • Distributed key recovery / redistribution
  • Cryptocurrency wallets (threshold signatures)
  • Enterprise-authorized signatures
  • Private Set Intersection (PSI) -- e.g., food delivery companies comparing datasets without revealing them
Remember This
MPC = compute together, reveal nothing individually. Yao 1982 started it all with the Billionaire's Problem.
💰 2. Yao's Millionaire's Protocol -- Worked Example
KEY PROTOCOL: Uses RSA encryption to determine who is wealthier without revealing actual amounts. This is the detailed worked example from the lecture slides.

Setup

Parameters

  • Mark: Public key (79, 3337), Private key 1019. Worth $5B (I = 5)
  • Elon: Worth $6B (J = 6)
  • Wealth values encoded as integers 1-10

Protocol Steps

Step-by-Step

  • Step 1: Elon picks random x = 1234. Computes C = 1234^79 mod 3337 = 901
  • Step 2: Elon sends C - J + 1 = 901 - 6 + 1 = 896 to Mark
  • Step 3: Mark decrypts (C - J + U) for U = 1 to 10 using his private key 1019, getting YU values
  • Step 4: Mark picks random prime p = 107. Computes ZU = YU mod p for each U
  • Step 5: Mark sends p and the first I (=5) numbers unmodified, the rest with +1 added
  • Step 6: Elon computes G = x mod p = 1234 mod 107 = 57. Checks if the J-th number (58) equals G (57). Not equal -- so Elon is wealthier
Protocol Flow
Elon (J=6, x=1234) Mark (I=5, privkey=1019) | | | C = 1234^79 mod 3337 = 901 | | Send C-J+1 = 896 | |---- 896 ------------------------> | | | Decrypt for U=1..10 | | ZU = YU mod 107 | | Send first 5 unchanged, | <--- p=107, Z1..Z10 ------------- | rest +1 | | | G = 1234 mod 107 = 57 | | Check Z[6] = 58 != 57 | | Result: Elon is wealthier |
Key Insight: If Z[J] = G, then Mark is wealthier (or equal). If Z[J] != G, Elon is wealthier. Neither party ever reveals their actual wealth -- only the comparison result is learned.
📈 3. MPC for Average Salary -- Additive Secret Sharing
METHOD: Additive secret sharing allows multiple parties to compute a sum (and therefore an average) without revealing individual values. Each party splits their value into random shares that sum to their actual value.

Worked Example from Lecture

Sam ($40K), Bob ($50K), Cassy ($60K)

  • Sam splits $40K: Three random shares: $44K, -$11K, $7K (sum = $40K)
  • Bob splits $50K: Three random shares that sum to $50K
  • Cassy splits $60K: Three random shares that sum to $60K
  • Each person keeps one of their own shares, distributes the other two
  • Each person sums their received column of shares
  • Everyone announces their column sum
  • Total of all column sums = $150K. Average = $50K
Secret Sharing Matrix
Sam's col Bob's col Cassy's col Sam: $44K -$11K $7K = $40K Bob: (share) (share) (share) = $50K Cassy: (share) (share) (share) = $60K ------ ------ ------ Col Sum: S1 S2 S3 S1 + S2 + S3 = $150K --> Average = $50K Individual salaries NEVER revealed
Why it works: Each person only sees random shares from other parties -- no individual share reveals anything about the original salary. But the math guarantees the column sums add up to the correct total. The randomness of the shares provides perfect privacy.
Remember This
Additive secret sharing: split value into random shares that sum to the value. Distribute shares. Sum columns. Total is correct, individual values stay hidden.
🔒 4. Homomorphic Encryption (HE) -- Overview
KEY IDEA: Homomorphic Encryption (HE) = encryption that allows computation on encrypted data WITHOUT knowing the secret key. Data remains confidential while being processed in untrusted environments like the cloud.

How HE Works

Public-Key Model

  • Encrypt with public key (client-side)
  • Evaluate homomorphically on ciphertext (server-side, no key needed)
  • Decrypt with secret key (client-side)
  • The server never sees the plaintext data or the secret key

The Problem HE Solves

Without HE (legacy approach):
  • Cloud providers require key sharing -- creates privacy concerns
  • Provider with keys has exclusive rights over encrypted material
  • Even without keys, encrypted material is shared with a third party
  • Untrusted servers can keep identifying information after relationship ends
With HE: Third party operates on encrypted data without ever decrypting it. No key sharing needed. Data stays private throughout processing.

Three Types of HE

Type Operations Limit Description
PHE One type (add OR multiply) Unlimited times Partially Homomorphic Encryption. Only addition or only multiplication, but can do it as many times as needed
SWHE Both (add AND multiply) Limited times Somewhat Homomorphic Encryption. Can do both operations but ciphertext grows with each operation -- eventually too noisy to decrypt
FHE Both (add AND multiply) Unlimited times Fully Homomorphic Encryption. The "holy grail" -- any computation, any number of times
Remember This
PHE = one op, unlimited. SWHE = both ops, limited. FHE = both ops, unlimited (holy grail). Each step forward was a major breakthrough.
🔢 5. RSA is Already PHE for Multiplication
KEY INSIGHT: RSA is already partially homomorphic for multiplication! Multiplying two RSA ciphertexts gives the encryption of the product of the plaintexts. But RSA CANNOT do homomorphic addition.

Proof: RSA Multiplicative Homomorphism

Mathematical Proof

  • E(m1) = m1^e mod n
  • E(m2) = m2^e mod n
  • E(m1) * E(m2) = m1^e * m2^e mod n = (m1 * m2)^e mod n = E(m1 * m2)
  • Multiplying ciphertexts = encryption of product of plaintexts

Worked Example (from lecture)

Setup: p=23, q=11, n=253, phi=220, e=39, d=79

  • m1 = 17, m2 = 13, product = 221
  • E(17) = 17^39 mod 253 = 57
  • E(13) = 13^39 mod 253 = 6
  • E(17 * 13) = E(221) = 221^39 mod 253 = 89
  • c1 * c2 = 57 * 6 = 342
  • Decrypt: 342^79 mod 253 = 221. Correct!

Why RSA FAILS for Addition

RSA is NOT homomorphic for addition:
  • E(m1) + E(m2) != E(m1 + m2)
  • Same example: 57 + 6 = 63
  • 63^79 mod 253 = 194
  • But m1 + m2 = 17 + 13 = 30, and E(30) = 30^39 mod 253 != 194
  • FAIL! Adding ciphertexts does NOT give encryption of sum
Remember This
RSA: multiply ciphertexts = encrypt product (WORKS). Add ciphertexts = encrypt sum (FAILS). RSA is PHE for multiplication ONLY.
🔒 6. Paillier Encryption -- PHE for Addition
DEFINITION: Paillier cryptosystem, invented by Pascal Paillier in 1999, is a partially homomorphic encryption scheme that supports addition of ciphertexts AND multiplication of a ciphertext by a plaintext number. It is probabilistic (uses random r).

Key Generation

Paillier Key Gen

  • Pick primes p, q. Compute n = p*q
  • L(x) = (x - 1) / n (a helper function)
  • lambda = lcm(p-1, q-1)
  • Pick random g in Z*_{n^2}
  • mu = (L(g^lambda mod n^2))^{-1} mod n
  • Public key = (n, g). Private key = lambda

Encryption / Decryption

Encryption: c = g^m * r^n mod n^2 (r is random -- makes it probabilistic)
Decryption: m = L(c^lambda mod n^2) * mu mod n

Worked Example (from lecture)

p=13, q=17, n=221, n^2=48841

  • lambda = lcm(12, 16) = 48
  • g = 4886, mu = 159
  • Public key = (221, 4886)
  • Message m = 123, random r = 59
  • c = 4886^123 * 59^221 mod 48841 = 13250
  • Decrypt: L(13250^48 mod 48841) * 159 mod 221 = 123. Correct!

Homomorphic Addition Proof

Why Paillier is homomorphic for addition:
  • E(m1, r1) * E(m2, r2)
  • = (g^m1 * r1^n) * (g^m2 * r2^n) mod n^2
  • = g^(m1 + m2) * (r1 * r2)^n mod n^2
  • = E(m1 + m2, r1*r2)
  • Multiplying Paillier ciphertexts = encryption of sum of plaintexts!
Remember This
Paillier: c = g^m * r^n mod n^2. Probabilistic (random r). Multiply ciphertexts = encrypt SUM. Complement of RSA (which does multiplication).
📚 7. History of Homomorphic Encryption
KEY HISTORY: The idea of computing on encrypted data dates back to 1978 -- the same year as RSA itself. It took 31 years before Craig Gentry solved the problem of Fully Homomorphic Encryption in 2009.

1978: The RAD Paper

"On Data Banks and Privacy Homomorphisms" -- Rivest, Adleman, Dertouzos

  • First use of "homomorphism" in cryptology
  • Motivated by: loan company using a time-sharing service, wants to encrypt all data but still compute on it
  • Discovered RSA "doubling ciphertext doubled the plaintext"
  • Coined "privacy homomorphisms" -- encryption functions that permit meaningful operations on encrypted data
  • Posed the fundamental question that Gentry answered 31 years later
Homomorphism: From Greek -- homos (same) + morphe (shape). A map that preserves algebraic structures. In cryptography: an operation on ciphertexts corresponds to a meaningful operation on plaintexts.

2009: Gentry's Breakthrough

Craig Gentry -- "Fully Homomorphic Encryption Using Ideal Lattices"
  • First-ever FHE scheme (MacArthur Fellow 2014)
  • Key insight: What if the scheme could decrypt itself using an encrypted secret key? This is bootstrapping
  • Conceptually groundbreaking but "practically not a realistic scheme" -- bootstrapping was too computationally costly
  • Started from SWHE (noisy ciphertext) and used bootstrapping to refresh noise, enabling unlimited operations

Four Generations of HE

Generation Era Key Features
1st Gen 2009-2011 Gentry's ideal lattices, van Dijk integers. "Performance truly atrocious"
2nd Gen ~2012 LWE-based schemes. Leveled FHE without bootstrapping (Brakerski, Gentry). SIMD parallelism
3rd Gen ~2013+ HE from LWE, conceptually simpler, asymptotically faster. Lattice-based FHE shown as secure as standard PKE
4th Gen Recent CKKS (approximate arithmetic, ideal for ML/floating point). Improved bootstrapping. Chimera (Ring-LWE)
Performance improvement: Roughly 8x faster every year. Bootstrapping time: 1,800 seconds in 2011 down to 0.5 seconds in 2021.
Remember This
1978 RAD paper posed the question. 2009 Gentry answered it with bootstrapping. 4 generations: ideal lattices -> LWE -> simpler lattice FHE -> CKKS/approximate. Performance: 1800s -> 0.5s.
🌐 8. Applications of Homomorphic Encryption
APPLICATIONS: HE enables secure computation in untrusted environments across many domains -- from cloud computing to genomics to neural networks.

Cloud Computing Model

HE Cloud Application
Client Cloud Server | | | Encrypt data with public key | |---- encrypted data --------------> | | | Evaluate function on | | encrypted data (no key!) | <--- encrypted result ------------ | | | | Decrypt with private key | | Get correct result! | | Server never saw plaintext |

Key Application Areas

From the Lecture

  • Genomics: Secure genome-wide association studies (GWAS) -- analyze genetic data without exposing individual genomes
  • Neural Networks: CryptoNets -- first paper on running neural networks over encrypted data. Train or infer on encrypted inputs
  • Private Information Retrieval (PIR): Query a database without the server knowing what you retrieved
  • Hardware Acceleration: DARPA DPRIVE program -- dedicated hardware for FHE operations
  • Encrypted Word Search: Search over encrypted documents without decrypting them

FHE vs. Encrypted Word Search

Important distinction:
  • Encrypted word search: Leaks some info -- queries are linkable (server can tell if you searched the same thing twice). Requires side-channel/timing attack to fully exploit
  • FHE: Does NOT leak query information. Fully private. But more computationally expensive

Google FHE Transpiler

Google's Contribution: Open-source FHE transpiler that converts high-level code (C++) working on plaintext into code that operates on encrypted data. Uses off-the-shelf FHE libraries. Proof of concept available on GitHub.

Standards and Libraries

Industry Ecosystem

  • Standards: ISO/IEC 18033 (encryption algorithms), HomomorphicEncryption.org standardization efforts
  • Intel HEXL: Hardware acceleration library for HE
  • Microsoft SEAL: Open-source HE library
  • IBM HElib: Open-source HE library
🕷 9. Side-Channel Attacks on HE
HE is not immune to side-channel attacks! Even though data stays encrypted during computation, the implementation itself can leak information through timing, power consumption, or other physical side channels.

RevEAL Paper

Single-Trace Side-Channel Leakage

  • Demonstrated side-channel leakage in Microsoft SEAL library
  • Single-trace attack -- only one execution trace needed
  • Timing attacks and power analysis remain viable even with HE
  • The math is sound, but implementation details can still leak secrets
Key Takeaway: HE protects data mathematically, but the physical implementation must also be secured. Side-channel resistance is an implementation concern, not a cryptographic one. Even the best encryption can be undermined by careless implementation.
📜 10. "On Data Banks and Privacy Homomorphisms" (1978) -- The Paper That Started It All
FOUNDATIONAL PAPER: Rivest, Adleman, and Dertouzos (RAD) published this paper in 1978. It posed the fundamental question: can we encrypt data and still compute on it? This is the paper Gentry finally answered 31 years later.

The Scenario

Motivating Problem

  • A loan company uses a time-sharing computing service
  • Company wants to encrypt ALL its data for confidentiality
  • But still needs the time-sharing service to compute on that data
  • Question: Can we define "privacy transformations" where encrypting data, operating on ciphertext, and decrypting the result gives a meaningful answer?

Key Contributions

What RAD established:
  • First to use the term "homomorphism" in cryptology
  • Defined privacy homomorphisms -- encryption functions that permit operations on encrypted data
  • Noticed RSA had the property: doubling ciphertext doubled plaintext (multiplicative homomorphism)
  • Posed the open problem of finding encryption that supports BOTH addition and multiplication (FHE)
  • The problem remained open for 31 years until Gentry 2009
Remember This
RAD 1978 = Rivest, Adleman, Dertouzos. Coined "privacy homomorphisms." Posed FHE as an open problem. Gentry solved it in 2009. 31-year gap!

7 What did the 1978 RAD paper ("On Data Banks and Privacy Homomorphisms") contribute to cryptography?

8 What is "bootstrapping" in the context of FHE?

Initializing the encryption keys from a random seed
Converting plaintext code to encrypted code using a transpiler
Starting with a simple encryption scheme and gradually adding features
The scheme decrypts itself using an encrypted secret key, refreshing noise to allow unlimited operations
Bootstrapping is Gentry's key insight: in SWHE, each operation adds noise to the ciphertext, eventually making it undecryptable. Bootstrapping lets the scheme homomorphically decrypt the noisy ciphertext using an encrypted version of the secret key, producing a fresh (less noisy) ciphertext. This enables unlimited operations, turning SWHE into FHE.
