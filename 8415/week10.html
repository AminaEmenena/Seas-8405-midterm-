🔒 1. Paillier Cryptosystem (Buchanan Ch 4 p.162)
DEFINITION: The Paillier cryptosystem is an additively homomorphic public-key encryption scheme. Multiplying two ciphertexts produces the encryption of the sum of the plaintexts: E(m1) * E(m2) = E(m1 + m2).

Homomorphic Property

Additive Homomorphism: E(m1) * E(m2) = E(m1 + m2)
This means you can add encrypted values without decrypting them. The multiplication of ciphertexts yields the encryption of the sum of plaintexts.

Secure Voting Application

How Paillier enables secure voting:
  • Each voter encrypts their vote: E(vote1), E(vote2), ...
  • Multiply all encrypted votes: E(vote1) * E(vote2) * ... = E(vote1 + vote2 + ...)
  • Decrypt the product to get the sum of all votes
  • Individual votes are never revealed -- only the total

Python Code Example (from textbook)

Using the phe library

from phe import paillier

# Generate keys
public_key, private_key = paillier.generate_paillier_keypair()

# Encrypt two values
a = 15
b = 25
enc_a = public_key.encrypt(a)
enc_b = public_key.encrypt(b)

# Add encrypted values (multiply ciphertexts)
enc_sum = enc_a + enc_b

# Decrypt to get the sum
result = private_key.decrypt(enc_sum)
print(result)  # Output: 40
Key Insight: The server performing the addition never sees the individual values (15 or 25). It only works with ciphertexts, yet produces a valid encrypted answer that decrypts to the correct sum (40).
🎒 2. Knapsack Encryption -- Merkle-Hellman (Buchanan Ch 4 p.163)
DEFINITION: The Merkle-Hellman knapsack cryptosystem is based on the subset sum problem (NP-hard in general). It was the first public-key encryption scheme proposed after RSA.

How It Works

Key Generation

  • Private key: A superincreasing sequence -- each element is greater than the sum of all preceding elements (e.g., [2, 7, 11, 21, 42, 89]). This makes the knapsack problem EASY to solve
  • Public key: Transform the superincreasing sequence into a hard knapsack using modular multiplication (multiply each element by w mod q). This makes the knapsack problem HARD to solve

Encryption / Decryption

  • Encrypt: Represent message as binary bits. Multiply each bit by corresponding public key element. Sum = ciphertext
  • Decrypt: Use private key to convert back to superincreasing knapsack, then solve easily using greedy algorithm
BROKEN -- Shamir (1984): Adi Shamir broke the Merkle-Hellman knapsack using the LLL lattice reduction algorithm. The transformation from superincreasing to hard knapsack could be reversed, revealing the private key. The scheme is NO LONGER SECURE.
Remember This
Knapsack = historically important (first post-RSA public-key scheme) but BROKEN. Subset sum problem is NP-hard in general, but the specific structure Merkle-Hellman used was exploitable.
Why It Matters: The knapsack scheme demonstrates that basing cryptography on an NP-hard problem is not sufficient -- the specific instance must also be hard. The structure used to create trapdoors can sometimes be exploited.
🕵 3. Zero-Knowledge Proofs (Buchanan Ch 11)
KEY IDEA: A zero-knowledge proof (ZKP) allows a prover to convince a verifier that a statement is true, WITHOUT revealing any information beyond the truth of the statement itself.

Three Properties of ZKP

Property Meaning
Completeness If the statement is true, an honest prover WILL convince an honest verifier
Soundness If the statement is false, a cheating prover CANNOT fool the verifier (except with negligible probability)
Zero-knowledge The verifier learns NOTHING beyond the fact that the statement is true -- no information about the secret is leaked

Interactive ZKP Protocol (from textbook)

Alice proves she knows secret x without revealing it

  • Public parameters: g (generator), p (prime)
  • Alice's secret: x
  • Alice's public value: y = g^x mod p
  • Step 1: Alice picks random v, computes t = g^v mod p, sends t to Bob
  • Step 2: Compute challenge c = hash(g, y, t)
  • Step 3: Alice computes r = v - c*x, sends r to Bob
  • Step 4: Bob verifies: g^r * y^c = t (mod p)
ZKP Verification
Alice (knows x) Bob (verifier) | | | y = g^x (public) | | | | Pick random v | | t = g^v | |---- t --------------------------> | | | | c = hash(g, y, t) | c = hash(g, y, t) | r = v - c*x | |---- r --------------------------> | | | | Verify: g^r * y^c = t? | If yes: Alice knows x | Bob learned NOTHING about x
Key Insight: Bob becomes convinced Alice knows x because only someone who knows x can compute r = v - c*x correctly. But Bob cannot extract x from r (he doesn't know v) and the protocol reveals no information about x beyond the fact that Alice knows it.
🎲 4. Fair Coin Flip (Buchanan Ch 11.7)
PROBLEM: Two parties who don't trust each other need to flip a fair coin remotely. Neither should be able to cheat by choosing the outcome after seeing the other's input.

Protocol Steps

Fair Coin Flip with Salted Hashes

  • Step 1: Both Alice and Bob independently generate random numbers (a and b)
  • Step 2: Both compute salted hashes of their numbers: H(salt || a) and H(salt || b)
  • Step 3: Exchange hashes FIRST (commit phase) -- neither can change their value after seeing the other's hash
  • Step 4: Reveal actual values and salts (reveal phase) -- both can verify the other's hash
  • Step 5: XOR the least significant bits of both values. Result = coin flip outcome
Why Salt Matters: The salt prevents replay attacks and rainbow table lookups. Without salt, an adversary could precompute hashes for many values and find a collision that produces their desired outcome.
Remember This
Fair Coin Flip = commit-then-reveal using hashes. Salt prevents cheating. XOR of LSBs = result.
🗳 5. Paillier Homomorphic Voting (Buchanan Ch 11.8)
KEY APPLICATION: Paillier's additive homomorphism enables secure electronic voting -- tally encrypted votes without ever decrypting individual ballots.

Voting Example (from textbook)

Secure Vote Tallying

  • Vote 1: Alice votes 100 -- encrypt: E(100)
  • Vote 2: Bob votes 200 -- encrypt: E(200)
  • Add encrypted votes: E(100) + E(200) = E(300)
  • Decrypt sum: D(E(300)) = 300
  • Result: Total = 300. Individual votes (100 and 200) are NEVER revealed
Homomorphic Voting Flow
Voter A: vote=100 Voter B: vote=200 | | v v E(100) E(200) | | +------> + <----------+ | E(300) | v Decrypt | Total = 300 (Individual votes never revealed)
Properties:
  • Privacy: individual votes remain encrypted throughout
  • Verifiability: each voter can verify their encrypted vote was included
  • Correctness: the decrypted sum is mathematically guaranteed to equal the sum of individual votes
📦 6. Oblivious Transfer (Buchanan Ch 11.9)
DEFINITION: Oblivious Transfer (OT) is a protocol where Alice has multiple messages and Bob wants to receive exactly ONE of them. Alice does not learn which message Bob chose, and Bob does not learn the other messages.

DH-Based 1-of-2 Oblivious Transfer

Protocol Steps

  • Step 1: Alice generates A = g^a (sends A to Bob)
  • Step 2: Bob wants message c (either 0 or 1):
    • If c=0: B = g^b
    • If c=1: B = A * g^b
    Bob sends B to Alice
  • Step 3: Alice computes two keys:
    • K0 = B^a = g^(ab) (if c=0) or A^a * g^(ab) (if c=1)
    • K1 = (B/A)^a
  • Step 4: Alice encrypts both messages: C0 = Enc(K0, m0), C1 = Enc(K1, m1)
  • Step 5: Bob can only decrypt ONE message -- the one corresponding to his choice c (he can compute g^(ab) = A^b but not the other key)
Two-Way Privacy: Alice never learns which message Bob chose (c=0 or c=1). Bob never learns the message he did NOT choose. This "oblivious" property is fundamental to many cryptographic protocols including garbled circuits.
🔌 7. Scrambled (Garbled) Circuits (Buchanan Ch 11.10)
DEFINITION: Garbled circuits enable secure two-party computation. Two parties can jointly compute a function on their private inputs without revealing those inputs to each other.

How Garbled Circuits Work

Protocol

  • Step 1: Bob (circuit generator) represents the function as a Boolean circuit of AND/OR/XOR gates
  • Step 2: Bob encrypts each gate's truth table with 4 different key combinations (one per input pair)
  • Step 3: Bob sends the garbled circuit to Alice
  • Step 4: Alice receives her input keys via oblivious transfer -- Bob sends keys without learning which input Alice has
  • Step 5: Alice can only decrypt ONE row of each truth table (matching her actual input), producing the output
Key Insight: Alice evaluates the circuit but never learns Bob's inputs (she only sees garbled values). Bob never learns Alice's inputs (oblivious transfer ensures this). Both learn only the final output.
💰 8. Millionaire's Problem (Buchanan Ch 11.11)
PROBLEM: Two millionaires want to know who has more money, but neither wants to reveal their actual amount. This is Yao's Millionaire Problem -- the foundational problem of secure multi-party computation.

RSA-Based Solution (from textbook)

Protocol Overview

  • Uses RSA encryption and modular arithmetic
  • Alice encrypts a value derived from her wealth with Bob's public key
  • Bob computes a series of Z values using his private key and his own wealth
  • Comparison of Z values reveals who is wealthier without revealing amounts
  • Neither party learns the other's actual wealth -- only the comparison result (> or <)
Remember This
Millionaire's Problem = compare private values without revealing them. Foundation of Secure Multi-Party Computation (MPC). Uses RSA for privacy.
📊 9. RAPPOR -- Differential Privacy (Buchanan Ch 11.12)
DEFINITION: RAPPOR (Randomized Aggregatable Privacy-Preserving Ordinal Response) is Google's protocol for collecting user data with differential privacy. Uses Bloom filters combined with randomized response.

Three Stages of RAPPOR

Stage Name Description
1 Signal Creation Hash the user's true value into a Bloom filter B (set specific bits to 1)
2 Permanent Randomized Response (PRR) Create B_fake by randomly flipping bits in B. This is a permanent "fake" version stored for the user. Provides longitudinal privacy
3 Instantaneous Randomized Response (IRR) Add additional noise to B_fake before each report. Different noise each time. Prevents tracking across reports
RAPPOR Pipeline
True Value --> Hash to Bloom Filter (B) | v PRR: Flip bits randomly --> B_fake (permanent) | v IRR: Add more noise --> Reported Value | v Server collects many noisy reports Statistical analysis recovers population trends Individual values remain private
Differential Privacy Guarantee: Even if an adversary has access to all the noisy reports, they cannot determine any individual user's true value with high confidence. The noise is calibrated so that aggregate statistics remain accurate while individual privacy is protected.
Remember This
RAPPOR = Bloom filter + PRR (permanent noise) + IRR (per-report noise). Provides differential privacy for data collection.
👥 10. SFE -- Secure Function Evaluation (Buchanan Ch 11.13)
DEFINITION: Secure Function Evaluation (SFE) allows multiple parties to jointly compute a function on their combined inputs, without any party revealing their individual input to the others.

Voting Example (from textbook)

Secret Sharing Approach

  • Alice = 7, Bob = 2, Carol = 7 (individual secret values)
  • Step 1: Each person splits their value into shares (one per participant)
  • Step 2: Exchange shares -- each person sends one share to each other participant
  • Step 3: Each person computes their partial sum (sum of received shares)
  • Step 4: Everyone announces their partial sum
  • Step 5: Total = sum of all partial sums mod 100 = actual total (16)
SFE with Secret Shares
Alice(7) Bob(2) Carol(7) | | | | Split into shares | | a1,a2,a3 b1,b2,b3 c1,c2,c3 | | | | Exchange shares | | | | | Sum received shares | | P_A P_B P_C | | | | Announce partial sums | | | | Total = P_A + P_B + P_C (mod 100) = 16 No one learns individual values
Key Properties:
  • Privacy: No party learns any other party's individual input
  • Correctness: The computed result is guaranteed to be correct
  • Modularity: Works for any computable function, not just addition

Connection: SRP (Secure Remote Password)

Buchanan Ch 11 also covers SRP

  • Password-based authentication where the server never stores or sees the password
  • Uses a verifier derived from the password instead of storing the password itself
  • Resistant to offline dictionary attacks even if the server's database is compromised
  • Based on Diffie-Hellman key exchange with password-derived parameters
