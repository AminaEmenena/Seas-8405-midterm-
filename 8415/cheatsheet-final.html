W8 - Blockchain & Digital Cash
  • Schneier digital cash: Anonymous, untraceable. 4 protocols building toward double-spend detection: Protocol #1 (basic digital check), #2 (identity verification), #3 (anonymous via blind signatures - bank signs without seeing content), #4 (secret splitting w/ XOR identity reveal on double-spend). Key: bank cannot trace spending, but CAN detect cheating.
  • 6 properties of ideal digital cash (Okamoto & Ohta): Independence (no physical device dependency), Security (cannot be copied/reused), Privacy/Untraceability (bank cannot link withdrawal to spending), Off-line Payment (no need to contact bank during transaction), Transferability (pass to others), Divisibility (make change).
  • DigiCash: David Chaum 1989 - bankruptcy 1998. First practical digital cash attempt. Used blind signatures for anonymity. Failed commercially but proved concept.
  • Blind signatures: Signer signs document without seeing content. Like signing through carbon paper in sealed envelope. Enables anonymous digital cash -- bank signs coin without knowing serial number.
  • Byzantine Generals (Lamport): Consensus w/ malicious nodes. Problem: generals must agree on attack/retreat, but some are traitors. Solvable if >2/3 loyal (oral messages). ANY number of traitors handled with written/signed messages (digital signatures). Lamport: 2013 Turing Award. Also: Time/Clocks/Ordering paper (1978).
  • Paxos: Lamport's consensus protocol for unreliable networks. Less robust than Byzantine fault tolerance but cheaper/more practical. Used in distributed databases.
  • Blockchain: Tamper-evident/tamper-resistant distributed digital ledger (NISTIR 8202). No central authority. DLT: all participants access immutable records. Write-only (append-only). Smart contracts auto-execute rules on-chain. Consensus mechanisms replace trusted third party.
  • Virtues: Verifiable (anyone can audit), Immutable (write-only, cannot alter history), Tamper-resistant (changing one block invalidates chain), Addresses double-spend (consensus prevents spending same coin twice).
  • Node types: Full (stores entire blockchain, validates all transactions), Publishing/Mining (full + creates new blocks, earns rewards), Lightweight/SPV (no full copy, passes transactions to full nodes for validation).
  • Bitcoin vs Schneier: Bitcoin is decentralized (no bank), uses Proof-of-Work consensus. Schneier model uses blind signatures with central bank. Both solve double-spend but through different mechanisms.
  • Consensus mechanisms: PoW (computational puzzle, energy-intensive, Bitcoin), PoS (stake-based, energy-efficient, Ethereum 2.0). Permissioned vs permissionless blockchains.
  • Apps: Cryptocurrency, supply chain tracking, medical records, voting systems, IoT device identity, digital identity, NFTs. Ronin hack (2022): $620M stolen via compromised validator keys.
  • Merkle trees: Binary hash tree. Leaf nodes = transaction hashes. Each parent = hash of children. Root hash in block header. Enables efficient verification of any transaction without downloading entire block. SPV nodes use Merkle proofs: only need log2(n) hashes to verify one transaction in block of n transactions.
  • Schneier's 4 protocols in detail: Protocol #1: basic serial-number check (bank verifies coin not spent). #2: identity embedded in coin (bank can trace). #3: blind signatures (bank signs coin without seeing serial number -- anonymity achieved, but double-spend not caught until deposit). #4: secret splitting with XOR -- identity I split into k random pairs (a_i, a_i XOR I). Bank verifies random half at withdrawal. On double-spend, two different halves revealed -- XOR any matching pair recovers full identity I.
  • Bitcoin vs Schneier model: Schneier requires trusted central bank (issues/verifies coins). Bitcoin eliminates central authority -- uses PoW consensus + distributed ledger. Both solve double-spend: Schneier via identity reveal on deposit, Bitcoin via blockchain confirmations (6 blocks = practically irreversible). Bitcoin is pseudonymous (addresses), not anonymous.
  • Mining process: Miners collect unconfirmed transactions into candidate block. Must find nonce such that SHA-256(block header + nonce) < target difficulty. Average 10 min/block for Bitcoin. Block reward halves every 210,000 blocks (~4 years). Started at 50 BTC, currently 3.125 BTC. Difficulty adjusts every 2,016 blocks.
  • 51% attack: Attacker controlling >50% of network hash power can: (1) double-spend by creating longer chain, (2) prevent transactions from confirming, (3) prevent other miners from finding blocks. CANNOT: steal coins from addresses, change block reward, create coins from nothing. Cost: billions for Bitcoin network.
  • Double-spend problem: Digital data is easily copied -- how to prevent spending same coin twice? Solutions: centralized (bank tracks all coins -- Schneier), decentralized (blockchain consensus confirms transaction ordering -- Bitcoin). Bitcoin's solution: first valid transaction seen by network gets confirmed; second attempt rejected by honest nodes.
  • Smart contract vulnerabilities: Reentrancy (DAO hack -- re-enters withdraw before balance updates). Integer overflow/underflow. Front-running (miners reorder transactions). Oracle manipulation. Immutable code = bugs are permanent.
  • Genesis block: Block 0 -- first block in any blockchain. Bitcoin genesis block mined Jan 3, 2009 by Satoshi. Contains The Times headline: "Chancellor on brink of second bailout for banks." Hardcoded into client software. Cannot be spent (by design).
  • Hard fork vs soft fork: Hard fork: backward-INCOMPATIBLE rule change, ALL nodes must upgrade or split (e.g., Ethereum/Ethereum Classic after DAO hack). Soft fork: backward-compatible, old nodes still accept new blocks (e.g., SegWit). Hard forks can create new cryptocurrency.
  • Blockchain types: Public/permissionless (anyone can join, read, write -- Bitcoin, Ethereum). Private/permissioned (single org controls access -- Hyperledger Fabric). Consortium (group of orgs share control -- R3 Corda for banking). Trade-off: decentralization vs performance vs privacy.
  • Tokenization: Representing real-world assets as blockchain tokens. Fungible (ERC-20: interchangeable). Non-fungible (ERC-721/NFTs: unique). Security tokens (real asset ownership, subject to securities law).
W9 - Elliptic Curve Cryptography
  • ECC: Discovered 1985 independently by Neal Koblitz and Victor Miller. Levchin Prize 2021 awarded to both. Next-generation public-key crypto -- more secure AND more efficient than RSA. Based on algebraic structure of elliptic curves over finite fields.
  • Equation: y^2 = x^3 + ax + b (Weierstrass form). Curve is symmetric about x-axis. Point at Infinity (O) = identity element (like 0 in addition). Curves form an abelian group.
  • Validity: 4a^3 + 27b^2 != 0 (discriminant non-zero -- ensures no singularities/cusps/self-intersections). If discriminant = 0, curve is NOT valid for crypto.
  • Point Addition: Draw line through P and Q, intersects curve at 3rd point R', reflect over x-axis = P+Q. Point Doubling: Draw tangent at P, intersect curve, reflect = 2P. Adding point to itself at infinity: P + O = P. P + (-P) = O (inverse is reflection).
  • Scalar multiplication: Q = kP means adding P to itself k times. This is the trapdoor one-way function: "dotting" k times is easy (O(log k) with double-and-add), but finding k from P and Q is hard.
  • ECDLP: Given generator P and public key Q=kP, find private key k. Computationally hard -- NO sub-exponential algorithm known even after 30+ years of research (unlike integer factoring for RSA which has sub-exponential algorithms like GNFS). This is WHY ECC keys can be shorter.
  • Key size equivalences: 160-bit ECC = 1024-bit RSA. 256-bit ECC = 3072-bit RSA. 384-bit ECC = 7680-bit RSA. 512-bit ECC = 15360-bit RSA. Shorter keys = faster computation + less power + less bandwidth + smaller certificates.
  • ECDH: ECC version of Diffie-Hellman key exchange. Alice picks private a, sends aG. Bob picks private b, sends bG. Shared secret = abG = baG. Used in TLS 1.3.
  • ECDSA: ECC digital signatures. Sign with private key, verify with public key. Used in Bitcoin (secp256k1 curve), Ethereum, TLS 1.3, SSH, code signing.
  • Finite fields/Galois fields: GF(p) for prime p or GF(2^m) for binary. Algebraic hierarchy: Group (one op, closure, assoc, identity, inverse) - Ring (two ops) - Field (two ops, both with inverses except 0). ECC operates over these finite structures.
  • Standard curves: NIST P-256 (secp256r1), P-384, P-521. Bitcoin uses secp256k1. Curve25519 (Daniel Bernstein) -- designed for speed and side-channel resistance.
  • Advantages over RSA: Smaller keys, faster key generation, faster signatures, lower power consumption, less bandwidth. Better for IoT/mobile/embedded/constrained devices. RSA has more mature ecosystem and is simpler to understand.
  • Vulnerabilities: ECC is vulnerable to quantum computers (like RSA) -- Shor's algorithm. More dependent on quality randomness than RSA (bad random k in ECDSA = private key leak, as happened with PS3 hack). Side-channel attacks if implementation leaks timing info.
  • Scalar multiplication detail (double-and-add): To compute kP: write k in binary, scan left-to-right. For each bit: double current result. If bit=1, also add P. Example: 11P -- 11=1011 binary. Start R=P. Bit 0: R=2P. Bit 1: R=4P+P=5P. Bit 1: R=10P+P=11P. Only O(log k) operations instead of O(k). This efficiency is what makes ECC practical.
  • ECDH protocol steps: (1) Agree on curve E and generator point G with large prime order n. (2) Alice picks random a (1 < a < n), computes A=aG, sends A to Bob. (3) Bob picks random b (1 < b < n), computes B=bG, sends B to Alice. (4) Alice computes shared secret S=aB=a(bG)=abG. (5) Bob computes S=bA=b(aG)=baG=abG. Same point. Eavesdropper sees A=aG and B=bG but cannot compute abG (ECDLP).
  • ECDSA signing: Hash h=H(m). Pick random k, R=kG, r=R_x mod n. s=k^(-1)(h+r*d) mod n. Sig=(r,s). Verify: u1=h*s^(-1), u2=r*s^(-1) mod n. R'=u1*G+u2*Q. Valid if R'_x mod n = r.
  • PS3 hack detail: Sony reused same k for every ECDSA signature. Two sigs with same k: s1-s2=k^(-1)(h1-h2) mod n. Solve for k, then d=r^(-1)(k*s-h) mod n. k MUST be unique per signature. Fix: deterministic k (RFC 6979).
  • Why index-calculus fails on EC: Index calculus works for discrete log in Z_p* because elements have useful algebraic structure (smooth factoring). Elliptic curve groups lack this -- no notion of "smooth" points. Best known attack is Pollard's rho: O(sqrt(n)) -- fully exponential. This is why 256-bit ECC matches 3072-bit RSA.
  • Curve25519: Daniel Bernstein. Montgomery curve over GF(2^255-19). Constant-time (side-channel resistant), no NIST influence (post-Snowden trust). Used in Signal, WhatsApp, SSH, WireGuard. Ed25519 = Edwards form for signatures.
  • Key size ratio grows: At 80-bit security ECC is 6.4x smaller than RSA. At 256-bit security ECC is 30x smaller. ECC advantage increases with security level.
  • ECC in practice: TLS 1.3 mandates ECDHE for key exchange. Bitcoin uses secp256k1 for all addresses and transaction signing. Signal Protocol uses Curve25519. Apple iMessage uses NIST P-256. US government Suite B specifies P-256 (SECRET) and P-384 (TOP SECRET).
W10 - Homomorphic Encryption & MPC
  • MPC (Multi-Party Computation): Compute function on joint inputs without revealing individual inputs. Yao's Millionaire's Protocol (1982): who is richer w/o revealing wealth? Uses RSA encryption. Average Salary Problem: use additive secret sharing to compute average without revealing individual salaries.
  • Additive secret sharing: Split salary S into random shares s1+s2+s3=S. Distribute one share to each party. Each party sums their column of shares. Sum of column sums = total of all salaries. No party learns any individual value. Requires honest majority.
  • Yao's protocol detail: Alice picks random x, encrypts x with Bob's public key to get E(x). Sends E(x)-i+1 through E(x)-i+n to Bob. Bob decrypts all with private key, checks modular results against random prime. Determines ordering without revealing amounts.
  • HE types: PHE (Partially HE): one operation unlimited times. SWHE (Somewhat HE): both add+multiply, but limited depth (noise grows). FHE (Fully HE): both operations unlimited times -- the "holy grail." Any computable function can be expressed as addition + multiplication.
  • RSA = PHE for multiplication: E(m1)*E(m2) = (m1^e mod n)*(m2^e mod n) = (m1*m2)^e mod n = E(m1*m2). RSA is NOT additively homomorphic: E(m1)+E(m2) != E(m1+m2). RSA is deterministic (same plaintext = same ciphertext).
  • Paillier = PHE for addition: c = g^m * r^n mod n^2. Multiplying ciphertexts = encryption of sum: E(m1)*E(m2) = E(m1+m2). Probabilistic (random r makes same plaintext encrypt differently each time). Invented 1999. Used for secure voting (sum encrypted votes without decrypting individual ballots).
  • ElGamal = PHE for multiplication: Like RSA, multiplicatively homomorphic. Also probabilistic (unlike RSA).
  • History: RAD 1978 paper (Rivest, Adleman, Dertouzos) coined "privacy homomorphisms" -- posed the open problem. Gentry 2009: first FHE scheme using ideal lattices. Key insight: bootstrapping. MacArthur Fellow 2014. Solved problem open for 31 years.
  • Bootstrapping: Homomorphically evaluate the decryption circuit using an encrypted version of the secret key. Refreshes noisy ciphertext so computation can continue. Both the KEY BREAKTHROUGH and the PERFORMANCE BOTTLENECK of FHE.
  • 4 generations of HE: 1st (Gentry 2009, ideal lattices, atrocious perf), 2nd (BV/BGV, LWE-based, leveled FHE without bootstrapping), 3rd (BFV/TFHE, simpler, faster), 4th (CKKS, approximate arithmetic for ML/floating point). Performance: ~8x improvement/year. Bootstrapping: 1800s (2011) - 0.5s (2021).
  • Schemes: BFV = exact integer arithmetic (counting, database queries). CKKS = approximate arithmetic (ML, floating point, acceptable small error). BGV = exact, good for bit-level operations. TFHE = fast bootstrapping, gate-by-gate evaluation.
  • Noise management: Every HE operation adds noise. Multiplication adds MORE noise than addition. When noise exceeds threshold, decryption fails. Leveled FHE: set max depth in advance, no bootstrapping needed. FHE: bootstrapping resets noise at cost of performance.
  • Apps: Cloud computing on encrypted data, genomics/medical research, CryptoNets (neural networks on encrypted data), PIR (private information retrieval), DARPA DPRIVE (hardware accelerator), Google FHE Transpiler (converts plaintext C++ to encrypted-data code), encrypted word search, secure auctions.
  • Pinocchio: Verifiable computation -- 288-byte proofs, 10ms verification. Client can verify cloud computed correctly without re-doing computation.
  • Side-channel: RevEAL paper showed side-channel attacks on Microsoft SEAL library. Mathematical security != implementation security. Timing attacks can leak information even from "secure" HE.
  • RSA HE worked example: p=23, q=11, n=253, phi=220, e=39, d=79. E(17)=17^39 mod 253=139. E(13)=13^39 mod 253=91. Multiply: 139*91 mod 253=221. E(17*13)=E(221)=221^39 mod 253=221. Match! Addition: E(17)+E(13)=230. E(30)=30^39 mod 253=207. 230!=207. RSA is NOT additively homomorphic.
  • Paillier key gen: Primes p,q. n=pq, lambda=lcm(p-1,q-1), g=n+1, mu=lambda^(-1) mod n. Public=(n,g), Private=(lambda,mu). Enc: c=g^m*r^n mod n^2 (random r). Dec: m=L(c^lambda mod n^2)*mu mod n, L(x)=(x-1)/n.
  • Paillier voting example: 5 voters, yes=1, no=0. Each encrypts vote: E(1), E(0), E(1), E(1), E(0). Multiply all ciphertexts: E(1)*E(0)*E(1)*E(1)*E(0) = E(1+0+1+1+0) = E(3). Decrypt once: result=3. Three yes votes, two no. No individual vote ever decrypted. Authority only learns tally.
  • HE word search vs FHE: Homomorphic word search: server searches encrypted index, returns encrypted results. Leaks: search pattern (same query = same encrypted query), access pattern (which documents match). Linkable queries compromise privacy over time. True FHE search: query encrypted differently each time (probabilistic), server learns nothing about query or results. Much slower but no leakage.
  • Libraries: Microsoft SEAL (BFV, CKKS). IBM HElib (BGV, CKKS). Google FHE Transpiler (C++ to FHE code). Intel HEXL (hardware accel). PALISADE/OpenFHE (multi-scheme, gov use). Lattigo (Go). ISO/IEC 18033 standardizes HE primitives.
  • DARPA DPRIVE: Data Protection in Virtual Environments. Goal: ASIC hardware to make FHE practical (reduce 10,000x overhead to near-realtime). Partners: Intel, Microsoft, Duality Technologies.
  • MPC protocols beyond Yao: GMW (Boolean circuits + oblivious transfer). BGW (information-theoretic, no crypto assumptions, needs honest majority). SPDZ (handles dishonest majority via MACs). Real-world: Boston wage equity study (2017) compared salaries across companies via MPC without revealing individual data.
W11 - Real World Systems (Email, SSL/TLS)
  • 5 security services: Authentication (who are you?), Key Agreement (establish shared secret), Confidentiality (encryption), Integrity (detect tampering), Nonrepudiation (cannot deny action). Not all protocols provide all five.
  • Network threats: Data on untrusted networks faces: sniffing (passive eavesdropping), tampering (active modification), spoofed gateways (MITM), replay attacks. Need crypto at multiple layers.
  • Secure email: Sender UNILATERALLY chooses crypto (no negotiation with recipient -- key difference from TLS). S/MIME needs X.509 certificate from CA. "Encryption does no good unless you turn it on!" Encrypted messages should ALSO be signed -- encryption alone does NOT guarantee integrity.
  • PGP pipeline: hash(MD5) - sign(RSA priv key) - ZIP compress - encrypt message(IDEA session key) - encrypt session key(RSA pub key of recipient). Combines fast symmetric (IDEA for bulk data) + secure asymmetric (RSA for key exchange). Web of Trust model (no CA needed).
  • Sign-then-encrypt (PGP/SSL): Create signature over plaintext, then encrypt everything. Hides signatories (privacy). But: must decrypt before you can authenticate -- cannot verify integrity until decryption. Receiver cannot prove to 3rd party who signed.
  • Encrypt-then-sign (IPsec): Encrypt first, then sign ciphertext. Can verify signature before decrypting -- efficient for automated/gateway processing. But: anyone can strip signature and re-sign (forgery risk). Signature is over ciphertext, not plaintext.
  • SSL/TLS: Provides auth + confidentiality + integrity. Does NOT provide nonrepudiation (shared session keys -- either party could have sent). SSL deprecated 2015 (SSLv3 broken by POODLE). TLS 1.3 = current standard (RFC 8446, 2018). The "S" in HTTPS.
  • TLS architecture: Sits between application layer and transport layer. Two sub-protocols: Record Protocol (HOW to transmit -- fragmentation, compression, MAC, encryption) + Handshake Protocol (key agreement, authentication). HTTP:80 vs HTTPS:443.
  • TLS Handshake: ClientHello (supported cipher suites, random nonce) - ServerHello (selected suite, certificate, random nonce) - Key Exchange (pre-master secret encrypted with server's public key) - Both derive master secret - Both derive 6 session keys.
  • 6 secret keys per session: 3 keys in EACH direction (client-to-server and server-to-client): encryption key, HMAC key, IV. Total = 6 keys. Derived from master secret + client random + server random.
  • Cipher suite format: Key exchange algo (RSA/DHE/ECDHE) + bulk encryption algo (AES-128/AES-256) + hash/MAC algo (SHA-256/SHA-384) + compression. Example: TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256.
  • TLS attacks: Heartbleed (OpenSSL buffer over-read, leaked server memory/private keys), BEAST (CBC predictable IV), CRIME/BREACH (compression side-channel), POODLE (SSLv3 padding oracle). All targeted IMPLEMENTATIONS, not the underlying math.
  • Export-grade ciphers: Deliberately weak 40-bit keys mandated by US export regulations (1990s). FREAK/Logjam attacks exploited servers still supporting export ciphers. Lesson: old weak crypto persists and gets exploited.
  • Digital certificates: X.509 standard. CA trust chain: Root CA (self-signed, pre-installed in browsers) - Intermediate CA - End entity cert. Always check revocation (CRL or OCSP). Certificate pinning: app remembers expected cert to prevent MITM with rogue CA.
  • Forward secrecy: Ephemeral DH (DHE/ECDHE) -- new key pair per session. If long-term private key compromised, past sessions remain secure. TLS 1.3 REQUIRES forward secrecy (no static RSA key exchange).
  • TLS handshake detail: (1) ClientHello: version, suites, client_random, extensions (SNI). (2) ServerHello: chosen suite, server_random. (3) Certificate: X.509 chain. (4) ServerKeyExchange: DH/ECDH params+sig (DHE/ECDHE only). (5) CertificateRequest (optional mutual auth). (6) ServerHelloDone. (7) ClientKeyExchange: pre-master secret. (8) ChangeCipherSpec: switch to encrypted. (9) Finished: hash of all handshake messages.
  • HSTS (HTTP Strict Transport Security): Server sends Strict-Transport-Security header. Browser remembers site requires HTTPS. Prevents SSL stripping attacks (MITM downgrades HTTPS to HTTP). Preload list: browsers ship with hardcoded HSTS domains. max-age directive controls duration.
  • Certificate pinning: App stores expected cert or public key hash. Verifies server cert matches pin on connection. Prevents MITM even with rogue CA cert. Used by mobile apps. Risk: pin rotation requires app update. HPKP deprecated in favor of Certificate Transparency.
  • FREAK attack: Factoring RSA Export Keys. MITM downgrades TLS to export-grade RSA (512-bit). Attacker factors 512-bit key in hours. Affected major sites (NSA.gov, FBI.gov). Root cause: 1990s US export crypto regulations left legacy weak ciphers enabled. Logjam: Similar but targets DHE. Downgrades to 512-bit DH. Pre-compute discrete log for common 512-bit primes. Fix: disable export ciphers, use 2048+ bit DH.
  • TLS 1.3 major changes: (1) 0-RTT resumption (send data with first message -- risk of replay). (2) Removed RSA key exchange (forward secrecy mandatory). (3) Only AEAD ciphers (AES-GCM, ChaCha20-Poly1305). (4) Removed compression (prevents CRIME). (5) Removed renegotiation. (6) Simplified handshake: 1-RTT (was 2-RTT). (7) Encrypted handshake messages (ServerHello encrypted). (8) Removed static DH, RC4, DES, 3DES, MD5, SHA-1.
  • PGP web of trust vs PKI: Web of trust: decentralized, users sign each other's keys, trust is transitive (if I trust Alice and Alice signed Bob's key, I can trust Bob). No central authority. PKI: hierarchical, Root CA at top, intermediate CAs, end-entity certs. Centralized trust anchors pre-installed in browsers/OS. PKI scales better but single point of failure (CA compromise).
  • Email virus deterrence: Signed-only policy: reject unsigned email (viruses lack private key). Encrypted-only: viruses cannot encrypt to correct recipient. Combined sign-then-encrypt eliminates most email malware.
  • Kerberos: Ticket-based auth. (1) AS Exchange: client to Authentication Server, receives TGT. (2) TGS Exchange: present TGT to Ticket Granting Server, get service ticket. (3) Client/Server: present service ticket to access service. Uses symmetric crypto (AES). Single sign-on. Time-sensitive: requires synchronized clocks (prevents replay).
  • Certificate formats: PKCS#7: signed/encrypted data (cert chains, S/MIME). PKCS#10: CSR format. PKCS#12: cert+private key bundle (.pfx/.p12). X.509v3: standard cert with extensions. PEM: Base64 DER with header/footer. DER: binary encoding.
W12 - Wireless Crypto & Stream Ciphers
  • Wireless architecture: STA (station/client device), AP (access point, ~100m range). Open broadcast medium = anyone within range can eavesdrop. No physical access needed. Fundamental trade-off: convenience vs security. Supplicant = client device requesting access.
  • Home vs Enterprise: Home: single router handles everything, PSK (pre-shared key) for all users. Enterprise: centralized auth via RADIUS/TACACS+ backend servers, lightweight APs managed by wireless controller, per-user credentials, certificate-based auth.
  • 802.1X + EAP + RADIUS: 802.1X = port-based access control (wired AND wireless). EAP = Extensible Authentication Protocol (framework, not single protocol). 7-step process: supplicant - authenticator (AP) - authentication server (RADIUS). EAPOL between client/AP, EAP over RADIUS to backend.
  • EAP variants: PEAP = server-side certs only (server proves identity, client uses password inside TLS tunnel). EAP-TLS = mutual TLS with client AND server certificates (strongest, but harder to deploy -- every device needs cert).
  • RC4 stream cipher: Two phases: Key Setup (initialize 256-byte S-box, swap based on key) - Keystream Generation (generate pseudo-random bytes). XOR keystream with plaintext = ciphertext. Byte-oriented, fast on limited hardware (why chosen for WEP).
  • RC4 key reuse = fatal: If same keystream used twice: C1 XOR C2 = P1 XOR P2 (keystream cancels out). Attacker gets relationship between plaintexts. With known plaintext, recovers everything. Solution: prepend unique IV to key for each packet.
  • WEP (Wired Equivalent Privacy) -- BROKEN: RC4 + 24-bit IV + 40-bit key (later 104-bit). Failures: (1) 24-bit IV = only 16.7M values, repeats in hours on busy network, (2) FMS attack exploits weak IVs in RC4 key schedule, (3) NO replay protection, (4) CRC-32 is linear (NOT crypto hash) -- bit-flipping attack: attacker modifies ciphertext AND recomputes valid CRC without knowing key, can redirect traffic, (5) Single global key shared by all users, (6) No key management protocol. Crackable in <5 minutes with aircrack-ng.
  • WPA (Wi-Fi Protected Access): TKIP = Temporal Key Integrity Protocol. Fixes over WEP: 48-bit IV (won't repeat for years), per-packet key mixing (hashed IV+key), MIC (Michael) for integrity (replaces CRC-32), sequence counter (replay protection). But: still RC4 underneath, still inherits some RC4 weaknesses. Designed as firmware-only upgrade for WEP hardware -- stepping stone.
  • WPA2 (802.11i): AES-CCMP replaces RC4 entirely. CCMP = Counter mode with CBC-MAC Protocol (encryption + integrity in one). 4-way handshake: (1) AP sends ANonce, (2) STA sends SNonce + MIC, (3) AP sends GTK + MIC, (4) STA sends ACK. PTK derived from: PMK + ANonce + SNonce + MAC addresses. PSK mode: PMK = PBKDF2(passphrase, SSID, 4096, 256). Enterprise mode: PMK from RADIUS/802.1X.
  • Cracking WPA2-PSK: Capture 4-way handshake (specifically Message 2 with SNonce + MIC). Offline dictionary attack: guess password - derive PMK via PBKDF2 - derive PTK - compute MIC - compare to captured MIC. If match, password found. NOT a crypto break -- vulnerability is weak/short passwords. Strong random passphrase = secure.
  • KRACK (Key Reinstallation Attack, 2017): Replays handshake message 3 - forces client to reinstall already-in-use key - nonce reuse. Targets the 4-way handshake IMPLEMENTATION, NOT AES itself. Affects clients (not APs). Allows packet decryption/injection. Fix: patch client software to reject replayed messages.
  • WPA3 (2018): SAE (Simultaneous Authentication of Equals)/Dragonfly replaces 4-way handshake with password-authenticated key exchange. Benefits: forward secrecy (each session has unique keys, compromising password doesn't reveal past sessions), brute-force protection (online only, no offline dictionary attack), individualized encryption (unique keys per client even with same PSK), PMF (Protected Management Frames) required -- prevents deauth attacks. 128-bit personal / 192-bit enterprise (CNSA suite). Mandatory for Wi-Fi 6 (802.11ax) certified devices.
  • Attacks: Evil Twin (fake AP with same SSID, stronger signal, intercepts traffic -- VPN protects). Rogue AP (unauthorized AP on corporate network, bypasses firewall -- detected by wireless IDS). DoS: RF jamming (physical layer), disassociation/deauthentication flooding (management frames -- WPA3 PMF mitigates). War driving: scanning for vulnerable networks using GPS + WiFi scanner (Kismet, Wigle).
  • 802.1X EAP 7-step process: (1) Client associates with AP (open). (2) AP blocks all traffic except EAP (port blocked). (3) Client sends EAP-Start/Identity. (4) AP forwards to RADIUS server (EAP over RADIUS). (5) RADIUS challenges client (credentials/cert). (6) Client responds, RADIUS validates. (7) RADIUS sends Accept -- AP opens port. EAPOL = EAP over LAN (Layer 2 frames between client and AP). RADIUS uses UDP 1812/1813.
  • RADIUS AAA: Authentication (who are you?), Authorization (what can you access?), Accounting (what did you do?). Centralized credential management. Supports multiple auth methods via EAP. TACACS+ (Cisco): similar but uses TCP, separates AAA functions, encrypts entire payload (RADIUS only encrypts password).
  • RC4 two-phase detail: KSA: init S[0..255]=identity. For i=0-255: j=(j+S[i]+key[i mod keylen]) mod 256, swap S[i],S[j]. Result: key-dependent permutation. PRGA: i=j=0. Each byte: i=(i+1)%256, j=(j+S[i])%256, swap S[i],S[j], output S[(S[i]+S[j])%256]. XOR output with plaintext = ciphertext.
  • WEP cracking method: (1) Collect packets (inject ARP to generate traffic). (2) 24-bit IV repeats in ~5 hours. (3) Same IV: C1 XOR C2 = P1 XOR P2. (4) FMS attack: weak IVs leak key bytes via KSA bias. (5) ~40K-85K weak IVs = full key recovery. Tools: aircrack-ng. Under 5 minutes.
  • WPA2 4-way handshake detail: M1: AP sends ANonce. Client derives PTK (has PMK+ANonce+SNonce+MACs). M2: Client sends SNonce+MIC. AP derives PTK, verifies MIC. M3: AP sends GTK (encrypted w/ PTK)+MIC. Client installs PTK+GTK. M4: Client ACK. Both have PTK (unicast) and GTK (multicast/broadcast).
  • PBKDF2 for PSK: PMK = PBKDF2-SHA1(passphrase, SSID, 4096, 256). Passphrase 8-63 chars. SSID=salt. 4096 iterations slow brute-force. Weak passwords still vulnerable to dictionary attacks despite stretching.
  • WPA3 OWE: Opportunistic Wireless Encryption for open networks. Unauthenticated DH = encrypted but NOT authenticated (still vulnerable to evil twin). No password needed. Each client gets unique keys. Better than no encryption.
  • Rogue AP detection: Wireless IDS scans for unauthorized APs. Methods: MAC address database comparison, signal strength triangulation, wired-side monitoring. 802.11w PMF prevents spoofed deauth to force clients to rogue AP.
  • PUFs (Physically Unclonable Functions): Hardware auth using manufacturing variations. Each chip has unique physical characteristics (gate delays, capacitances). Challenge-response: cannot be cloned even by manufacturer. Used for IoT device identity, key generation without storage, anti-counterfeiting.
KEY SIZE EQUIVALENCES (ECC vs RSA vs Symmetric)
  • 80-bit sym = 1024-bit RSA = 160-bit ECC (minimum, legacy)
  • 112-bit sym = 2048-bit RSA = 224-bit ECC (transitional)
  • 128-bit sym = 3072-bit RSA = 256-bit ECC (current standard, NIST P-256)
  • 192-bit sym = 7680-bit RSA = 384-bit ECC (NIST P-384)
  • 256-bit sym = 15360-bit RSA = 512-bit ECC (highest security)
  • CAB Forum requires RSA min 3072 bits. ECC 256-bit provides equivalent security with 12x smaller key.
  • ECDLP has NO sub-exponential algorithm -- RSA's integer factoring DOES (GNFS). This is why ECC keys are shorter.
EMAIL vs SSL/TLS vs IPsec COMPARISON
  • Email (PGP): Unilateral crypto (sender chooses, no negotiation), single message granularity, nonrepudiation YES (signs plaintext with private key), sign-then-encrypt order, Web of Trust (no CA), provides all 5 security services.
  • SSL/TLS: Negotiated cipher suite (ClientHello/ServerHello), session-based (multiple messages), nonrepudiation NO (shared session keys), sign-then-encrypt, sits above transport layer, 6 keys/session (3 per direction), requires PKI/certificates.
  • IPsec: Negotiated (IKE), encrypts-then-signs, nonrepudiation NO, transparent to user/application, operates at network layer (encrypts IP packets), two modes: transport (payload only) vs tunnel (entire packet). Verify signature before decrypting.
  • Key difference: Only PGP provides nonrepudiation. TLS/IPsec use shared session keys -- either party could have generated the MAC. PGP signs with sender's private key (only sender has it).
HOMOMORPHIC ENCRYPTION AT A GLANCE
  • PHE: One operation unlimited. RSA=multiply (deterministic), Paillier=add (probabilistic), ElGamal=multiply (probabilistic).
  • SWHE: Both add+multiply, limited circuit depth. Noise grows with operations. No bootstrapping.
  • FHE: Both operations, unlimited depth. Gentry 2009. Bootstrapping refreshes noise. Any function = add+multiply.
  • Schemes: BFV=exact integers (database queries). CKKS=approximate/ML (floating point, small error OK). BGV=exact, bit-level ops. TFHE=fast gate-by-gate bootstrapping.
  • RSA HE test: E(3)*E(4) should = E(12). Example: n=33, e=7. E(3)=3^7 mod 33=2187 mod 33=9. E(4)=4^7 mod 33=16384 mod 33=16. 9*16=144 mod 33=12. E(12)=12^7 mod 33=12. Confirmed: 12=12.
  • Paillier HE test: E(m1)*E(m2) mod n^2 = E(m1+m2). Multiplying ciphertexts = adding plaintexts. Random r makes each encryption unique.
  • Performance: ~8x improvement/year since 2011. Bootstrapping: 1800s (2011) to 0.5s (2021). Still 1000-1,000,000x slower than plaintext operations. Hardware acceleration (DARPA DPRIVE) aims to close gap.
WIRELESS SECURITY EVOLUTION
  • WEP: RC4 stream cipher + 24-bit IV + 40-bit key. IV repeats in hours. FMS weak key attack. CRC-32 (linear, bit-flipping possible). No replay protection. Single global key. Cracked in minutes.
  • WPA: TKIP wrapper around RC4. 48-bit IV + per-packet key mixing + MIC (Michael) + sequence counter. Firmware upgrade for WEP hardware. Still inherits RC4 weaknesses.
  • WPA2: AES-CCMP (block cipher, real crypto). 4-way handshake derives PTK from PMK+nonces+MACs. PSK (home) vs Enterprise (RADIUS/802.1X). KRACK vulnerability targets handshake implementation, not AES.
  • WPA3: SAE/Dragonfly (PAKE), forward secrecy, no offline dictionary attack, individualized encryption, PMF required, 128/192-bit. Mandatory Wi-Fi 6. Fixes every major WPA2 weakness.
  • Progression: WEP (no real security) - WPA (band-aid) - WPA2 (solid but implementation flaws) - WPA3 (forward secrecy + resistance to offline attacks).
SECURITY SERVICES: WHAT PROVIDES WHAT?
  • Digital Sigs (ECDSA/RSA): Integrity YES | Auth YES | Non-repudiation YES | Confidentiality NO. Sign with private key, verify with public.
  • HMAC: Integrity YES | Auth YES | Confidentiality NO | Non-repudiation NO (shared key -- either party could produce).
  • Sym Encryption (AES): Confidentiality YES | Integrity NO | Auth NO. Add HMAC or use GCM mode for integrity.
  • PGP: Auth+Integrity+Non-repudiation+Confidentiality (signs plaintext with private key, then encrypts). ALL 5 services.
  • SSL/TLS: Auth+Confidentiality+Integrity. NO non-repudiation (shared session keys).
  • Hashing (SHA-256): Integrity YES (detect changes) | Confidentiality NO | Auth NO (no key) | Non-repudiation NO. Irreversible.
  • HE: Confidentiality YES (data stays encrypted) | Computation YES | Integrity depends on scheme. Does NOT authenticate.
  • Blockchain: Integrity YES (tamper-evident) | Non-repudiation YES (signed transactions) | Availability YES (distributed). Confidentiality: only if transactions are encrypted.
BLOCKCHAIN & CONSENSUS QUICK REF
  • Byzantine fault tolerance: Oral messages: need >2/3 loyal (n >= 3f+1 where f=traitors). Written/signed messages: tolerate ANY number of traitors.
  • Schneier Protocol #4: Secret splitting with XOR. Identity string split into pairs. Bank chooses random subset to verify. Remaining pairs embedded in coin. Double-spend: two copies reveal ALL identity pairs -- XOR recovers identity.
  • Consensus types: PoW (Bitcoin, energy-intensive, 51% attack risk), PoS (Ethereum, stake-based, nothing-at-stake problem), PBFT (permissioned, <1/3 faulty), Paxos (crash tolerance, not Byzantine).
  • Smart contracts: Self-executing code on blockchain. "Code is law." Risks: bugs are permanent (immutable), reentrancy attacks (DAO hack 2016, $60M), oracle problem (external data feeds).
TLS HANDSHAKE & SESSION KEYS
  • Handshake flow: (1) ClientHello: version, cipher suites, client_random. (2) ServerHello: selected suite, server_random, certificate. (3) Client verifies cert chain. (4) Key exchange (pre-master secret). (5) Both derive master secret. (6) Both derive 6 session keys.
  • 6 keys: Client write encryption key, Client write MAC key, Client write IV, Server write encryption key, Server write MAC key, Server write IV.
  • TLS 1.3 changes: Removed RSA key exchange (forward secrecy required). Only AEAD ciphers (AES-GCM, ChaCha20-Poly1305). 1-RTT handshake (faster). Removed compression (CRIME attack). Removed renegotiation.
  • Cipher suite example: TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 = ECDHE key exchange, RSA auth, AES-128-GCM encryption, SHA-256 for PRF.
EXAM TRAPS & GOTCHAS
  • SSL/TLS does NOT provide nonrepudiation (PGP does -- because PGP signs with private key)
  • RSA is multiplicatively homomorphic (NOT additively). Paillier is additively homomorphic (NOT multiplicatively)
  • WPA2 KRACK targets handshake IMPLEMENTATION, NOT the AES algorithm itself
  • ECC 256-bit = RSA 3072-bit security (not equal bit count). ECDLP has NO sub-exponential algorithm
  • Bootstrapping = solution AND bottleneck for FHE. Refreshes noise but is computationally expensive
  • WEP uses CRC-32 (NOT a crypto hash) -- CRC is linear, enables bit-flipping attacks
  • TLS uses 6 secret keys per session (3 per direction: encryption, MAC, IV)
  • Sign-then-encrypt = PGP/SSL (hides signatories). Encrypt-then-sign = IPsec (verify before decrypt)
  • Byzantine: >2/3 loyal needed for oral messages. ANY number of traitors with written/signed messages
  • 4a^3 + 27b^2 != 0 for valid elliptic curve (non-zero discriminant = no singularities)
  • WPA2-PSK cracking = weak passwords, NOT broken crypto. Strong passphrase = secure
  • RC4 key reuse = fatal (XOR of two ciphertexts cancels keystream, reveals P1 XOR P2)
  • Paillier is probabilistic (random r), RSA is deterministic. Both are PHE but for different operations
  • RAD 1978 POSED the HE problem. Gentry 2009 SOLVED it (31 years later)
  • WPA3 SAE prevents OFFLINE dictionary attacks (unlike WPA2-PSK which allows offline cracking)
  • Email crypto is UNILATERAL (sender chooses). TLS crypto is NEGOTIATED (both sides agree)
  • Forward secrecy: compromise of long-term key does NOT reveal past sessions (ephemeral DH)
  • ECDSA with bad random k = private key leak (PS3 hack). ECC more dependent on randomness than RSA
  • TLS 1.3 removed static RSA key exchange -- REQUIRES forward secrecy (DHE/ECDHE only)
  • Point at Infinity = identity element in ECC (like 0 in addition, like 1 in multiplication)
KEY FORMULAS & NUMBERS
  • ECC: y^2 = x^3 + ax + b. Valid if 4a^3 + 27b^2 != 0. Q=kP (ECDLP: given P, Q, find k). Point addition: line through P,Q, reflect 3rd intersection.
  • RSA HE (multiply): E(m1)*E(m2) = (m1*m2)^e mod n = E(m1*m2). Enc: c=m^e mod n. Dec: m=c^d mod n.
  • Paillier HE (add): c = g^m * r^n mod n^2. E(m1)*E(m2) mod n^2 = E(m1+m2).
  • ECDH: Alice: aG. Bob: bG. Shared: abG = baG (commutativity of scalar multiplication).
  • WPA2 key derivation: PMK = PBKDF2(passphrase, SSID, 4096 iterations, 256 bits). PTK = PRF(PMK, ANonce, SNonce, MAC_AP, MAC_STA).
  • WEP: 24-bit IV (16.7M values) + 40/104-bit key. WPA: 48-bit IV (281 trillion). WPA3: 128/192-bit.
  • HE performance: ~8x improvement/year. Bootstrapping: 1800s (2011) to 0.5s (2021). Pinocchio: 288-byte proofs, 10ms verify.
  • Byzantine: n >= 3f+1 generals needed (f = max traitors tolerated) for oral messages.
  • TLS: 6 keys/session. Master secret derived from pre-master + client_random + server_random.

PROTOCOL COMPARISON: PGP vs S/MIME vs TLS vs IPsec
  • PGP: Layer=Application. Crypto selection=Unilateral (sender). Auth=Web of Trust. Non-repudiation=YES. Order=Sign-then-encrypt. Key mgmt=Manual/keyservers. Granularity=Per message. Use=Email, file encryption.
  • S/MIME: Layer=Application. Crypto selection=Unilateral. Auth=PKI (X.509 certs from CA). Non-repudiation=YES. Order=Sign-then-encrypt. Key mgmt=CA-issued certs. Granularity=Per message. Use=Enterprise email. Easier to deploy in corporate environment than PGP.
  • TLS: Layer=Transport (between app and TCP). Crypto selection=Negotiated (ClientHello/ServerHello). Auth=PKI certs (usually server-only). Non-repudiation=NO (shared session keys). Order=Sign-then-encrypt. Key mgmt=PKI + ephemeral DH. Granularity=Per session. Use=HTTPS, secure web. 6 keys/session.
  • IPsec: Layer=Network (IP). Crypto selection=Negotiated (IKE). Auth=Pre-shared keys or certs. Non-repudiation=NO. Order=Encrypt-then-sign. Key mgmt=IKE (automated). Granularity=Per packet. Modes: Transport (payload only) vs Tunnel (entire IP packet wrapped). Use=VPNs. Transparent to applications. AH (auth only) vs ESP (auth+encrypt).
  • Key differences: Only PGP/S/MIME provide non-repudiation. Only TLS/IPsec negotiate crypto. Only IPsec encrypts-then-signs. TLS is session-based; PGP/S/MIME are message-based. IPsec is transparent to apps; TLS requires app support (HTTPS). PGP has no central authority; all others use some form of PKI.
BLOCKCHAIN CONSENSUS: PoW vs PoS vs DPoS vs PBFT
  • PoW (Proof of Work): Miners solve SHA-256 puzzle (find nonce where hash < target). First to solve wins block reward. Energy-intensive (Bitcoin uses ~150 TWh/year). Security: 51% of hash power to attack. Finality: probabilistic (6 confirmations ~1 hour). Throughput: ~7 TPS (Bitcoin). Sybil-resistant: cost of compute. Used by: Bitcoin, Litecoin, Monero.
  • PoS (Proof of Stake): Validators stake cryptocurrency as collateral. Selected to propose blocks proportional to stake. Slashing: lose stake for malicious behavior. Energy-efficient (99.9% less than PoW). Nothing-at-stake problem: validators can cheaply vote on multiple forks. Finality: faster (~12s Ethereum). Throughput: ~30 TPS. Used by: Ethereum (post-Merge 2022), Cardano, Solana.
  • DPoS (Delegated PoS): Token holders vote for delegates/witnesses who produce blocks. Small fixed set of validators (21-101 typically). Very fast (1-3s blocks, ~1000+ TPS). Trade-off: more centralized (cartel risk). Used by: EOS, TRON, Lisk. Democratic but concentration of power possible.
  • PBFT (Practical Byzantine Fault Tolerance): Permissioned consensus. Leader proposes block, validators vote in rounds (pre-prepare, prepare, commit). Tolerates
  • Summary: PoW=most decentralized, least efficient. PoS=balanced. DPoS=fastest, least decentralized. PBFT=instant finality, permissioned only. Blockchain trilemma: cannot optimize decentralization + security + scalability simultaneously (pick 2).
MORE EXAM TRAPS
  • Paillier ciphertext MULTIPLICATION = plaintext ADDITION (do NOT confuse operations)
  • ElGamal is multiplicatively homomorphic AND probabilistic (unlike deterministic RSA)
  • Bootstrapping evaluates the DECRYPTION circuit homomorphically (not encryption)
  • CKKS = approximate (ML/float). BFV = exact integers. Do not swap them
  • WPA uses TKIP (still RC4). WPA2 uses AES-CCMP (completely replaces RC4)
  • KRACK = nonce reuse via replayed M3. Targets CLIENTS not APs. Does NOT break AES
  • OWE provides encryption but NOT authentication (still vulnerable to evil twin)
  • 802.1X is for BOTH wired AND wireless (not wireless-only)
  • PEAP = server cert only. EAP-TLS = mutual certs (both sides)
  • Bitcoin is pseudonymous (linkable addresses), NOT anonymous
  • Hard fork = backward-INCOMPATIBLE (chain splits). Soft fork = compatible
  • PBKDF2 uses SSID as salt -- same password, different network = different PMK
  • Heartbleed = OpenSSL implementation bug, NOT TLS protocol flaw
EXCEL QUICK REFERENCE (Post-Midterm)
  • Core: =MOD(a,n) modular. =POWER(base,exp). =GCD(a,b).
  • RSA HE test: E(m)==MOD(POWER(m,e),n). Verify: E(m1)*E(m2) mod n = E(m1*m2). =MOD(E1*E2,n) should equal =MOD(POWER(m1*m2,e),n).
  • Paillier verify: =MOD(E1*E2,n^2) should = E(m1+m2).
  • ECC discriminant: =4*POWER(a,3)+27*POWER(b,2). If non-zero, curve is valid.
  • ECDH: Shared secret = =MOD(POWER(g,a*b),p) (simplified for small numbers).
  • WPA2 key space: 24-bit IV: =POWER(2,24) = 16,777,216. 48-bit IV: =POWER(2,48) = 281 trillion.
  • Mod inverse (brute): Col A: 1,2,3... Col B: =MOD(A1*e,phi). Find row where B=1. That A value = d.
