W1 - Visualization Fundamentals
  • CHART TYPES - WHEN TO USE: Bar (compare categories, GAPS between bars), Scatter (2 variables, correlations, no line connecting), Line (trends over TIME, connected points), Pie (parts of whole - AVOID, hard to read, angle=rel.freq*360, 25%=90 degrees), Histogram (distribution of ONE numeric variable, bars TOUCH, x-axis=number ranges), Heatmap (matrix values, color intensity shows magnitude), Dot plot (small datasets, individual values), Stem-and-leaf (small datasets, preserves actual digits, stem=tens, leaf=ones).
  • BAR vs HISTOGRAM: Bar = categories with GAPS between bars. Histogram = numeric ranges, bars TOUCH. If x-axis has labels = bar chart. If x-axis has number ranges = histogram. NEVER confuse these on exam.
  • WORD CLOUD: Most repetitive word drawn BIGGER. Good for customer feedback/text analysis. Size proportional to frequency.
  • PERCEPTION HIERARCHY: Position > Length > Angle > Area > Color for accuracy of human judgment. Use position-based encodings (bar charts) over area-based (pie charts) when precision matters.
  • PRE-ATTENTIVE ATTRIBUTES: Color, size, orientation, shape - processed BEFORE conscious thought (within 200ms). Use for highlighting important data. Limited to ~4 distinct pre-attentive features before cognitive overload.
  • DATA-INK RATIO (Tufte): = Data-ink / Total ink used. MAXIMIZE data ink, MINIMIZE chart junk. Remove: unnecessary gridlines, borders, backgrounds, 3D effects, decorative elements. "Above all else, show the data." Every drop of ink should present new info.
  • COLOR USE: Sequential palette (low-to-high, single hue gradient), Diverging (center point, two hues diverge - good for pos/neg), Categorical (distinct unrelated groups, max ~7 colors). ~8% males colorblind (red-green most common). Tableau/Power BI can swap palettes for accessibility. Use color PURPOSEFULLY not haphazardly.
W2 - Data Sources, Tools & Statistical Foundations
  • SECURITY DATA SOURCES: Network devices (switches, routers), firewalls, IDS/IPS, endpoint security (Norton etc), servers/apps, IAM/MFA/SSO, DLP, vulnerability scanners, threat intel feeds, honeypots, SIEM, cloud logs (AWS CloudWatch, Azure Defender/Sentinel), cloud access security brokers (CASB).
  • DATA FORMATS: JSON (name-value pairs, current standard, replaced XML), CSV (legacy, simple flat files), Parquet (columnar, big data).
  • STORAGE - RELATIONAL SQL: Oracle, MySQL, MS SQL, PostgreSQL. Structured, ACID transactions, star schema for reporting.
  • STORAGE - NoSQL: MongoDB (document/JSON store), Redis (in-memory key-value cache), Cassandra (column-based, highly resilient), Neo4j (graph DB - nodes + relationships).
  • GRAPH DB: Nodes + relationships. Natural for reasoning, social networks, fraud detection. "Friends within 5 hops" = trivial query (extremely hard in SQL with JOINs). Augments LLMs for reasoning/knowledge graphs.
  • HDFS (Hadoop): Files chunked into 128MB blocks, replicated 3x across machines. Compute moves to data (not data to compute). Spark = execution engine. Linearly scalable - add nodes for more capacity.
  • OTHER STORAGE: Object (S3, Azure Blob - versioning), Time-series (InfluxDB - indexed by timestamp), In-memory (Redis, SAP HANA - fuses transactional + reporting), Search/Log (Splunk = proprietary/Cisco, ELK = open source).
  • STAR SCHEMA: Dimension tables (WHO/WHAT/WHERE/WHEN) + Fact tables (measurements/metrics). Optimized for reporting/analytics. Power BI and Tableau designed to read star schemas. Kimball methodology.
  • TOOLS - GENERAL PURPOSE (GP): Swiss army knife. Power BI (drag-drop, connects to anything, PowerPoint integration, marketplace components, desktop+cloud, scheduling, free GWU license). Tableau (interactive, Data Flow for ETL, strong visual storytelling). Looker (Google). GP features: drag-drop, cloud+desktop, marketplace, connect to anything incl HDFS, scheduling, embed in presentations, predefined dashboards, ETL built-in.
  • TOOLS - SPECIALIZED: Excel (quick analysis, pivots, ~1.5M row limit), Python (pandas/matplotlib/seaborn, most flexible, LLMs write code for you), Splunk (SIEM, file/index-based, event queries, results update as searched, now Cisco), ELK (open source: Elasticsearch+Logstash+Kibana), Grafana (time-series dashboards), ArcGIS (geospatial).
  • GARTNER MAGIC QUADRANT: Leaders = Salesforce/Tableau, Microsoft/Power BI, Google/Looker. Evaluates vision + execution ability.
  • TELLING THE STORY: Who is audience? What action should they take? What data supports the message? Structure: context -> insight -> action. "Getting the Visualization Done."
  • DESCRIPTIVE vs INFERENTIAL: Descriptive = summarize data (mean, median, charts, tables). Inferential = use sample to draw conclusions about population (hypothesis tests, confidence intervals).
  • POPULATION vs SAMPLE: Population = everything of interest. Sample = slice actually measured. Target pop (want to study) vs Sampled pop (actually measured). Can't measure everything (too expensive, impossible, destructive). Fix: take representative sample. Non-representative sample = wrong conclusions.
  • 4 SAMPLING METHODS: Simple Random (equal chance for each unit, default gold standard), Stratified (split into groups by characteristic, sample a BIT from EVERY group - ensures representation), Systematic (random start, then every m-th item, m=N/n), Cluster (pick a FEW whole groups randomly, take EVERYTHING in those groups).
  • STRATIFIED vs CLUSTER (EXAM TRAP): Stratified = sample FROM every group (bit from each). Cluster = sample WHOLE groups (everything from a few). Example: stratified = sample students from every department. Cluster = pick 3 departments, survey ALL students in those 3.
  • SAMPLING TERMS: Sampling unit (thing you pick/select), Sampling frame (complete list of all units), Variable (characteristic you measure on each unit).
  • 4 DATA TYPES (NOIR): Nominal (labels, NO order: eye color, gender, IP address, protocol, port number), Ordinal (labels, CAN order: satisfaction, severity low/med/high, military rank), Interval (numbers, no TRUE zero: temp C/F, dates, pH - 0 degrees C is NOT "no temperature"), Ratio (numbers, TRUE zero: height, weight, age, packet size, duration - 0 = none of it, ratios meaningful like "twice as heavy").
  • TYPE DECISION TREE: Step 1: Label or Number? LABEL -> Step 2: Can you order/rank? No = NOMINAL. Yes = ORDINAL. NUMBER -> Step 3: Does zero mean "nothing/absence"? Yes = RATIO. No = INTERVAL. NOIR = increasing info: Nominal < Ordinal < Interval < Ratio.
  • TRICKY EXAMPLES: Port numbers = NOMINAL (not ratio! arithmetic on port numbers meaningless - port 80 is not "twice" port 40). Temperature C/F = INTERVAL (not ratio! 0 degrees C is not "no temperature"). Height/weight/age = RATIO. IP address = NOMINAL.
  • FREQUENCY TABLE: Frequency f, relative freq = f/total, percentage = rel*100, cumulative freq = running sum. Class recipe: Range R = max - min. Number of classes m = 1 + 3.3*log10(n), rounded. Width = R/m, rounded UP. Bracket notation: [110,117) means 110 included, 117 excluded.
  • PIE CHART ANGLE: Angle = relative frequency * 360 degrees. 25% of data = 0.25 * 360 = 90 degree slice.
W3 - Endpoint Security, Preprocessing & Numeric Measures
  • ENDPOINT: Any device on network - desktop, laptop, server, smartphone, IoT device, tablet. Each = potential attack vector. Data sources: antivirus/EDR logs, quarantined files, process execution logs.
  • ML PIPELINE: Dataset -> Cleaning -> Feature Engineering -> Training Data -> Algorithm -> Model | New Data -> Score -> Evaluate. "Garbage In, Garbage Out" - data prep = 80% of ML work.
  • STEP ZERO - EXPLORE FIRST: df.describe() (stats summary: count, mean, std, min, quartiles, max), df.info() (dtypes, null counts, memory), data dictionary. Understand shape, types, distributions BEFORE cleaning.
  • CLEANING COMMANDS: df.dropna(inplace=True) drop all rows with any null, df.dropna(subset=['col']) drop only if specific col is null, df.fillna(value) fill nulls, df.duplicated().any() check for dupes, df.drop_duplicates(inplace=True), df.replace(old, new), df.reset_index(drop=True), df.astype(type) convert types.
  • TEXT OPS: str.replace(), str.lower(), str.upper(), str.strip() (remove leading/trailing whitespace).
  • df.loc: df.loc[row, col] access by label, df.loc[df['col']>5] boolean mask filtering, df.loc[0:5, 'A':'C'] slicing rows and columns by label.
  • IMPUTATION METHODS: Mean/Median/Mode (simple, fast, underestimates variability), Constant Value (0, "Unknown" - good for categorical), Linear Interpolation (time-series with smooth trends), Forward Fill ffill (carry last known value forward), Backward Fill bfill (carry next known backward), KNN (average of k nearest neighbors, preserves relationships, O(n^2) slow), Model-based (regression/decision tree/neural net, best accuracy, most complex).
  • FEATURE ENGINEERING: Create NEW features from existing data. "Secret sauce" of ML. Requires domain knowledge. Examples: time-of-day from timestamp, login frequency, failed-to-success ratio, financial stability index (combines income+education+balance). Transforms raw data into predictive signals.
  • NORMALIZATION: Scale features so no single feature dominates due to unit differences. Accelerates model training. Ensures all features contribute equally regardless of original scale.
  • CENTER - MEAN: X-bar = sum(Xi)/n. Arithmetic average. SENSITIVE to outliers - one billionaire in room of 10 makes "average income" misleading. Use for symmetric data.
  • CENTER - MEDIAN: Middle value at rank position (n+1)/2. If n is even, average the two middle values. ROBUST to outliers (barely moves). Use for skewed data (income, home prices, salaries).
  • CENTER - MODE: Most frequent value. Only center measure that works for NOMINAL/categorical data. Can be unimodal (1 peak), bimodal (2 peaks), multimodal (3+ peaks). A dataset CAN have no mode if all values appear equally.
  • SHAPE FROM CENTER: Mean = Median = Mode -> symmetric (bell curve). Mode < Median < Mean -> RIGHT-skewed (tail stretches right, few large values pull mean up). Mean < Median < Mode -> LEFT-skewed (tail stretches left). MEMORY: "The mean chases the tail" - mean always pulled toward the long tail.
  • SPREAD - RANGE: Range = max - min. Quick overview but uses only 2 data points. Very sensitive to outliers.
  • SPREAD - VARIANCE: S^2 = sum(Xi - X-bar)^2 / (n-1). Why SQUARE deviations? Plain gaps would cancel to zero (positives and negatives cancel). Why n-1 (not n)? Bessel's correction - corrects underestimation bias in sample. Population variance uses N (no correction needed). VARIANCE IS IN SQUARED UNITS (e.g., inches^2).
  • SPREAD - STANDARD DEVIATION: S = sqrt(S^2). Returns spread to ORIGINAL units. Tells you typical distance from mean. SD calculation: Data 4,2,5,1,3,6,2,4,3,5. Sum=35. Mean=3.5. Sum of Xi^2=145. S^2=(1/(n-1))*(SumXi^2 - n*X-bar^2) = (1/9)*(145-122.5) = 2.5. S=sqrt(2.5)=1.58.
  • PARAMETER vs STATISTIC: Parameter = population measure, Greek letters (mu for mean, sigma for SD, sigma^2 for variance). Statistic = sample measure, Latin letters (X-bar for mean, S for SD, S^2 for variance). Same concept, different notation depending on population vs sample.
  • EMPIRICAL RULE (bell-shaped ONLY): Within 1 SD = 68% of data. Within 2 SD = 95%. Within 3 SD = 99.7%. Security application: anything beyond 3 sigma = anomaly flag. "3 sigma out = this is weird, investigate it."
  • CHEBYSHEV'S THEOREM: Works for ANY shape distribution (not just bell). At least 1 - 1/k^2 of data within k SDs of mean. k=2: at least 75%. k=3: at least 88.9%. Always gives LOOSER (more conservative) bounds than Empirical Rule.
  • Z-SCORE: Z = (Xi - mean) / SD. How many SDs a value is from the mean. UNITLESS (allows comparison across different scales). |Z| > 3 = likely outlier in bell-shaped data. Z=0 means value equals the mean.
  • COVARIANCE: Measures linear association between two variables. Positive = move together (both up or both down). Negative = move opposite. Units = product of original units (hard to interpret magnitude).
  • CORRELATION r: r = Cov(X,Y) / (Sx * Sy). Standardized covariance. Range: [-1, +1]. +1 = perfect positive linear, -1 = perfect negative linear, 0 = no LINEAR relationship. UNITLESS. Correlation does NOT imply causation. Only measures LINEAR relationships (can miss curves).
W4 - User Security & Hypothesis Testing
  • USER DEFINED: Any entity (human OR non-human) with user ID and system permissions. Includes bots, APIs, service accounts, automated processes. Not just people.
  • VERIZON DBIR 2025: 60% breaches involve human element, 30% third-party involvement, 17% espionage-motivated. Initial access vectors: credential abuse 22%, vulnerability exploitation 20%, phishing 16%.
  • BREACH PATTERNS: System Intrusion 53% (most common), Misc Errors, Social Engineering, Basic Web App Attacks, Privilege Misuse. Internal actors compromise 10x MORE records than external actors.
  • USER SECURITY DATA SOURCES: Auth/access logs, user account info, network traffic logs, firewall logs, IDS/IPS logs, endpoint security logs, application logs, SIEM logs, incident response records, vulnerability assessment reports, security policies, external threat intel.
  • DEV DATA SOURCES: Code repo logs (Git/SVN), CI/CD pipeline logs, APM (Application Performance Monitoring) data, change management records, privileged access logs, ACLs/RBAC configs.
  • MOBILE DATA: App usage logs, device location, communication logs, social media activity.
  • PRIVACY LAWS: GDPR (EU - consent required, data minimization, right to access/correct/delete, 72hr breach notification). CCPA (California - right to know/delete/opt-out of sale of personal info). PIPEDA (Canada). LGPD (Brazil). DPA 2018 (UK, post-Brexit GDPR equivalent).
  • HYPOTHESIS TESTING = COURTROOM: Assume "nothing interesting" (H0), ask if evidence strong enough to overturn. Like a trial: defendant starts innocent (H0), prosecution must prove guilt (reject H0).
  • H0 (NULL HYPOTHESIS): Boring default = status quo. ALWAYS contains = sign (e.g., mu = 1000, mu >= 500). Like "defendant is innocent." You NEVER "accept H0." You either REJECT H0 or FAIL TO REJECT H0. Never "proven innocent" - just "not enough evidence to convict."
  • H1 (ALTERNATIVE HYPOTHESIS): Your claim/suspicion. Contains inequality (!=, <, >). Like "defendant is guilty." H1 is what you're trying to gather evidence FOR.
  • ONE-TAILED vs TWO-TAILED: One-tailed (H1: mu > mu0 or H1: mu < mu0): rejection region in ONE tail only. Two-tailed (H1: mu != mu0): rejection regions in BOTH tails (alpha/2 in each). H1 decides WHERE rejection region goes. Alpha decides HOW BIG it is.
  • TEST COMPONENTS: Test statistic = single number computed from sample data. Rejection region = range of values extreme enough to reject H0. Critical point = boundary between reject/don't reject regions. Acceptance region = where you fail to reject (NOT "accept").
  • TYPE I ERROR (alpha): FALSE ALARM = reject a TRUE H0. IDS screams "attack!" but it was normal traffic. Probability = alpha (significance level). You CHOOSE alpha before looking at data.
  • TYPE II ERROR (beta): MISSED DETECTION = fail to reject a FALSE H0. Real attack slips through undetected. Probability = beta.
  • POWER = 1 - beta: Ability to correctly detect a real effect/difference. Higher power = better test. Want power >= 0.80 typically.
  • TRADEOFF: Increase sensitivity -> more false alarms (Type I up). Quiet the alarms -> miss real attacks (Type II up). BIGGER SAMPLES reduce BOTH error types simultaneously.
  • ALPHA (SIGNIFICANCE LEVEL): Probability of Type I error you're willing to tolerate. Common values: 0.01 (strict), 0.05 (standard), 0.10 (lenient). Chosen BEFORE looking at data, NEVER after.
  • 6-STEP PROCEDURE: 1. State H0 and H1 clearly 2. Pick significance level alpha 3. Choose a suitable test statistic 4. Identify the test statistic's probability distribution 5. Locate the rejection region(s) and critical point(s) 6. Compute the statistic from data and make decision (reject or fail to reject).
W5 - Code Security & Hypothesis Mechanics
  • CODE SECURITY: Identifying, assessing, mitigating vulnerabilities in software code. Goal: prevent unauthorized access, data breaches. Ensures CIA (Confidentiality, Integrity, Availability). Code = instructions in any programming language.
  • VON NEUMANN ARCHITECTURE: CPU (Control Unit + ALU) + Memory Unit + I/O devices. Instructions and data SHARE same memory. Fundamental vulnerability: data can become instructions (basis for ALL code injection attacks - SQL injection, buffer overflow, XSS).
  • HEARTBLEED (2014): CVE-2014-0160. OpenSSL TLS heartbeat extension. Missing BOUNDS CHECK on payload length field. Attacker sends small payload but CLAIMS large length -> server returns payload + up to 64KB extra memory (private keys, passwords, session tokens). Fix: validate payload length before returning data. Affected ~17% of web servers globally.
  • SOFTWARE SUPPLY CHAIN ATTACK: Threat actors tamper with third-party code to compromise downstream applications. Check Point: 925 attacks/week per org. Exposed secrets: credit cards, passwords, API tokens, certificates, private keys.
  • EQUIFAX (2017): CVE-2017-5638. Apache Struts framework vulnerability. Patch available March 2017, breach discovered September 2017 (6 months!). 147 million people affected. Root cause: FAILED TO APPLY PATCH in timely manner. Lesson: patch management is critical.
  • XZ UTILS (2024): CVE-2024-3094. "Jia Tan" (pseudonym) spent 3 YEARS becoming trusted maintainer through social engineering. Introduced multi-stage backdoor into liblzma library. Exploited glibc IFUNC mechanism to intercept RSA decryption calls in OpenSSH daemon (sshd). Potential RCE on millions of Linux servers. Most critical because it was DELIBERATE, not a mistake. Supply chain attack via trust exploitation.
  • CROWDSTRIKE GLOBAL OUTAGE (2024): NOT a breach/hack but SQA-as-security case study. Channel File 291 configuration update contained bug causing out-of-bounds memory read in Windows sensor client. The "Content Validator" (code designed to CHECK if update was safe) had its OWN bug, allowing malformed data through to kernel driver. Result: BSOD on 8.5 million Windows systems globally. Lesson: single line of defective code = global "Denial of Service." SQA IS security.
  • CVE: MITRE program. Identify, define, catalog publicly disclosed cybersecurity vulnerabilities. cve.mitre.org. NIST: National Institute of Standards and Technology - standards/guidelines for organizations.
  • 10 STEPS TO SECURE CODE: 1. Adopt secure coding practices (input validation, proper error handling, least privilege, secure session mgmt) 2. Perform code reviews (peer + automated) 3. Use SAST and DAST tools 4. Implement vulnerability management (track, prioritize, remediate) 5. Keep dependencies updated 6. Incorporate security testing in SDLC early 7. Use threat modeling 8. Establish secure deployment (environment hardening, access controls) 9. Monitor and audit continuously 10. Foster security culture.
  • SAST vs DAST: SAST = Static Application Security Testing. Examines code WITHOUT executing. White-box (sees source). Finds bugs early in development. DAST = Dynamic Application Security Testing. Tests app WHILE RUNNING. Black-box (no source access). Finds runtime vulnerabilities. RULE: No Security Scans and Reviews -> No Code to Production.
  • Z-TEST STATISTIC: Z = (X-bar - mu0) / (sigma / sqrt(n)). X-bar = sample mean. mu0 = value claimed by H0. sigma = known population SD. n = sample size. sigma/sqrt(n) = STANDARD ERROR.
  • STANDARD ERROR: SE = sigma / sqrt(n). Measures how much sample means naturally wobble around true mean. Bigger n -> smaller SE -> same gap between X-bar and mu0 becomes MORE convincing. Z of 0.5 = meh. Z of 3 = very significant.
  • P-VALUE: Probability of getting a result AT LEAST AS EXTREME as yours, ASSUMING H0 is true. The smallest alpha at which H0 would be rejected. Small p = data is surprising under H0 = evidence AGAINST H0. P-value is NOT P(H0 is true)!
  • DECISION RULE: p-value < alpha -> REJECT H0 (result too surprising to be chance, effect looks real). p-value >= alpha -> DO NOT REJECT H0 (result consistent with boring default, insufficient evidence).
  • P-VALUE vs REJECTION REGION: Two methods, ALWAYS give same answer. P-value usually faster because software gives p directly.
  • TAIL DIRECTION FOR P-VALUE: Left-sided (H1: mu < mu0): p = P(Z <= z_computed). Right-sided (H1: mu > mu0): p = P(Z >= z_computed). Two-sided (H1: mu != mu0): p = 2 * P(Z >= |z_computed|) -- DOUBLE the one-tail probability.
  • WORKED EXAMPLE: Wire tensile strength. n=16, X-bar=967.8 psi, sigma=128 psi. Test H0: mu=1000 vs H1: mu<1000, alpha=0.05. SE = 128/sqrt(16) = 128/4 = 32. Z = (967.8-1000)/32 = -32.2/32 = -1.006. Critical value (left-tail, alpha=0.05): z_crit = -1.645. Since -1.006 > -1.645 (NOT in rejection region), do not reject H0. P-value: P(Z <= -1.006) = 0.1562. Since 0.1562 >= 0.05, do not reject. Both methods agree.
W6 - App Security, Dashboards & Outlier Detection
  • APPLICATION: Any system (software/hardware) or API for specific tasks. Components: frontend + backend + data storage + communication channels. Application Security = protecting apps throughout lifecycle (design -> development -> deployment -> maintenance). Ensures CIA.
  • DASHBOARD DEFINITION (Stephen Few, 2006): "A visual display of the most important information needed to achieve one or more objectives that has been consolidated in a single computer screen [or printed page] so it can be monitored at a glance." Key: SINGLE SCREEN, AT A GLANCE, most IMPORTANT info.
  • MACKINLAY CRITERION: Two requirements: EXPRESSIVENESS (visualization shows ALL and ONLY the facts in the data - no more, no less) + EFFECTIVENESS (information conveyed is more readily perceived than in alternative visualizations - choose the BEST encoding).
  • 13 DASHBOARD ANTI-PATTERNS (Stephen Few): 1. Exceeding boundaries of single screen (scrolling/switching loses context, short-term memory holds only few chunks) 2. Supplying inadequate context (gauges without comparison - "compared to WHAT? forecast? industry?") 3. Displaying excessive detail or precision (10+ significant digits) 4. Choosing a deficient measure (raw budget vs actual when VARIANCE is what matters) 5. Choosing inappropriate visualization type (pie chart when bar easier to interpret) 6. Introducing meaningless variety (mixing chart types for no reason) 7. Using poorly designed visualization type (3D charts, confusing layouts) 8. Encoding quantitative data inaccurately (Y-axis NOT starting at 0, misleading proportions) 9. Arranging data poorly (top-left corner = prime real estate, related data far apart) 10. Highlighting important data ineffectively or not at all (everything equally prominent = nothing stands out) 11. Cluttering display with useless decoration (electronic panel look for sales dashboard) 12. Misusing or overusing color (haphazard, no purpose) 13. Designing an unattractive visual display.
  • BAR > PIE: Humans judge LENGTH more accurately than ANGLE or AREA. Bar chart always better than pie for comparison. Pie chart only acceptable for showing simple proportions (and even then, bar is usually clearer).
  • DESIGN PRINCIPLES: Top-left corner = most important info (eye starts there). Don't throw info on dashboard "just because you can." Related metrics near each other. Use consistent color coding throughout.
  • OUTLIER DEFINED: A value FAR from the rest of the dataset. Can completely DISTORT an average. Salary example: 10 employees including CEO at $100K. Mean WITH outlier = $26K per person. Mean WITHOUT outlier = $17.78K. One value dragged average up ~50%.
  • MEAN vs MEDIAN WITH OUTLIERS: Mean is FRAGILE (outliers drag it dramatically). Median is TOUGH/ROBUST (barely moves with outliers: 17.5 vs 17.0 in salary example). ALWAYS report median for skewed data (salaries, home prices, net worth).
  • BOXPLOT: Visual outlier detector built from QUARTILES (rank-based, so itself outlier-resistant). Components: Q1 (first quartile, 25th percentile), Median/Q2 (50th percentile - line in box), Q3 (third quartile, 75th percentile). Box spans Q1 to Q3. IQR = Q3 - Q1 (width of middle 50% of data). Whiskers extend to last data point within fences.
  • IQR RULE - FENCES: Mild outlier fence: below Q1 - 1.5*IQR or above Q3 + 1.5*IQR ("step 1.5 box-widths past each edge = mildly weird"). Extreme outlier fence: below Q1 - 3*IQR or above Q3 + 3*IQR ("step 3 box-widths = seriously weird"). TRAP: fences calculated from Q1/Q3, NOT from min/max!
  • WHAT TO DO WITH OUTLIERS: Extreme (past 3xIQR) -> usually discard (badly skew results, keep only if clearly genuine and meaningful). Mild (past 1.5xIQR) -> investigate first (could be data-entry error, sensor glitch, or real rare event - don't auto-delete).
  • WHEN YOU CAN'T DELETE: Down-weight observations or use ROBUST statistics: median (instead of mean), MAD (Median Absolute Deviation), Huber loss, Bisquare loss, trimmed mean. These methods aren't thrown off by extreme values.
  • SECURITY ANGLE ON OUTLIERS: In stats class, outlier = noise to remove. In SECURITY, outlier = often THE WHOLE POINT. The login from another continent, the process spawning 10,000 connections, the 3AM data exfiltration. INVESTIGATE before discarding. The outlier might be the attack you're hunting.
  • IQR WORKED EXAMPLE: Q1=10, Q3=30. IQR = 30-10 = 20. Mild fence: [10 - 1.5*20, 30 + 1.5*20] = [10-30, 30+30] = [-20, 60]. Extreme fence: [10 - 3*20, 30 + 3*20] = [10-60, 30+60] = [-50, 90]. Value of 65: outside mild fence (65>60) but inside extreme fence (65<90) = MILD outlier. Value of 95: outside extreme fence (95>90) = EXTREME outlier.
KEY FORMULAS
  • Z-TEST: Z = (X-bar - mu0) / (sigma / sqrt(n)). Reject if |Z| > Z_alpha/2 (two-tail) or Z > Z_alpha (right-tail) or Z < -Z_alpha (left-tail). Common critical values: Z_0.05 = 1.645 (one-tail), Z_0.025 = 1.96 (two-tail at alpha=0.05).
  • VARIANCE: S^2 = sum(Xi - X-bar)^2 / (n-1) [SAMPLE, use n-1]. sigma^2 = sum(Xi - mu)^2 / N [POPULATION, use N]. Variance is in SQUARED units.
  • STANDARD DEVIATION: S = sqrt(S^2). Back in original units. Typical distance from mean.
  • STANDARD ERROR: SE = sigma / sqrt(n). Larger n -> smaller SE -> more precise estimate of population mean. Measures wobble of sample means.
  • IQR FENCES: IQR = Q3 - Q1. Mild: [Q1 - 1.5*IQR, Q3 + 1.5*IQR]. Extreme: [Q1 - 3*IQR, Q3 + 3*IQR]. Points outside = outliers.
  • CLASS RECIPE: R = max - min. m = 1 + 3.3*log10(n), round. Width = R/m, round UP. Brackets: [lower, upper).
  • EMPIRICAL RULE: 68-95-99.7% within 1-2-3 SD. Bell-shaped data ONLY. Chebyshev: at least 1-1/k^2 within k SD (ANY shape). k=2: 75%. k=3: 88.9%.
  • CV (Coefficient of Variation): CV = (S / X-bar) * 100%. Compares variability across different units/scales. Higher CV = more relative spread.
  • CORRELATION: r = Cov(X,Y) / (Sx * Sy). Range [-1, +1]. Unitless. r = 0 means no LINEAR relationship. Correlation != causation.
  • MEDIAN POSITION: Rank = (n+1)/2. If n is even, average the two middle values. Robust to outliers.
  • Z-SCORE: Z = (Xi - mean) / SD. Unitless. |Z| > 3 = likely outlier (bell-shaped). Z = 0 means at the mean.
  • PIE ANGLE: Angle = relative frequency * 360 degrees. Relative freq = count / total.
DATA TYPES DECISION FLOW
  • STEP 1: Is it a NUMBER or a LABEL? LABEL -> Step 2. NUMBER -> Step 3.
  • STEP 2 (Label): Can you ORDER/RANK them? NO = NOMINAL (gender, blood type, IP, protocol, port#). YES = ORDINAL (severity low/med/high, satisfaction, military rank).
  • STEP 3 (Number): Does ZERO mean "nothing/absence"? YES = RATIO (age, weight, height, packets, bytes, duration, income). NO = INTERVAL (temp C/F, dates, pH, calendar year).
  • NOIR HIERARCHY: Nominal < Ordinal < Interval < Ratio = increasing information. Ratio is richest (all arithmetic operations valid: +, -, *, /).
  • SECURITY TRICKY CASES: IP address = NOMINAL (label, no meaningful order). Port number = NOMINAL (NOT ratio - port 80 is not "twice" port 40, arithmetic meaningless). Severity rating = ORDINAL. Timestamp/date = INTERVAL. Packet size in bytes = RATIO. Duration in seconds = RATIO. Temperature C/F = INTERVAL (0 degrees is NOT absence of temperature).
EXAM TRAPS - 20 MOST LIKELY MISTAKES
  • 1. "Accept H0" is WRONG. Correct: "fail to reject H0" or "insufficient evidence to reject."
  • 2. Z-test tests the MEAN (not median). Use median for skewed data descriptions, but z-test is about mu.
  • 3. Use n-1 for SAMPLE variance (Bessel correction). Use N for population variance. Get this wrong = wrong answer.
  • 4. P-value is NOT P(H0 is true). It IS P(getting data this extreme OR more extreme | H0 is true).
  • 5. Large p-value does NOT "prove H0 true." It means insufficient evidence to reject. Absence of evidence != evidence of absence.
  • 6. Pie chart BAD for comparison (angle/area perception poor). Bar chart ALWAYS better for comparing values.
  • 7. "Mean chases the tail." Right-skew -> mean > median > mode. Left-skew -> mean < median < mode.
  • 8. Port numbers are NOMINAL not ratio. Arithmetic on port numbers is meaningless.
  • 9. IQR fence = 1.5*IQR added/subtracted from Q1 and Q3 (NOT from min/max, NOT 1.5*Q1).
  • 10. Type I = false alarm (alpha, reject true H0). Type II = missed detection (beta, fail to reject false H0). Power = 1 - beta.
  • 11. SAST = static, no execution, WHITE-box, early dev. DAST = dynamic, app running, BLACK-box, runtime.
  • 12. Data-ink ratio: MAXIMIZE (more data, less junk). Tufte says remove everything that doesn't show data.
  • 13. Stratified = sample FROM every group (bit from each). Cluster = take WHOLE groups (everything from few). EASY TO CONFUSE.
  • 14. Temperature C/F = INTERVAL (not ratio). 0 degrees C does NOT mean "no temperature." Height/weight/age = RATIO.
  • 15. Bar chart has GAPS between bars (categories). Histogram bars TOUCH (continuous numeric ranges).
  • 16. Variance is in SQUARED units. That's why we take sqrt to get SD back in original units.
  • 17. Alpha chosen BEFORE looking at data, never after. H1 determines WHERE rejection region goes, alpha determines HOW BIG.
  • 18. Two-sided test: DOUBLE the tail probability. p = 2 * P(Z >= |z|). Forgetting to double = wrong p-value.
  • 19. Heartbleed fix = validate payload length. Equifax = apply patch timely. XZ = trust exploitation over 3 years.
  • 20. Correlation does NOT mean causation. r only measures LINEAR relationships. Non-linear pattern can have r near 0.
IMPUTATION METHODS COMPARISON
  • MEAN/MEDIAN/MODE: Simplest. Fast. Drawback: underestimates variability (makes data look less spread). Use for: MCAR data, small % missing, quick-and-dirty.
  • CONSTANT VALUE: Replace all missing with fixed value (0, "Unknown", "N/A"). Use for: categorical data, when missingness itself is informative.
  • LINEAR INTERPOLATION: Estimate between two known data points using straight line. Use for: time-series with smooth, gradual trends.
  • FORWARD FILL (ffill): Carry last known value forward in time. Use for: time-series, status data, sensor readings. Assumes "stays the same until changed."
  • BACKWARD FILL (bfill): Carry next known value backward. Use for: when future value is better estimate than past value.
  • KNN IMPUTATION: Average of k nearest neighbors (using distance in feature space). Better: preserves relationships between variables. Slower: O(n^2) computational complexity. Good for: moderate missing data with complex patterns.
  • MODEL-BASED: Use regression, decision tree, or neural net to PREDICT missing values from other features. Best accuracy. Most complex to implement. Use for: large datasets with many features, when accuracy critical.

KEY BREACHES, CVEs & CASE STUDIES
  • HEARTBLEED (2014): CVE-2014-0160. OpenSSL. Missing bounds check on TLS heartbeat payload length. Returns up to 64KB extra memory per request. ~17% web servers affected. Fix = validate length. Lesson: one missing check = catastrophic data leak.
  • EQUIFAX (2017): CVE-2017-5638. Apache Struts. 147M records. Patch available MONTHS before breach. Lesson: patch management failure. Most preventable major breach.
  • XZ UTILS (2024): CVE-2024-3094. 3-year social engineering to become trusted maintainer. Backdoor in liblzma targeting sshd via glibc IFUNC. Deliberate (not accident). Supply chain. Caught by accident (Andres Freund noticed 500ms SSH delay).
  • CROWDSTRIKE (2024): Config update (Channel File 291). Content Validator had its own bug. 8.5M Windows BSOD. NOT a hack - software quality failure. Single defective line = global outage. Lesson: QA/testing IS security.
  • SOLARWINDS (2020): SUNBURST backdoor inserted into Orion build process. 18,000+ orgs received compromised update. US govt agencies breached. Supply chain attack via build system compromise.
  • CVE PROGRAM: MITRE maintains. Unique ID for each public vulnerability (CVE-YEAR-NUMBER). NIST NVD adds severity scores (CVSS). Used industry-wide for tracking/communication.
  • SUPPLY CHAIN ATTACKS: Tamper with third-party code/tools to compromise downstream users. Growing trend: 925 attacks/week per org (Check Point). Trust in open-source maintainers = vulnerability. Dependencies = attack surface.

WORKED EXAMPLES & CALCULATIONS
  • SD CALCULATION: Data: 4,2,5,1,3,6,2,4,3,5 (n=10). Sum=35. Mean=3.5. Sum of Xi^2 = 16+4+25+1+9+36+4+16+9+25 = 145. S^2 = (1/9)*(145 - 35^2/10) = (1/9)*(145-122.5) = (1/9)*22.5 = 2.5. S = sqrt(2.5) = 1.58.
  • Z-SCORE EXAMPLE: Mean=42, SD=11. Data point=53. Z = (53-42)/11 = 11/11 = 1.0. This point is exactly 1 SD above mean. Within normal range (68% band). Not an outlier.
  • IQR EXAMPLE: Data quartiles: Q1=10, Q3=30. IQR = 30-10 = 20. Mild fence: [10-30, 30+30] = [-20, 60]. Extreme fence: [10-60, 30+60] = [-50, 90]. Test value 65: mild outlier (outside 60 but inside 90). Test value 95: extreme outlier (outside 90).
  • CLASS RECIPE EXAMPLE: n=40 observations, min=110, max=152. R = 152-110 = 42. m = 1 + 3.3*log10(40) = 1 + 3.3*1.602 = 1 + 5.29 = 6.29, round to 6 classes. Width = 42/6 = 7. Classes: [110,117), [117,124), [124,131), [131,138), [138,145), [145,152].
  • Z-TEST EXAMPLE: H0: mu=1000, H1: mu<1000 (left-tail), alpha=0.05. n=16, X-bar=967.8, sigma=128. SE = 128/4 = 32. Z = (967.8-1000)/32 = -1.006. Critical value = -1.645. Since -1.006 > -1.645, do NOT reject H0. p = P(Z <= -1.006) = 0.1562 > 0.05, same conclusion.
  • CHEBYSHEV EXAMPLE: Mean=100, SD=15. k=2: at least 1-1/4=75% of data within [70, 130]. k=3: at least 1-1/9=88.9% within [55, 145]. Works regardless of distribution shape.
  • EMPIRICAL RULE EXAMPLE: Bell-shaped data, mean=500, SD=50. 68% within [450, 550]. 95% within [400, 600]. 99.7% within [350, 650]. Value of 360 = within 3 SD (normal). Value of 340 = beyond 3 SD (anomaly flag).
  • VARIANCE SHORTCUT: S^2 = [sum(Xi^2) - n*(X-bar)^2] / (n-1). Faster than computing each deviation separately. Same answer.
HYPOTHESIS TESTING - COMPLETE REFERENCE
  • SETUP: H0 always has = (mu=value, mu>=value, mu<=value). H1 has inequality (!=, <, >). H1 is what researcher suspects/wants to prove.
  • LEFT-TAIL TEST: H1: mu < mu0. Rejection region on LEFT. Reject if Z < -Z_alpha. p = P(Z <= z_computed). Example: "mean is LESS than claimed."
  • RIGHT-TAIL TEST: H1: mu > mu0. Rejection region on RIGHT. Reject if Z > Z_alpha. p = P(Z >= z_computed). Example: "mean is GREATER than claimed."
  • TWO-TAIL TEST: H1: mu != mu0. Rejection regions on BOTH sides. Reject if |Z| > Z_alpha/2. p = 2*P(Z >= |z_computed|). Example: "mean DIFFERS from claimed (either direction)."
  • COMMON CRITICAL VALUES: alpha=0.10: Z=1.28 (one-tail), 1.645 (two-tail). alpha=0.05: Z=1.645 (one-tail), 1.96 (two-tail). alpha=0.01: Z=2.33 (one-tail), 2.576 (two-tail).
  • P-VALUE INTERPRETATION: p < 0.01 = very strong evidence against H0. 0.01 < p < 0.05 = moderate evidence. 0.05 < p < 0.10 = weak evidence. p > 0.10 = little/no evidence against H0. Always compare to YOUR chosen alpha.
  • SECURITY ANALOGY: H0 = "system is secure/normal." Type I (alpha) = false alarm (alert on normal traffic, wastes analyst time). Type II (beta) = missed attack (real intrusion goes undetected, catastrophic). In security, Type II is usually WORSE (miss a breach vs false alarm).
  • INCREASING POWER: Increase sample size n (most effective), increase alpha (accept more false alarms), increase true effect size (can't control), decrease variability (better measurements). Bigger n reduces BOTH Type I and Type II errors.
13 ANTI-PATTERNS - EXPANDED WITH EXAMPLES
  • #1 EXCEEDING SCREEN: Scrolling/tab-switching = context lost. Short-term memory holds ~4 chunks. If user must scroll, most important info may be invisible. Solution: prioritize ruthlessly, remove non-essential.
  • #2 NO CONTEXT: Gauge showing "85%" means nothing alone. Compared to WHAT? Last month? Industry average? Target? Always provide comparison baseline (forecast, budget, historical, benchmark).
  • #3 EXCESSIVE PRECISION: Revenue "$1,234,567.89" on a dashboard. Nobody needs 9 digits at a glance. Round to meaningful precision: "$1.2M" conveys same insight faster.
  • #4 DEFICIENT MEASURE: Showing "Budget: $500K, Actual: $480K" when what matters is the VARIANCE ($20K under, 4% savings). Choose the measure that directly answers the question.
  • #5 WRONG VIZ TYPE: Using pie chart to compare 12 categories (impossible to read small slices). Using line chart for categorical data. Match chart type to data relationship.
  • #6 MEANINGLESS VARIETY: Using bar, line, pie, gauge, and scatter on same dashboard for no analytical reason. Variety for variety's sake = cognitive load. Use different types only when data REQUIRES it.
  • #7 BAD VIZ DESIGN: 3D bar charts (depth distorts height perception). Exploded pie charts. Circular gauge when linear scale clearer. Keep it simple and 2D.
  • #8 INACCURATE ENCODING: Y-axis starting at 50 instead of 0 makes 5% difference look like 500% difference. Truncated axes MISLEAD. Dual-axis charts can also mislead if scales differ wildly.
  • #9 POOR ARRANGEMENT: Most important info should be TOP-LEFT (where eye goes first). Related metrics should be NEAR each other. Don't make user hunt for context across the screen.
  • #10 BAD HIGHLIGHTING: If everything is bold/colored/large, NOTHING stands out. Highlight only what needs immediate attention. Use color/size sparingly for alerts and KPIs.
  • #11 DECORATION CLUTTER: Faux-metal gauge borders, gradient backgrounds, decorative images. Every pixel should earn its place by conveying data or aiding comprehension.
  • #12 COLOR MISUSE: Random colors with no meaning. Red for "good" and green for "bad" (reversed convention). Too many colors (>7 categories = hard to distinguish). Be intentional.
  • #13 UGLY DESIGN: Poor alignment, inconsistent fonts, clashing colors, cramped layout. Aesthetics matter for credibility and usability. Clean design = trusted dashboard.
PRIVACY LAWS, DBIR & SAMPLING QUICK REF
  • GDPR (EU): General Data Protection Regulation. Consent required. Data minimization (collect only what needed). Rights: access, correct, delete ("right to be forgotten"), portability. 72-hour breach notification. Fines up to 4% global revenue or 20M EUR.
  • CCPA (California): Right to KNOW what data collected. Right to DELETE. Right to OPT-OUT of SALE of personal info. Applies to businesses meeting revenue/data thresholds. California Privacy Rights Act (CPRA) expanded it.
  • OTHER LAWS: PIPEDA (Canada - consent-based, similar to GDPR). LGPD (Brazil - modeled after GDPR). DPA 2018 (UK - post-Brexit GDPR equivalent, maintains similar protections).
  • DBIR KEY STATS: 60% breaches = human element. 30% = third-party involvement. 17% = espionage-motivated. Credential abuse = 22% of initial access. Vulnerability exploitation = 20%. Phishing = 16%. System Intrusion = 53% of breach patterns. Internal actors = 10x more records than external.
  • SAMPLING DECISION: Want representation of ALL subgroups? -> Stratified. Limited budget, groups are geographically scattered? -> Cluster. No special requirements? -> Simple Random. Have ordered list? -> Systematic (every m-th).
  • SIMPLE RANDOM: Every unit has EQUAL chance of selection. Gold standard. Use random number generator or lottery. Requires complete sampling frame (list of all units).
  • SYSTEMATIC: Pick random start, then every m-th item. m = N/n (population size / desired sample size). Risk: if data has hidden periodicity matching m, sample is biased.
  • NON-REPRESENTATIVE SAMPLE: Leads to WRONG conclusions about population. Sample MUST represent the population it claims to describe. Selection bias = biggest threat to validity.
